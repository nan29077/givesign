## 1. 높음 6건

문자 템플릿은 예외입니다. 샌드박스 발송이 같은 템플릿을 써야 하므로 **조회(GET)는 열어 두고 등록·수정(POST)만 막았습니다** — 승인된 템플릿은 운영 발송에 그대로 쓰이는 설정이라 테스트 키로 바꿀 수 있으면 안 됩니다.

문서(`/studio/docs`)에도 "테스트 키가 닿는 범위는 `/sandbox/*`, `/charges` 계열, `/mt/*` 뿐" 이라고 명시했습니다.

### H-2. 샌드박스 이벤트 위조

`{ sandbox: true, ...body.data }` 를 `{ ...body.data, sandbox: true }` 로 뒤집었습니다. 이제 요청 본문에 `"sandbox": false` 를 넣어도 표식이 덮이지 않습니다.

### H-3. 문자 치환값 검수

`reviewVariableValues()` 를 새로 만들어 발송 시점에 치환값을 검사합니다. 값 하나당 40자, 링크·줄바꿈·중괄호·광고 표현·금칙어·개인정보를 모두 거부합니다(`400 INVALID_VARIABLES`).

본문 검수는 등록 시점 한 번이라는 기존 원칙은 그대로 두었습니다. 치환값은 발송할 때마다 새로 들어오는 값이라 등록 시점에는 볼 수가 없어서, 여기서만 예외를 둔 것입니다. 본문 검수와 달리 광고 표현도 보류가 아니라 **거부**합니다 — 보류시킬 사람이 없기 때문입니다.

### H-4. 웹훅 SSRF

문자열 정규식을 대역 판정으로 바꿨습니다. `127.0.0.2`, `0.0.0.0/8`, `169.254.x`(클라우드 메타데이터), `[::1]`, `fc00::/7`, `fe80::`, 100.64/10(통신사 NAT), IPv4 사상 주소를 모두 막습니다. 전송할 때마다 이름을 다시 풀어 확인해 DNS 리바인딩을 막고, `redirect: 'manual'` 로 302 경유 내부망 접근도 차단합니다.

이름 풀이가 **실패한** 경우는 막지 않습니다. 막아야 할 것은 "풀렸는데 내부망인 주소" 이고, 풀리지 않는 이름은 fetch 도 똑같이 실패합니다. 조회 실패를 차단으로 다루면 사내 DNS 가 잠깐 흔들릴 때 전 사회복지기관 웹훅이 함께 멈춥니다.

### H-5. 정산 재시도가 환불 건을 덮는 문제

결제 건 확정을 `markSettlementPaid` 안으로 옮겨 지급 분개와 같은 트랜잭션에서 처리하고, 조건에 `status ∈ PAID_STATUSES` 를 추가했습니다. 이제 이미 환불된 건은 어떤 경로로도 `SETTLED` 로 되살아나지 않습니다. 재시도 전에는 잔액을 다시 확인해, 실패 이후 환불로 잔액이 줄었으면 이체하지 않고 거절합니다.

### H-6. 배송 상태 전이

상태별 허용 전이표(`SHIPMENT_TRANSITIONS`)를 만들었습니다. `DELIVERED → PREPARING` 같은 되돌리기가 막혀 시각이 지워지지 않고, 발송 안내 문자가 두 번 나가지 않습니다. 환불되었거나 환불 요청 중인 주문은 발송 단계로 갈 수 없습니다. 일괄 발송도 같은 표를 씁니다(전에는 `SHIPPED` 와 반품만 걸러 `DELIVERED`·`CANCELED` 주문을 조용히 덮었습니다).

## 2. 중간 17건

파트너 API 쪽은 멱등키 동시 요청이 500 대신 처음 결과를 돌려주도록 P2002 를 처리했고(M-1), 웹훅 재전송 큐가 집어 온 건을 선점하도록 바꿔 크론이 겹쳐 돌아도 같은 이벤트가 두 번 나가지 않게 했습니다(M-2). 문서가 "준비 중" 으로 표시하던 `payer.linked`·`product.stock_low` 를 실제 발행에 맞게 고쳤고(M-3), 일일 발송 한도의 하루 경계를 서버 시간대가 아닌 KST 자정으로 맞췄습니다(M-4). 상품 일괄 동기화는 전부 검사한 뒤 한 트랜잭션에서 반영하도록 바꾸고 `(사회복지기관, sku)` 유니크 제약을 추가했으며(M-5), 문자 발송에서 플랫폼 차단 후원자도 함께 확인합니다(M-6).

관리자 콘솔은 수동 "지급 완료" 가 결제 건을 `SETTLED` 로 확정하지 않던 문제를 H-5 와 같은 방식으로 함께 해결했습니다(M-7). 지급 실패 회차를 영영 반려할 수 없던 조건을 고쳐(M-8) 묶인 결제 건이 미지급으로 갇히지 않게 했고, 반려 시 확정된 건이 남아 있으면 오류 로그로 사람이 확인하게 했습니다(M-9). 환불 승인은 선점 시각을 함께 기록해, PG 취소를 기다리는 사이에 되돌려지고 다시 승인되어 원장에 반대분개가 두 번 쌓이는 경로를 막았습니다(M-10). `?role=constructor` 같은 프로토타입 키가 통과해 목록이 500 으로 죽던 것은 `Object.hasOwn` 으로 고쳤습니다(M-11).

결제·정산 쪽은 환불 시 한도 롤백 기준이 항상 `paidAt` 으로 떨어지던 것을 선점 전에 잡아 둔 승인 거래의 `requestedAt` 으로 바로잡았고(M-12), 판정 트랜잭션 커밋 후 결제대행 호출 전에 예외가 나면 예약한 한도·재고를 되돌리도록 했습니다(M-13). PIN 승인 중 예외가 나면 세션을 되돌려 다시 시도할 수 있게 했습니다(M-14) — 전에는 세션은 완료, 결제는 대기로 남아 아무도 풀 수 없었습니다.

인프라·인증은 Redis 재연결을 5회에서 무제한(간격 최대 10초)으로 바꿔 페일오버 한 번에 한도 카운터가 통째로 인메모리로 내려앉지 않게 했고(M-15), 인증번호 오입력 횟수를 원자적 카운터로 분리해 동시 요청 우회와 TTL 연장을 함께 없앴습니다(M-16). 웹 결제 PIN 요청에는 번호당 하루 한도를 추가해 특정인 대상 문자 반복을 제한했습니다(M-17).

## 3. 낮음 27건

사회복지기관 콘솔은 `parseInt` 가 `"1,000"` 을 1 로 읽던 자리를 전부 고쳤고(재고·유효기간·입력 단위), 직접 입력 최대 금액의 하한 검사, IP 허용목록의 실제 범위 검증(`300.1.1.1`·`/99` 거부), 키 발급 시 잘못된 IP 를 조용히 버리지 않고 오류로 알리기(발급 **전에** 검사), 약속만 있고 없던 "되돌리기" 버튼 추가, 일괄 발송의 완료·취소 주문 보호, 보류 처리 시 지급 시각 삭제, 이미 판매를 끈 마지막 상품 보관 허용, `?page=1.5`·`?month=9999-12` 로 인한 500 제거, 배송 요청 메모의 전화번호 가리기를 했습니다.

관리자 콘솔은 템플릿 검수·회원 상태 변경을 상위 권한으로 올리고 화면 버튼도 같은 기준으로 잠갔으며, 지급 결과 일괄 반영에 회차 목록 감사 기록을 추가하고, 수수료 정책의 과거 시작일을 막고, MO 번호 회수 시 배정을 함께 풀고, `//evil.com` 이 통과하던 URL 검사를 고치고, 마지막 최고관리자 보호에 계정 상태를 반영하고(강등·정지 양쪽), 권한 안내 문구를 실제 제한과 맞췄습니다.

API·문서는 응답 형식(`{ok, items}` / 최상위 `code`), 시각 표기(UTC `Z`, KST 는 날짜 묶음만), 멱등키 적용 범위(문자 발송만), 배송 API 의 자동 문자 문구 삭제, 배송지 원문이 내려간다는 사실과 감사 기록 명시를 바로잡았습니다. 통계의 환불 건수가 항상 0 이던 것을 고치고 환불 금액을 함께 내려주며, OpenAPI 에 빠져 있던 경로 변수를 자동으로 채우고 타입 매핑(boolean·배열·날짜)을 실제 타입으로 바꿨습니다. IP 허용목록은 프록시가 붙인 형태를 정규화하고 CIDR 표기를 실제로 판정하도록 했습니다.

그 밖에 PIN 콜백의 검증 실패 요청에 IP 당 횟수 제한을 걸어 인증 없이 로그 테이블을 채우지 못하게 했고, 웹 결제 진행 쿠키에 서명을 붙여 남의 결제 상태를 들여다볼 수 없게 했으며, 결제수단 등록 후 자동 계정 연결을 **번호가 같을 때만** 하도록 좁혔습니다(로그인 CSRF). 운영 기동 점검에 발신번호 기본값(`15880000`) 경고를 추가하고, 일일 발송 한도 환경변수가 숫자가 아니면 한도가 통째로 사라지던 문제를 기본값 복귀로 막았습니다.

## 5. 배포 전 확인할 것

**마이그레이션이 하나 추가되었습니다.** `20260909120000_product_sku_unique` — 사회복지기관 안에서 상품 `sku` 를 유일하게 만듭니다. 빈 DB 에서는 정상 적용되는 것을 확인했지만, **운영 DB 에 이미 같은 sku 가 두 건 이상 있으면 이 마이그레이션은 실패합니다.** 적용 전에 아래로 확인해 주세요.

```sql
SELECT merchant_id, sku, count(*) FROM charge_product
 WHERE sku IS NOT NULL GROUP BY 1,2 HAVING count(*) > 1;
```

결과가 나오면 한쪽 sku 를 바꾸거나 비운 뒤 적용하면 됩니다. 마이그레이션 파일 주석에도 같은 안내를 적어 두었습니다.

**동작이 달라지는 것** 세 가지를 미리 알려 드립니다. 첫째, 이미 테스트 키로 상품·웹훅 API 를 쓰던 사회복지기관이 있다면 이제 403 을 받습니다(문서에 명시했고, 애초에 의도된 사용법이 아니었습니다). 둘째, 배송 상태를 되돌리던 운영 방식이 있었다면 막힙니다. 셋째, 수수료 정책의 적용 시작일을 과거로 잡을 수 없습니다.

**커밋·푸시는 하지 않았습니다.** 늘 하시던 대로 확인 후 직접 올려 주세요.
