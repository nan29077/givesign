## 1. 사회복지기관 귀속 모델 — 대표님 설명이 코드와 정확히 일치합니다

### 확인한 것

`src/server/services/charge-flow.ts` 의 `routeMerchant()` 를 직접 확인했습니다.

- 결제가 **어느 사회복지기관의 매출인가**는 후원자가 문자를 보낸 **MO 번호**가 결정합니다.
  - 전용번호(DEDICATED): 번호 하나 = 사회복지기관 하나
  - 대표번호(SHARED_PREFIX): 대표번호 + 문자 맨 앞 키워드 = 사회복지기관
- 결제자(`PayerProfile`)는 **전화번호 기준으로 전역 1개**입니다. 사회복지기관별로 따로 만들지 않습니다.
- 결제수단(빌링키)도 결제자에 붙습니다. 사회복지기관에 붙지 않습니다.

즉 **카드 한 장으로 A 편의점, B 음식점에서 각각 결제하면 각 매장 매출로 잡히는 구조 그대로**입니다. 코드가 이미 그렇게 되어 있습니다.

### 한도도 이 모델에 맞게 두 층으로 되어 있습니다

`src/server/services/limits.ts` 확인:

| 한도 | 범위 | 기본값 |
|---|---|---|
| `payerDailyLimit` | 전 사회복지기관 합산 / 1일 | 100,000원 |
| `payerMonthlyLimit` | 전 사회복지기관 합산 / 1개월 | 1,000,000원 |
| `perMerchantDailyLimit` | 사회복지기관 1곳 / 1일 | 정책값 |

카드와 같습니다. 카드 자체의 한도가 있고, 그 안에서 사회복지기관별로 쓰는 것과 동일합니다.

### 이 모델을 지키는 안전장치도 있습니다

같은 MO 번호에 전용번호 배정과 대표번호 공유 배정이 **동시에 걸려 있으면** 라우팅을 아예 중단하고 관리자에게 알립니다. 이 방어가 없으면 대표번호를 쓰던 여러 사회복지기관의 결제가 전용 사회복지기관 한 곳으로 전부 흘러들어가는데, **후원자도 사회복지기관도 알아챌 수 없는 사고**라서 막아 둔 것입니다. (`charge-flow.ts` 라우팅 충돌 검사)

**결론: 이 부분은 손댈 것이 없습니다.**

## 2. 본인인증 — 헥토 API 연결 전제를 반영한 재정리

### 대표님이 정리해 주신 흐름

1. 후원자가 사회복지기관 MO 번호로 문자를 보낸다
2. 헥토(또는 빌링키 업체)가 PIN 입력을 요청한다
3. 그 이전에 이미 헥토 쪽에 **휴대폰 번호와 매칭된 계좌/카드 소유주 정보**가 등록되어 있다
4. API가 연결되면 그 **소유주 정보가 우리 서버로 내려온다**

이 전제는 코드 주석에도 이미 적혀 있습니다 — `src/app/mock/pg/register/mock-register-form.tsx:10`:
> 실제 헥토파이낸셜 결제창에서는 계좌 인증과 ARS/휴대폰 본인확인이 금융기관을 통해 수행된다.

### 그래서 철회하는 지적 3건

| 번호 | 원래 지적 | 철회 사유 |
|---|---|---|
| ① | PC 결제 링크(`startWebPinCharge`)에 OTP가 없다 | 링크는 **이미 등록된 번호로만** 문자 발송되고, 승인은 헥토 화면에서 PIN을 넣어야 난다. 번호를 안다고 남의 문자를 받을 수는 없으므로 탈취 경로가 없다. |
| ② | PIN 요청 문자가 임의 문자 발송 통로가 될 수 있다 | `tplPinRequest` 확인 결과 사회복지기관명 + 금액 + 링크만 들어간다. 요청자가 쓴 본문은 들어가지 않는다. 번호당 10분에 3건 제한도 걸려 있다. |
| ③ | 본인확인 근거가 없다 | **조건부 철회.** 헥토 API 연결 후에는 소유주 정보를 받으므로 해결된다. 다만 아래 3-1의 준비가 필요하다. |

### 2-3. CI를 저장하면 한 번에 풀리는 문제 3가지

| 문제 | 지금 | CI 저장 후 |
|---|---|---|
| **한도 우회** | 식별 기준이 전화번호. 한 사람이 번호 3개로 등록하면 일/월 한도가 **3배**가 된다 | CI는 사람 단위. 번호가 몇 개든 한 사람으로 합산 |
| **번호 재사용** | 통신사가 해지 번호를 6개월 뒤 다른 사람에게 재배정한다. 예전 주인의 빌링키가 그대로 붙어 있으면 새 주인이 문자 한 통으로 남의 카드를 긁는다. 재인증 로직 없음 | CI가 달라지면 재등록을 강제할 수 있다 |
| **분쟁 대응** | "나는 결제한 적 없다"에 낼 수 있는 자료가 번호와 빌링키뿐. 헥토에 물어봐야 한다 | 우리 선에서 소명 가능 |

**헥토 계약/연동 규격서에서 확인하실 것**: 빌링키 등록 응답에 **CI 또는 DI, 실명, 생년월일(또는 성인여부)** 이 내려오는지. 통상 내려옵니다.

## 3. 파트너 API — 제가 잘못 보고했습니다. 정정합니다.

### 무엇을 잘못 말했나

두 가지 **서로 다른** 문제를 하나로 묶어서 A/B/C/D 선택지를 드렸습니다. 혼란을 드려 죄송합니다.

| | 문제 | 대상 |
|---|---|---|
| (a) | GET 요청에 서명이 없다 | **키가 도난당했을 때**의 위험 |
| (b) | 결제자 전화번호가 평문으로 나간다 | **정상적인 사회복지기관**에게 나가는 데이터 |

**서명을 걸어도 (b)는 그대로입니다.** 서명은 "이 요청이 진짜 그 사회복지기관이 보낸 것인가"를 확인할 뿐, 정당한 사회복지기관에게 무엇을 보낼지와는 무관합니다. 제가 이 둘을 섞었습니다.

### (b)는 결함이 아닙니다 — 필요한 데이터 흐름입니다

대표님이 설명해 주신 모델을 적용하면 답이 분명해집니다.

후원자가 **A 사회복지기관의 MO 번호로** 문자를 보내 결제했습니다. A 사회복지기관은 자기 사이트 회원에게 포인트를 적립해야 합니다. **회원을 특정하려면 전화번호가 필요합니다.** 이것이 이 API의 존재 이유입니다.

즉 이것은 기술로 막을 사안이 아니라 **계약·약관으로 처리할 사안**입니다.

- 이용약관에 **개인정보 제3자 제공 동의**(제공받는 자: 결제한 사회복지기관 / 항목: 휴대폰번호 / 목적: 포인트 적립 / 보유기간) 명시
- 사회복지기관 연동 규격서에 **처리위탁 조항** 및 목적 외 이용 금지 명시

코드 쪽에는 이미 배려가 되어 있습니다 — 번호를 저장하고 싶지 않은 사회복지기관을 위해 `payerRef`(고정 해시)와 `payerPhoneMasked`(마스킹)를 함께 내려주고 있습니다. (`src/app/api/partner/v1/charges/route.ts`)

### "기존 사회복지기관 연동이 깨진다"는 말도 정정합니다

이건 제가 **일반론으로 한 말이고, 이 시스템에는 해당되지 않습니다.**

- 서비스가 아직 오픈 전입니다 (결제 어댑터 mock, 헥토 미계약)
- 발급된 사회복지기관 API 키가 없습니다
- **깨질 연동 자체가 존재하지 않습니다**

따라서 **지금 GET에 서명을 필수로 거는 비용은 0입니다.** 오픈 후에 바꾸려면 연동한 사회복지기관 전부에게 재작업을 요구해야 하지만, 지금은 그럴 대상이 없습니다.

### 그래서 남는 실제 과제 2건

**① GET 서명 필수화 (권장 — 지금 하면 비용 0)**

현재 `authenticatePartner()` 는 GET에 대해 Bearer 키만 있으면 통과시킵니다. 키 하나가 유출되면 그 사회복지기관의 **결제자 명단 전체**(전화번호·이름·주소 포함)가 새어 나갑니다. 분당 300회 제한이 있지만, 회당 최대 500건이므로 1분에 15만 건까지 긁을 수 있습니다.

수정 위치: `src/server/services/partner-auth.ts` — `const writeMethod = method !== 'GET' && method !== 'HEAD';` 를 제거하고 모든 요청에 서명을 요구. 연동 규격서 예제도 함께 수정.

**② 접속기록이 없습니다 (신규 · 법정 의무)**

지금은 어느 사회복지기관이 언제 몇 건의 개인정보를 가져갔는지 남는 기록이 없습니다. 개인정보보호법상 개인정보처리시스템 **접속기록 보관 의무** 대상입니다(최소 1년, 고유식별정보 처리 시 2년).

남길 항목: 사회복지기관 ID, API 키 ID, 시각, 요청 IP, 조회 건수, 조회 범위(since/cursor). **전화번호 자체는 로그에 남기지 않습니다.**

## 4. 수수료 부가세 — 확정. 현재 기본값이 방침과 반대입니다.

### 대표님 방침

> 수수료는 무조건 부가세를 포함한 금액으로 받는다.
> 부가세 별도 요율이면 **5% + 0.5% = 5.5%**, 부가세 포함 요율이면 **5.5%** 를 적용한다.

즉 **최종 차감은 언제나 5.5%** 여야 합니다.

### 계산기 자체는 두 방식을 모두 지원합니다

`src/server/services/settlement.ts` 의 `computeFees()`:

| 설정 | 요율 입력 | 실제 차감 | 세금계산서 |
|---|---|---|---|
| `vatIncluded = false` | 5% | 5% + 부가세 0.5% = **5.5%** | 공급가 5% / 부가세 0.5% **분리 기록** ✅ |
| `vatIncluded = true` | 5.5% | **5.5%** | 부가세 **0원**으로 기록 ⚠️ |
| `vatIncluded = true` | 5% | **5%** ❌ | 부가세 0원 ❌ |

돈만 보면 위 두 줄은 같습니다. 그러나 **세금계산서 발행 시 공급가액과 부가세를 분리해야 하므로 `vatIncluded = false` 가 맞습니다.**

### 문제: 지금 기본값이 전부 세 번째 줄로 가게 되어 있습니다

| 위치 | 현재 값 |
|---|---|
| `prisma/schema.prisma` — `FeePolicy.vatIncluded` | `@default(true)` |
| `settlement.ts` — `FALLBACK_FEE_RATES` | `vatIncluded: true` |
| `src/app/admin/fees/page.tsx:148` — 새 정책 폼 | `defaultChecked` (체크된 상태로 시작) |
| 기본 요율 | PG 1.8% / 플랫폼 15% |

관리자 화면에서 **아무 생각 없이 "1.8%", "15%" 를 입력하면 부가세가 붙지 않습니다.** 그 0.18%p + 1.5%p 는 우리가 국세청에 대신 내게 됩니다.

### 3,000원 결제 기준 비교 (플랫폼 15% · PG 1.8%)

| 항목 | 지금 (포함, 요율 그대로) | 별도로 전환 후 |
|---|---|---|
| PG 수수료 차감 | 54원 | 59원 (54 + 부가세 5) |
| 플랫폼 수수료 차감 | 450원 | 495원 (450 + 부가세 45) |
| 부가세 기록 | **0원** | **50원** |
| 사회복지기관 정산금 | 2,496원 | 2,446원 |

**거래액의 약 1.68%** 가 매 건 빠집니다. (수수료 16.8% × 부가세 10%)
월 거래액 1억 기준 **월 168만원**입니다.

### 수정 계획 (5곳)

1. `prisma/schema.prisma` — `vatIncluded @default(false)` + 새 마이그레이션 추가
2. `settlement.ts` — `FALLBACK_FEE_RATES.vatIncluded: false`
3. `src/app/admin/fees/page.tsx:148` — `defaultChecked` 제거
4. 같은 화면 문구 — 요율 입력란 안내를 **"부가세 별도 요율을 입력하세요"** 로, 체크박스 라벨을 **"요율에 부가세가 이미 포함되어 있음 (비권장)"** 으로
5. `tests/fee-vat-and-settings.test.ts` — `platformFeeVat === 0n`, `feeVat === 0n` 기대값 2건 수정

### ⚠️ 먼저 확인해 주셔야 하는 것
