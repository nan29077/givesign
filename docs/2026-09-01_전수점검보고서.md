### C-2 ✔ 지급 실패 시 멱등키를 삭제해, 같은 정산분이 두 번 이체될 수 있다
`src/server/services/auto-settlement.ts:186-190`, `:206-212`

```ts
if (!result.ok) {
  await prisma.settlementRequest.update({ ... status: 'PAYOUT_FAILED' ... });
  await prisma.idempotencyKey
    .delete({ where: { scope_key: { scope: 'payout', key: `${merchantId}:${dateKey}` } } })
    .catch(() => undefined);
```

지급대행 계약은 "`requestId` 를 멱등키로 쓰고 결과를 못 받으면 `inquire()` 로 확정하며 재이체하지 않는다"(`adapters/payout/index.ts:11-14`)인데, 실패 처리에서 그날의 멱등키를 스스로 지운다. `settledAt` 도 채우지 않고 `PAYOUT_FAILED` 는 pending 대상이 아니라 가용 잔액이 그대로 복구된다.

**재현**: 실이체 967,000원 → `transfer()` 타임아웃 → `inquire()` 도 미확정(`ok:false`) → `PAYOUT_FAILED` + 멱등키 삭제. 관리자가 `runPayoutBatchAction` 으로 배치를 재실행하면 새 `SettlementRequest`(= 대행사 입장의 새 멱등키)가 만들어져 **967,000원이 한 번 더 나간다.** 원장에는 PAYOUT 1건뿐이라 967,000원 손실.

같은 결함의 다른 창: `transfer()` 성공 직후 `markSettlementPaid()` 전에 프로세스가 죽으면 회차는 `APPROVED` 로 남고 `settledAt` 도 비어 다음 배치가 또 이체한다. **`transfer()` 호출 직전에 "이체 시도함" 을 영속화하는 지점이 코드 어디에도 없다.**

**조치**: 실패 경로에서 멱등키를 지우지 않는다(상태만 `FAILED` 로 표시). 재시도는 `retryPayout` 으로만 하고, `transfer()` 직전에 회차를 `PAYOUT_ISSUED` 같은 중간 상태로 커밋한다.

참고: `auto-settlement.ts:1` 이 `withAdvisoryLock` 을 import 하지만 파일 전체에서 한 번도 쓰지 않는다(lint 경고로도 잡혔다). 즉 이 경로의 유일한 방어가 그 멱등키다.

## 잘 되어 있는 점

- **중복 승인의 최종 방어선이 애플리케이션이 아니라 DB 에 있다.** `mo_inbound_message.provider_message_id` UNIQUE, `idempotency_key(scope,key)` UNIQUE, `payment_pin_session.charge_id`/`session_id` UNIQUE, 부분 유니크 `payment_transaction_approved_uniq`. 개명 마이그레이션이 이것들을 온전히 보존했다.
- 상태 선점을 전부 조건부 `updateMany` 로 처리해(보안링크 1회 사용, PIN 세션 PENDING→COMPLETED, 환불 REQUESTED→APPROVED, 대사 UNKNOWN→APPROVED) 동시 클릭·중복 콜백·관리자 동시 처리가 승인 단계로 두 번 넘어가지 못한다.
- 결과 미확인(UNKNOWN)을 실패로 덮지 않고 관리자 대사 큐로 넘기는 판단, 한도 재검사부터 집계 예약까지를 후원자 행 `FOR UPDATE` 로 직렬화한 설계, 재고를 승인 요청 **전에** 잠금 안에서 선점하는 순서는 정확하다.
- 충전 반영을 사회복지기관 pull(파트너 조회 API + `pointStatus` 재노출)로 완전히 분리해, 반영 실패가 결제 상태를 오염시키지 않고 재시도가 자연스럽게 큐 역할을 한다.
- 원천징수를 소득세·지방소득세 각각 산출 후 각각 10원 절사하는 국내 실무 방식으로 정확히 구현했고, 환불 수수료 환입을 재계산이 아니라 **원 거래의 실제 분개 비율**로 산출해 요율 변경·부분환불에도 총 환입액이 원 차감액을 넘지 않는다.
- 세션·보안링크·재설정 토큰·파트너 API 키를 전부 HMAC 해시로만 저장하고, 재설정 성공 시 전 세션 폐기 + 잔여 링크 무효화를 한 트랜잭션으로 처리한다. 관리자 액션 25종이 예외 없이 `requireWriteAdmin` 을 거치고, 스튜디오 액션과 CSV 내보내기는 모두 `merchantId` 조건을 직접 걸어 IDOR 을 닫았다.
- 업로드는 확장자·MIME 대신 매직바이트로 판정하고 파일명을 32바이트 난수로 재생성하며, 로거가 메시지와 meta 양쪽에서 URL·전화번호·비밀키를 지운다.
