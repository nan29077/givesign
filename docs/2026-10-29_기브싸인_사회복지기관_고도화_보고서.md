## 1. 데이터 모델 (`prisma/migrations/20261029100000_givesign_welfare_domain`)

- `merchant_profile` +11 컬럼: `org_type` `representative_name` `address` `contact_*` `designated_donee(_until)` `donation_code` `fundraising_reg_no(_authority)`
- `merchant_donation_page` (기관당 1행) — 후원페이지 구성·공개 항목
- `campaign` — 키워드(`code`, 기관 내 유일)·목표액·기간·상태(DRAFT/ACTIVE/CLOSED/ARCHIVED)·결과 보고
- `charge` +3 컬럼: `campaign_id` `recurring_id` `receipt_id`
- `recurring_donation` / `recurring_run` — 약정과 월별 실행 기록 `(recurring, month, attempt)` 유일
- `payer_receipt_profile` — `resident_no_enc` + `resident_no_hash` + `resident_no_masked`
- `donation_receipt` — `(merchant, tax_year, seq)` 유일, 발급 시점 스냅샷(기부자·기관·건 목록)
- `receipt_export` — 홈택스 명세 생성 이력(행수·합계·SHA-256)
- `consent_type` += `RECEIPT_ISSUANCE` `RECURRING_DEBIT` (약관 시드 포함, 가입 화면에는 노출하지 않고 각 흐름에서 받음)
- 마지막 절에서 초안의 `system_setting` JSON 후원페이지·캠페인을 새 테이블로 이관하고 키를 지운다.

## 2. 흐름

### 2-1. 캠페인 지정후원
```
MO "김장 응원합니다" → routeMerchant(기관) → matchCampaignKeyword(모금 중 캠페인) 
  → charge.campaignId 지정, 메시지 "응원합니다" → 금액 선택(/r) 에서 캠페인 변경 가능 → 결제
웹(/c/[code]?campaign=) · 정기후원 약정에도 campaignId 를 둔다.
```
모금액은 항상 `charge.campaign_id` + PAID_STATUSES 집계(캐시 없음, 환불 반영). 키워드가 모금 기간 밖이면 일반 후원.

### 2-2. 정기후원
```
후원자 약정(/my/recurring/new) → RECURRING_DEBIT 동의 기록 → RECURRING_STARTED 문자
매일 /api/cron/recurring (Bearer CRON_SECRET, Redis 잠금)
  → nextChargeOn ≤ 오늘 인 ACTIVE 약정
  → 멱등키 recurring:{id}:{yyyy-MM} (DUPLICATE 면 건너뜀)
  → Charge(channel=RECURRING, DIRECT_TRIGGER) → executePayment (기존 한도·원장·감사문자 그대로)
  → 성공: 다음 달 같은 날 / 실패: 3일 뒤 재시도, 3회차 실패 → SUSPENDED + 안내 문자
```
실결제사에서 PIN 없는 빌키 출금은 `ALLOW_RECURRING_DEBIT=true`(금융사 승인) 전에는 SKIPPED. mock 결제사는 항상 실행(화면에 mock 표기).

### 2-3. 기부금영수증
```
후원자: /my/receipts 에서 성명·주민번호 등록(RECEIPT_ISSUANCE 동의) → 암호화 저장
기관:   /studio/receipts → 연도 선택 → 건별/일괄 발급(기관 정보 준비 필수) → RECEIPT_ISSUED 문자(열람 링크)
      → 홈택스 명세 CSV (/api/studio/receipts/export?year=) — 주민번호 원문 포함, 동일 출처 검사, 감사로그
환불 승인 → voidReceiptForRefundedCharge → 영수증 VOID, 포함 건 해제 → 기관이 "재발급"(새 번호)
```
발급 번호 `{기관코드}-{연도}-{000001}`. 기관 행 `FOR UPDATE` 로 채번. 영수증 서식은 스냅샷으로 고정되어 이후 기관 정보가 바뀌어도 발급본은 변하지 않는다.

## 4. 규칙 반영 (CLAUDE.md 절대 규칙)

- 2(mock 명시): 정기후원·영수증 화면에 mock·미승인 상태를 표시. 홈택스는 파일 생성까지만.
- 3(사후 처리 분리): 영수증 무효화·안내 문자 실패가 환불·결제 결과를 바꾸지 않음(`catch` 후 로그).
- 4(멱등): 정기후원 `recurring:{id}:{yyyy-MM}` + `recurring_run` 유일 제약.
- 6(3분리 저장): 주민번호 `enc/hash/masked`. 복호화는 홈택스 명세 생성 한 곳. 화면·문자·스냅샷은 마스킹만.
- 9(영수증 정합성): PAID_STATUSES 만 합산, 환불 시 VOID, 번호 재사용 없음.
- 10(집계 원천): 캠페인 모금액은 `charge.campaign_id` 집계.

## 6. 운영 전 확인·결정 필요

1. **MO 번호 체계** — 시드는 아직 050 번호다. 메시지페이 보고서(`2026-09-03_수신번호체계…`)의 1688 전환 결정은 기브싸인에 아직 반영하지 않았다. 중계사 계약 후 같은 6개 지점을 고친다.
2. **정기후원 실출금** — 헥토 빌키 무PIN 출금 승인 후 `ALLOW_RECURRING_DEBIT=true`. 외부 스케줄러에 `GET /api/cron/recurring` 매일 1회(권장 10:00 KST) 등록.
3. **홈택스 서식** — CSV 열 구성은 전산매체 서식을 기준으로 했으나 연도별 서식 변경에 따라 제출 전 홈택스 변환·검증 필요. 기관이 직접 제출한다.
4. **법무 검토** — 기부금품법 모집 등록(연 1천만원 이상), 공익법인 지정 확인 절차, 주민번호 수집 근거(소득세법 시행령 113조) 문안, 약관 2종(`RECEIPT_ISSUANCE`·`RECURRING_DEBIT`) 검토.
5. **숨긴 기능** — 실물 상품·배송·문서 상품은 `FEATURE_GOODS=true` 로만 노출. 후원 물품(굿즈) 용도로 되살릴지 결정.
6. **GitHub** — 새 이력으로 재생성했다. `4_깃푸시.bat` 으로 `nan29077/givesign` 에 첫 푸시(강제 푸시 필요할 수 있음).
