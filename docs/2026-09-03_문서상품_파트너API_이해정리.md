# 문서·컨텐츠 상품 확장 + 파트너 API(엠마형) — 이해한 내용 정리

작성일 2026-09-03 · **보고 전용. 개발 착수 안 함.**

---

## 0. 제가 이해한 것

지시는 두 개의 안건입니다.

**안건 A — 판매 상품에 "문서·컨텐츠"를 추가한다.**
지금은 실물 상품 / 비실물 상품 두 갈래인데, 여기에 계약서·문서 같은 것을 추가한다. 후원자가 문자로 요청하면 해당 계약서·문서가 MT 문자를 통해 요청자에게 전달된다. 모두싸인 같은 전자계약·문서인증 영역이다.

**안건 B — 이걸 API 규격서로 만들어 외부 업체에 공급한다.**
'페이사인'(모두싸인 같은 문서인증 서비스 회사)에 우리 연동 규격서를 주면, 페이사인이 **자기 사회복지기관들에게 우리가 부여한 MO 번호를 각각 나눠 준다.** 즉 기브싸인가 **인포뱅크 엠마(EMMA)와 같은 위치**에 서는 것이다. 엠마가 우리에게 회선과 번호를 공급하듯, 우리가 페이사인 같은 업체에 번호와 문자 인프라를 공급한다.

엠마는 기브싸인에는 없고 **토네이도에 설치되어 있어 그것을 참고**하면 된다.

한 문장으로: **기브싸인를 "문자로 결제받는 서비스"에서 "문자 채널을 남에게 공급하는 사업자"로 한 겹 올린다.**

계층으로 그리면 이렇습니다.

```
인포뱅크 EMMA  →  기브싸인  →  페이사인(파트너)  →  페이사인 사회복지기관  →  최종 후원자
   (회선·번호)      (번호 재분배·      (자기 고객에게        (문서 발송 주체)     (문자 요청자)
                    문자 API 공급)      번호 배정)
```

# 1. 안건 A — 문서·컨텐츠 상품

## 1-1. 지금 코드에 이미 있는 것

뼈대는 상당 부분 있습니다. 새 개념을 처음부터 만드는 게 아닙니다.

| 있는 것 | 위치 | 내용 |
|---|---|---|
| 상품 대분류 | `ProductKind` | `PHYSICAL`(실물) / `DIGITAL`(비실물) |
| 비실물 세부 유형 | `DigitalProductType` | `POINT` `VOUCHER` `PASS` **`CONTENT`(디지털 컨텐츠 — 파일·영상·이미지)** |
| 지급 방식 | `FulfillmentMode` | `MANUAL`(사회복지기관 수동) / `API`(사회복지기관 서버가 가져감) / **`INSTANT`(결제 즉시 문자 발송)** |
| 즉시 지급 문자 | `tplFulfillmentInstant` | 사회복지기관이 상품에 적어 둔 안내(코드·다운로드 주소)를 결제 완료 즉시 MT 로 발송 |

즉 **"CONTENT 상품 + INSTANT 지급"** 조합이 이미 동작합니다. "문자 요청 → 결제 → 문서가 문자로 감"의 골격은 이미 서 있습니다.

## 1-2. 그런데 계약서·문서는 기존 CONTENT 와 결정적으로 다릅니다 ★

**① 문서는 "미리 등록된 상품"이 아니라 "요청 시점에 만들어지는 개별 건"입니다.**
지금 CONTENT 는 사회복지기관이 상품에 미리 적어 둔 **고정 문구**를 모든 구매자에게 똑같이 보냅니다. 계약서는 사람마다 내용이 다릅니다. 상품 테이블에 담기는 성격이 아니라, **요청 1건 = 문서 1건**으로 따로 관리해야 합니다.

**② 문서 파일 자체는 문자에 실어 보낼 수 없습니다.**
MMS 첨부는 사실상 이미지용이고 계약서 PDF 에는 맞지 않습니다. **일회용 보안링크 + 본인확인** 방식이어야 합니다. 다행히 이 뼈대도 이미 있습니다 — 결제수단 등록 안내(REGISTER_GUIDE)와 PIN 요청(PIN_REQUEST)이 정확히 그 방식입니다.

**③ 결제가 없는 흐름이 생깁니다.** ← 가장 큰 구조 변화
문서 발송은 무료일 수 있습니다. 그런데 지금 기브싸인의 전 흐름(`ChargeStatus` 상태머신, 감사문자, 정산)은 **결제 성공을 전제**로 짜여 있습니다. 0원 또는 결제 없는 요청 흐름을 넣으면 상태머신에 새 갈래가 생깁니다. 여기서 설계 판단이 필요합니다.

**④ 법·보안 요구가 상품과 다릅니다.**
계약서에는 개인정보와 법적 효력이 있습니다. 링크 만료, 열람 로그, 재발급 통제, 다운로드 횟수 제한, 보관 기간이 필수이고, 전자서명법·전자문서법 검토가 따라옵니다.

## 1-3. 정리

"실물 / 비실물 / **문서·컨텐츠**" 3분류로 나누는 것 자체는 자연스럽고, 상품 유형만 늘리는 작업이라면 크지 않습니다. 다만 **개인화된 문서**와 **무료 발송**을 넣는 순간 상품 확장이 아니라 새 흐름 추가가 됩니다. 어디까지 갈지가 첫 결정 사항입니다.

# 2. 안건 B — 파트너 API (엠마형 공급 구조)

## 2-1. 지금 있는 "파트너 API" 는 이름만 같고 층이 다릅니다 ★

기브싸인에는 이미 `/api/partner/v1` 과 규격서(`docs/연동규격서_사회복지기관API.md`)가 있습니다.

- 엔드포인트: `ping` / `charges`(조회) / `charges/ack`(처리결과 통보) / `charges/shipment`(배송등록)
- 인증: `MerchantApiKey` — API 키 + HMAC-SHA256 서명 + IP 제한

그런데 이건 **사회복지기관 1곳 = 키 1개** 구조입니다. 페이사인 같은 채널은 **계약자 1곳이 수백 개 하위 사회복지기관을 거느리는 2단 구조**라 지금 모델로는 표현이 안 됩니다. 새 계층(파트너)이 필요합니다.

## 2-2. 토네이도의 엠마를 확인한 결과 (중요) ★

`E:\프로젝트\토네이도\src\server\emma\` 를 읽었습니다. 예상보다 훨씬 많이 준비되어 있습니다.

**① 1688 번호 체계가 이미 구현되어 있고, 이식을 전제로 짜여 있습니다.**
`src/server/emma/index.ts` 첫 주석에 이렇게 적혀 있습니다 — *"이 디렉터리는 토네이도 도메인에 의존하지 않는다. **기브싸인**·셀러브릭스에 그대로 복사해 쓰고, 각 프로젝트는 도메인 핸들러만 갈아 끼운다."*
즉 지난번에 지시하신 **기브싸인의 1688 전환은 새로 만드는 게 아니라 이식 작업**입니다.

**② 번호 구조가 지시하신 것과 정확히 같습니다.**
`1688-□□□□-XXXX` — 앞 8자리는 인포뱅크 계약 대표번호로 고정, **뒤 4자리는 인포뱅크 승인 없이 우리가 직접 부여.** 지난 지시와 한 글자도 다르지 않습니다.

**③ 채번 규칙 3가지가 이미 검증되어 있습니다.** (`src/server/services/mo-number-issue.ts`)
- **순차가 아니라 CSPRNG 난수로 뽑는다** — 0001, 0002 로 나가면 ±1 만 해 봐도 남의 번호를 알아낼 수 있다.
- **오입력이 몰리는 번호는 제외한다** — `0000 1111 … 9999 1234 4321 0123 1004 0119 0112`. (참고: 예시로 드신 `1234` 는 서브번호로는 예약어입니다. 대표번호 뒤 4자리로 쓰는 건 무관합니다.)
- **회수한 번호는 180일 냉각 후 재사용한다** — 가장 중요합니다. A 가 그만둬 회수된 번호를 곧바로 B 에게 주면, A 에게 보내던 사람의 문자가 **B 에게 실제로 결제**됩니다. 누구도 알아채지 못합니다.

**④ 엠마는 웹훅이 아니라 DB 테이블 폴링입니다.**
MO 는 `em_mo_log_YYYYMM` 을 읽고, MT 는 `em_smt_tran` 에 INSERT 하면 엠마가 픽업해 발송합니다. 기브싸인의 현재 MO 는 웹훅 전제(MTONET 어댑터)라 **어댑터를 하나 더 붙이는 형태**가 됩니다. 기존 구조를 갈아엎을 필요는 없습니다.

## 2-3. 우리가 파트너에게 제공해야 하는 것

엠마가 우리에게 해 주는 일의 대응물입니다. 다섯 덩어리로 봅니다.

1. **번호 발급·회수 API** — 파트너가 자기 사회복지기관에 번호를 붙였다 뗐다 할 수 있게. 냉각기간·예약번호 규칙은 우리가 강제한다.
2. **MO 수신 전달** — 엠마식 DB 폴링은 외부 파트너에게 줄 수 없습니다. **웹훅 푸시 + 재전송 정책**으로 제공해야 합니다.
3. **MT 발송 API** — 파트너가 자기 문구로 문자를 보낼 수 있게. 발신번호 사전등록과 스팸 정책은 우리가 건다.
4. **조회·콜백** — 발송 결과, 수신 이력, 상태 조회.
5. **파트너 콘솔** — 키 발급/폐기, 번호 재고와 할당량, 사용량·과금 확인.

# 3. 이 방향이 제품에 만드는 변화 (미리 짚을 점)

- **정체성이 한 겹 올라갑니다.** "문자로 결제받는 서비스"에서 "문자 채널 공급자(CPaaS)"가 됩니다. 결제가 전혀 없는 문자 트래픽이 들어오기 시작합니다. 지금 코드는 모든 MO 를 결제 시도로 간주합니다.
- **번호 소진.** 대표번호 1개당 서브번호는 1만 개(예약 제외 약 9,984개)입니다. 파트너가 늘면 대표번호 추가 계약이 필요하고, **파트너별 번호 할당량(쿼터)** 개념이 있어야 한 파트너가 다 써 버리는 일을 막습니다.
- **책임 경계.** 페이사인의 사회복지기관이 스팸·불법 문자를 보내면 제재받는 건 **우리 대표번호**입니다. 파트너 계약서에 책임 소재와 우리의 즉시 차단 권한이 들어가야 합니다.
- **과금 모델이 둘로 갈립니다.** 결제형(거래 수수료)과 인프라형(건당·월정액)이 섞입니다. 정산 로직이 지금은 전자만 전제합니다.
- **개인정보 위수탁.** 최종 후원자 휴대폰 번호를 우리가 보유하는지 파트너가 보유하는지에 따라 위수탁 관계와 동의 주체가 달라집니다.

# 4. 확인·결정이 필요한 것

| # | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | 후원자가 문서를 **문자(MO)로 요청**하는 게 맞는지 | 말씀 중 한 단어를 확실히 못 알아들었습니다. 흐름의 출발점이라 확인이 필요합니다. |
| 2 | 문서 발송이 **유료인지 무료인지** | 무료면 결제 없는 새 흐름이 필요합니다. 안건 A 에서 가장 큰 분기입니다. |
| 3 | 문서가 **미리 등록된 파일**인지, **건별로 생성되는 개인 문서**인지 | 전자는 기존 CONTENT 로 거의 됩니다. 후자는 새 모델이 필요합니다. |
| 4 | **페이사인**이 실제 논의 중인 곳인지, 유형을 설명하는 예시인지 | 실제라면 그쪽 요구사항을 먼저 받아야 규격서를 씁니다. |
| 5 | 파트너 구조에서 **결제·정산도 파트너를 경유**하는지, 우리와 최종 사회복지기관이 직접인지 | **가장 큰 설계 분기입니다.** 정산·세금계산서·환불 책임이 전부 여기서 갈립니다. |
| 6 | 엠마 이식을 **1688 전환과 함께 할지** 나중에 할지 | 같이 하면 번호 체계를 두 번 안 건드립니다. |
| 7 | 안건 A 와 B 의 **선후** | A(문서 상품)를 먼저 만들어 우리 서비스로 검증하고 B(파트너 공급)로 넓히는 순서를 권합니다. |

# 5. 제 판단 (참고용, 지시 아님)

- 안건 B 는 **생각보다 훨씬 유리한 자리에 있습니다.** 토네이도의 엠마 코드가 이식 전제로 짜여 있고, 번호 체계·채번 규칙·안전장치가 이미 검증되어 있습니다. 밑바닥부터 만드는 일이 아닙니다.
- 반대로 **가장 손이 많이 가는 건 안건 A 의 "결제 없는 흐름"** 입니다. 상태머신 전체가 결제 성공을 전제로 짜여 있어서, 여기를 건드리면 파급이 넓습니다.
- 순서는 **1688 전환 + 엠마 이식 → 문서 상품(유료부터) → 파트너 API** 를 권합니다. 번호 체계가 바닥이라 먼저 깔지 않으면 나머지를 두 번 고치게 됩니다.

**개발은 지시하실 때까지 진행하지 않습니다.**
