## 2. 정산 일자와 수수료 — 일괄 지정 + 사회복지기관별 조정

### 어떻게 동작하나

`FeePolicy` 에 **지급일(settlementDays)** 를 넣었습니다. 수수료율과 같은 표에 있으므로
**수수료와 지급일이 항상 한 세트로 움직입니다.**

```
전역 정책 (scope=GLOBAL)      → 모든 사회복지기관의 기본값        예) 수수료 1.8% · D+5
사회복지기관 정책 (scope=MERCHANT)  → 그 사회복지기관만 덮어쓰기        예) 수수료 1.5% · D+2
```

적용 우선순위는 **사회복지기관 정책 > 전역 정책 > 코드 기본값(D+5)** 입니다.
`resolveFeePolicy()` 한 곳에서만 판단하므로 화면·배치·계산이 절대 갈라지지 않습니다.

### 화면

- **최고관리자 → 수수료 정책**
  - 새 정책 등록 폼에 **지급일 (영업일)** 입력이 생겼습니다.
  - 적용 범위를 `전역`으로 두면 일괄 지정, `사회복지기관 개별`로 두면 그 사회복지기관만 조정됩니다.
  - 정책 이력 표에 `D+5` 형태로 표시됩니다.
- **사회복지기관 → 정산 관리 → 지급 내역**
  - 지금 적용되는 지급 주기(D+N)를 그대로 보여줍니다.

지급일은 **영업일** 기준이며 토·일과 공휴일(관리자가 관리하는 `public_holiday` 표)을 뺍니다.

## 3. 자동 지급 (사회복지기관 출금 요청 없음)

### 흐름

```
매일 1회 (은행 영업시간 안)
  GET /api/cron/payout   Authorization: Bearer ${CRON_SECRET}
        │
        ├─ 승인된 사회복지기관 중 정산계좌가 인증된 곳만 훑는다
        ├─ 지급일(결제일 + N영업일)이 도래한 결제를 모은다
        ├─ 원장 가용 잔액을 넘지 않는 범위에서 금액을 정한다
        ├─ 최소 지급 금액(PAYOUT_MIN_AMOUNT, 기본 1,000원) 미만이면 다음 회차로 이월
        ├─ 지급 회차 생성 → 즉시 승인(auto=true) → 지급대행 이체
        └─ 성공하면 원장 분개 + 결제 건에 settledAt 기록
```

### 돈이 나가는 코드라서 지킨 것

| 위험 | 대응 |
| --- | --- |
| 같은 건 이중 지급 | 지급된 결제에 `settledAt` 을 남겨 다음 회차에서 제외 |
| 같은 날 배치 중복 실행 | 멱등키 `payout:{사회복지기관}:{날짜}` + 사회복지기관 단위 advisory lock |
| 배치 동시 실행 | `cron:payout:lock` (10분 TTL) |
| 환불로 잔액이 줄었는데 그대로 지급 | 원장 가용 잔액을 넘지 않는 범위에서만 지급 |
| 대행사 응답 미수신 | **재이체하지 않고** 조회(inquire)로 확정 |
| 한 사회복지기관 실패가 전체를 막음 | 사회복지기관 단위로 예외를 가둠, 실패 시 최고관리자 알림 |
| 인증 없이 배치 호출 | fail-closed. `CRON_SECRET` 이 없으면 로컬에서만 통과 |

### 지급 실패 처리

- 실패한 회차는 `PAYOUT_FAILED` 로 남고, 결제 건은 **미정산 상태를 유지**합니다(다음 회차에 다시 잡힘).
- 최고관리자 화면에서 **지급 재시도**를 누르면, **먼저 대행사에 조회**해 이미 나갔는지 확인한 뒤
  성공 기록이 없을 때만 다시 이체합니다. (이중 지급 차단)

### 계좌 미인증 사회복지기관

지급하지 않고 **다음 회차로 이월**합니다. 금액은 사라지지 않습니다.
최고관리자 화면의 **지급 보류(계좌)** 지표에 사회복지기관과 금액이 표시됩니다.

> ⚠️ 지급대행은 아직 **mock** 입니다(`PAYOUT_PROVIDER=mock`). 실제 이체는 일어나지 않으며,
> 관리자 화면에 mock 임을 명시했습니다. 대행사 계약 후 어댑터만 교체하면 됩니다.

## 4. 포인트 지급 처리 (비실물)

포인트는 **사회복지기관이 발행**합니다. 기브싸인는 결제·정산만 하고 외부를 호출하지 않습니다.

- 사회복지기관 → **후원 내역** 에서 `지급 대기 / 지급 완료 / 보류` 로 걸러 보고,
  체크박스로 골라 **일괄 지급 완료 / 보류(사유 필수) / 되돌리기** 를 처리합니다.
- **CSV 내려받기** 로 목록을 받아 자기 시스템에서 처리할 수도 있습니다.
  (수식 인젝션 차단 · UTF-8 BOM · 번호는 마스킹만)
- 후원자 마이페이지에는 `포인트 지급 완료 / 대기 / 보류` 가 표시되고,
  **지급 주체는 사회복지기관**이라는 안내가 함께 나갑니다.

## 5. 상품 설정 (신규)

사회복지기관 관리자에 **상품 설정** 메뉴를 새로 만들었습니다. (`/studio/products`)

### 비실물 상품

| 항목 | 설명 |
| --- | --- |
| 유형 | **포인트 · 상품권 · 이용권** |
| 판매 금액 | 결제 한도 범위 안에서만 |
| 지급 수량 | 비우면 포인트는 금액과 1:1. 크게 적으면 **보너스 지급** |
| 지급 단위 | 포인트 · 매 · 개월 |
| 유효기간 | 이용권은 필수, 상품권은 선택 |
| 설명 · 노출 순서 · 노출 여부 | 결제 화면에 그대로 반영 |

### 실물 상품

| 항목 | 설명 |
| --- | --- |
| 판매 금액 / SKU | 배송비를 제외한 상품 1개 가격 |
| **재고** | 비우면 무제한. **결제 승인 시점에 차감** |
| 재고 경고 기준 | 이 수량 이하면 화면·관리자 모니터링에 경고 |
| 1회 주문 최대 수량 | 비우면 결제 한도까지 |
| **배송비** | 비우면 사회복지기관 기본 배송정책 |
| **조건부 무료 기준** | 이 금액 이상이면 배송비 무료 |
| **항상 무료배송** | 위 두 값보다 우선 |
| **옵션** | `사이즈: S, M, L` 형식으로 최대 3종 |

등록 화면에서 **1개 주문 시 실제 결제 금액**(상품 + 배송비, 조건부 무료 반영)을 바로 보여주고,
결제 한도를 넘으면 그 자리에서 경고합니다.

### 배송 정책 (사회복지기관 기본값)

기본 배송비 · 조건부 무료 기준 · **도서산간 추가 배송비** · 택배사 · 배송 안내 문구.
상품별 값이 없을 때만 적용되며, 화면에 **상품별 적용 결과**를 표로 함께 보여줍니다.

### 배송비 계산 규칙 (한 곳에서만 판단)

```
1. 상품이 '항상 무료배송'      → 0원
2. 조건부 무료 기준을 넘으면    → 0원   (상품값 → 없으면 사회복지기관 정책)
3. 그 외                       → 상품 배송비 → 없으면 사회복지기관 기본 배송비
4. 도서산간이면 위 결과에 추가 배송비를 더한다 (무료배송이어도 붙음)
```

화면·서버·주문 조회가 **같은 함수(`quoteShipping`)** 를 씁니다.
화면에 보여준 금액과 실제 청구 금액이 다르면 그대로 결제 분쟁이 되기 때문입니다.

## 6. MO 안내문자 고도화 (감사문자와 별개)

| | MO 안내문자 | 감사문자 |
| --- | --- | --- |
| 언제 | 후원자가 문자를 보낸 **직후** | 결제가 **끝난 뒤** |
| 무엇이 붙나 | **상품 선택·결제 링크** | 없음 |
| 치환자 | `{사회복지기관}` `{상품목록}` `{유효시간}` | `{후원자}` `{사회복지기관}` `{금액}` `{메시지}` `{누적}` |
| 길이 | 160자 (링크가 뒤에 붙으므로 짧게) | 200자 |

**사회복지기관이 바꿀 수 없는 것**

- 결제 링크 — 시스템이 본문 끝에 붙입니다. 본문에 링크를 넣으면 저장이 거절됩니다.
- **"아직 결제되지 않았습니다"** 고지 — 오인 결제 민원을 막기 위한 것이라 시스템이 붙입니다.

안내 문자에는 판매 중인 상품 이름이 최대 4개까지 들어가, 링크를 열기 전에 무엇을 살 수 있는지 알 수 있습니다.
설정 화면에 **실제 발송 문장 미리보기**와 기본 문구를 함께 보여줍니다.

## 7. 실물 상품 구매 흐름 (신규)

```
MO 문자 → 안내 문자(결제 링크)
        → [링크 화면] 상품 선택
             ├─ 비실물 : 금액만 고르면 끝
             └─ 실물   : 수량 · 옵션 · 배송지 입력 → 배송비 자동 계산
        → PIN 인증
        → 결제 승인  ← ★ 이 시점에 재고 차감
        → 정산 대기
```

### 재고 차감 — 승인 시점, 상품 단위 잠금

승인 요청을 보내기 **전에**, 상품 단위 advisory lock 안에서 재고를 확인하고 줄입니다.

- 승인 후에 줄이면 마지막 1개를 두 사람이 동시에 사도 둘 다 승인되고 **재고만 음수**가 됩니다.
  돈은 받았는데 보낼 물건이 없는 상태가 되므로, 승인 전에 잠그고 부족하면 결제를 막습니다.
- **선택 단계에서는 줄이지 않습니다.** 결제를 포기한 사람들 때문에 재고가 잠겨 팔지 못하게 됩니다.
- 결제가 실패하면 잡아둔 재고를 되돌립니다.
- 결과 미확인(UNKNOWN)은 되돌리지 않습니다 — 실제로 출금됐을 수 있기 때문입니다.

### 환불과 재고

| 상황 | 재고 | 배송 |
| --- | --- | --- |
| 발송 전(PREPARING) 환불 | **복구** | `CANCELED` 로 변경 |
| 발송 후(SHIPPED·DELIVERED) 환불 | 복구하지 않음 | 메모에 "발송분 회수 필요" 기록 |

물건이 이미 나간 뒤라면 회수와 재고 조정은 사회복지기관이 합니다.

### 배송지 개인정보

- 수령인 이름 · 연락처 · 주소는 **암호화 저장**하고, 목록에는 마스킹(`서울특별시 강남구 ***`)만 씁니다.
- 원문은 **해당 사회복지기관 콘솔과 연동 API** 에서만 복호화합니다.
  최고관리자 모니터링 화면에는 **원문을 표시하지 않습니다**(분쟁 시 결제 상세에서 건별 확인).
- 우편번호로 **도서산간을 자동 판단**해 추가 배송비를 붙입니다(제주 63xxx, 울릉 40200~40240 등).

## 8. 주문 · 배송 관리

- **사회복지기관 → 주문·배송** : 배송 준비 / 발송 완료 / 배송 완료 / 취소 로 걸러 보고,
  택배사·송장번호를 입력해 발송 처리합니다.
  **송장 없이 발송 처리는 막습니다** — 후원자가 조회할 수 없고 분쟁 시 발송 사실을 증명하지 못합니다.
- **최고관리자 → 상품·주문** : 사회복지기관별 상품 목록, 판매 건수, 재고,
  **72시간 넘게 발송되지 않은 지연 주문**, **재고 5개 이하 상품**을 모아 보여줍니다.

## 9. 사회복지기관 연동 API (선택 기능)

사회복지기관은 **기브싸인 관리자에서 모든 처리를 할 수 있습니다.** 이 API 는
자기 사이트에서 포인트를 자동 적립하거나 자기 물류로 출고하려는 사회복지기관만 씁니다.

```
GET  /api/partner/v1/ping                 연결 점검
GET  /api/partner/v1/charges?status=pending   결제 완료 주문 조회 (상품·수량·옵션·배송지 포함)
POST /api/partner/v1/charges/ack          처리 결과 통보 (SENT / FAILED)
POST /api/partner/v1/charges/shipment     송장 등록 (실물)
```

- 인증: `Authorization: Bearer <API 키>` + 쓰기 요청은 **HMAC-SHA256 서명 필수**
- 키는 **해시로만 저장**하고 원문은 발급 시 1회만 노출합니다. 사회복지기관당 최대 3개.
- 서명 재사용(재전송) 차단, 타임스탬프 ±300초, 키당 분당 300회 제한
- 커서 페이지네이션, ack 는 멱등
- `goodsAmount`(= 결제 금액 − 배송비)를 함께 내려줘 **배송비까지 적립하는 실수**를 막습니다.

발급·폐기는 **사회복지기관 → 결제 설정 → 연동 API** 에서 합니다.
규격서: `docs/연동규격서_사회복지기관API.md` (요청/응답 예시, 서명 코드, 오류 코드 포함)

## 10. 약관 개정 (v2.0)

시드 문안을 실제 구조에 맞게 다시 썼습니다. 이전 버전은 자동으로 비활성화됩니다.

- **제3조** — 회사는 결제·정산을 **대행**한다. **포인트는 사회복지기관이 발행·지급**한다.
  따라서 회사는 **선불전자지급수단을 발행·관리하지 않는다.**
- **제6조** — 환불 시 **이미 지급된 포인트의 회수는 사회복지기관 책임**. 사용한 뒤면 환불이 제한될 수 있음.
- **제7조** — 금칙어는 **기록만 가림 처리**하고 결제는 정상 진행.
- **제9조** — 미성년자는 법정대리인 동의 필요, **별도의 낮은 한도**, 동의 없는 결제는 취소 가능.
- 개인정보 동의서에 **사회복지기관 제3자 제공**(번호·금액·일시·거래번호·메시지)을 명시.

> 최종 문안은 법률 검토 후 관리자 화면(약관 관리)에서 새 버전으로 교체하시면 됩니다.

## 11. 원천징수 처리 방식 (자동 지급 전환에 따른 변경)

사회복지기관이 정산을 **요청하는 단계가 사라져서**, 요청 폼에서 받던 주민등록번호를 받을 곳이 없어졌습니다.

- **사업자 사회복지기관**(사업자등록번호 등록) → 원천징수 **없음**. 전액 지급, 수수료는 세금계산서.
- **개인 사회복지기관** → 사업소득 3.3% 원천징수.
  신고용 주민등록번호를 **정산 계좌 탭에서 미리 등록**해 두면, 지급 회차 생성 시 자동으로 쓰입니다.
  (암호화 저장 · 마스킹 표기 · 신고 완료 시 파기하는 기존 흐름 그대로)

### 시뮬레이션으로 직접 확인한 것

**자동 정산**

```
1. 지급일 전 배치 실행        → 지급 0건
2. 전역 지급일 D+5 → D+1 변경  → 지급 예정 1곳 4,992원
3. 배치 실행                  → 지급 1건 4,992원, 회차 auto=true
4. 같은 날 재실행             → 지급 0건, 회차 총 1개 (이중 지급 없음)
5. 모니터링                   → 예정 0 / 오늘 완료 1건 4,992원 / 실패 0 / 보류 0
6. 원장                       → PAYOUT · PAYOUT_WITHHOLDING · PG_FEE 분개 정상
7. 사회복지기관별 개별 지정         → 바람소리 D+5 / 별하늘 D+2 (전역 D+5 위에 덮어씀)
```

**상품 · 실물 주문**

```
배송비 계산 (19,000원 · 배송비 3,000원 · 50,000원 이상 무료)
  1개 22,000원 (31,000원 더 담으면 무료)
  2개 41,000원 (12,000원 더 담으면 무료)
  3개 57,000원 (조건부 무료)
  제주 1개 25,000원 (도서산간 +3,000원)

MO → 안내 문자
  [기브싸인] 바람소리 결제를 진행합니다. (3,000 포인트 · 5,000 포인트 · …)
  아래 링크에서 상품과 금액을 고르고 PIN 을 입력해 주세요. (유효시간 10분)
  아직 결제되지 않았습니다. <링크>

주문  기념 굿즈 티셔츠 × 2 (사이즈: L / 색상: 블랙)
금액  상품 38,000원 + 배송비 3,000원 = 41,000원
배송지 홍*동 / 010-****-5432 / 서울특별시 강남구 ***   (원문은 암호화 저장)
재고  30 → 선택 직후 30(차감 안 함) → 승인 후 28

연동 API 조회 → product·quantity·optionText·shippingFee·goodsAmount·shipping 정상
송장 등록      → 200 SHIPPED (CJ대한통운 123456789012)
송장 없이 발송  → 400 TRACKING_REQUIRED (차단됨)
```

### 검증 중에 찾아서 고친 것

1. **MO 안내 문자 본문 끝에 "결제" 가 덧붙던 오류** — 기본 문구가
   `… (유효시간 10분) 결제 아직 결제되지 않았습니다.` 로 나갔습니다. 템플릿 조립 로직을 고쳤습니다.
2. **지급 재시도 시 결제 건 일부가 미정산으로 남던 문제** — 원천징수를 뺀 실지급액으로 세고 있었습니다.
   회차 금액(수수료 차감 후 정산액)으로 세도록 바꿨습니다. 그대로 뒀으면 마지막 결제 건이
   다음 회차에 다시 잡혀 **이중 지급**이 될 수 있었습니다.
3. **ack 응답의 `unchanged` 가 방금 처리한 건까지 포함하던 문제** — 갱신 후에 상태를 읽고 있었습니다.
   갱신 전 상태를 먼저 읽도록 바꿔, 사회복지기관이 "왜 처리가 안 됐는지" 를 정확히 알 수 있게 했습니다.
4. **테스트·시드가 문자 본문 문구에 묶여 있던 문제** — 사회복지기관이 안내 문구를 바꿀 수 있게 되면서
   본문 매칭이 깨졌습니다. mock 발송함에 템플릿 코드를 함께 남기고 코드로 찾도록 바꿨습니다.
5. **정산 원장 append-only 트리거** — 테스트가 원장 시각을 수정하려다 차단됐습니다.
   방어가 의도대로 동작한 것이라, 테스트 쪽을 고쳤습니다.
