## A-2. 보안·금전 (P1)

- **운영 안전장치**: `APP_ENV` 미설정 시 테스트 로그인 노출 → 화이트리스트(`local`만 허용) + `NODE_ENV=production` 강제 차단, 부팅 시 `assertProductionSafety()` 호출로 위반 시 기동 중단
- **시크릿 fail-open**: `SESSION_SECRET` / `PHONE_HASH_SECRET` 기본값 제거 → 미설정 시 모듈 로드 단계에서 즉시 예외
- **MO 웹훅 fail-open**: 시크릿 없으면 통과하던 것을 **fail-closed**로 전환 (C장 연동과 함께 진행)
- **사회복지기관 상태 미검사**: `requireCreator()`가 `status==='APPROVED'` 확인, 정지 시 세션 무효화, role 승격을 승인 시점으로 이동
- **웹 후원 이중 출금**: 멱등키를 "금액·메시지 확정 시점"에 1회 생성해 고정, 성공 후에만 회전
- **웹 후원 표시명 `***`**: 이중 마스킹 제거(`donor.displayName || '익명의 후원자'`)
- **로그인 CSRF**: 로그인/로그아웃 라우트에 Origin 검증 추가
- **인증번호 난수**: `Math.random()` → `crypto.randomInt()` (3개 파일)
- **후원자 차단 무효**: `checkLimits`에 후원자→사회복지기관 차단 반영
- **정책 시행일 무시**: 한도·수수료·약관 resolver에 `effectiveFrom<=now`, `effectiveTo` 조건 추가
- **환불 수수료 환입 오차**: 원 거래 확정 분개를 환입하도록 변경
- **정산 지급 검증**: `markSettlementPaid`에서 `APPROVED` 재확인 + 잔액·계좌 인증 재검증
- **정산 요청 페이지네이션**: 요청/원장 목록 분리 페이징, 오래된 순 정렬
- **캘린더 집계 상수 불일치**: 로컬 `PAID_STATUSES` 제거 → 공용 상수 사용
- **/api/health 정보 노출**: 공개 응답을 `{ok}`로 축소

# B. 문의 로직 점검 결과 (신규 감사)

요청하신 문의 로직을 별도로 정밀 점검했습니다. **총 21건** 발견(높음 5 · 중간 9 · 낮음 7). 2차 감사에서 이미 지적된 3건(무인증 액션, /support userId 노출, /support rate limit 없음)과 별개로 **신규 18건**입니다.

## B-1. 높음

1. **`markInquiryRead`가 무인증 공개 액션** — `'use server'` 파일에서 `run()`/`requireAdmin()` 없이 export. 임의 `inquiryId`로 읽음 처리 가능 → 미답변 큐가 0으로 보여 문의를 놓침. (2차 감사와 중복 = 확정)
2. **발송 제한을 클라이언트가 무력화** — rate limit 키가 `guestToken`(클라이언트 제출 쿠키)이라 매 요청 랜덤 토큰을 보내면 제한이 전혀 걸리지 않고, 매번 새 스레드가 생성됨. 스크립트로 분당 수천 건 스팸 가능.
3. **비회원 문의 → 로그인 시 스레드 승계 없음** — 게스트로 문의하고 답변을 받은 뒤 로그인하면 위젯이 빈 화면. 답변을 영원히 못 보고, 관리자 화면엔 같은 사람 문의가 2건으로 분리됨.
4. **/support 신고 내용과 내부 userId가 사회복지기관에게 그대로 노출** — `content`에 `[회원 문의 / userId=...]`를 박아 저장 → `/studio/reports`에 원문 노출. 같은 화면 안내문("신고자 정보는 표시되지 않습니다")과 정면 모순. 보복 위험.
5. **/support 접수에 인증·제한·캡차 전무** — 비로그인 무제한 접수 가능. 신고 테이블 폭증 시 실제 신고가 묻힘.

## B-2. 중간

6. **게스트 연락처를 암호화 저장하지만 복호화 경로가 없음** — 관리자는 마스킹만 보므로 회신 불가. 개인정보만 무기한 보관되는 최악 조합.
7. **메시지 조회가 `asc + take 200`** — 스레드가 길어지면 **최신 메시지가 잘려** 방금 보낸 글과 최신 답변이 안 보임.
8. **전송 실패 시 작성 본문 유실** — 실패해도 폼이 리셋되어 장문을 다시 작성해야 함.
9. **답변 도착 알림 수단 전무** — 위젯을 열어야만 확인. 미읽음 배지·이메일·푸시 전부 없음. 비회원은 6번과 겹쳐 사실상 답변 유실.
10. **게스트 이름·연락처 입력칸이 첫 폴링 응답에 사라짐** — 입력 중 값 소실, 이후 연락처 추가 불가.
11. **문의 시스템이 2개로 분리** — 위젯(SupportInquiry)과 /support 폼(Report)이 모델·상태·식별자 모두 달라 조인 불가. 중복·모순 응대 발생, 사용자별 이력 조회 불가.
12. **접수번호를 발급하지만 조회·답변 채널이 없음** — Report에 답변 본문 필드 자체가 없고 조회 페이지도 없음. 비회원 접수는 무응답 종결.
13. **관리자 문의 화면에 검색·담당자·SLA·템플릿 없음** — 필터가 상태 하나. `category` 컬럼은 있으나 미사용(죽은 컬럼). 300건 쌓이면 특정인 문의를 못 찾음.
14. **게스트 쿠키 `secure` 플래그가 `APP_BASE_URL` 문자열 의존** — 세션 쿠키와 기준이 달라, 변수 누락 시 조용히 평문 전송. 이 쿠키는 스레드 접근 권한 그 자체.

## B-3. 낮음

15. 동일 사용자 중복 스레드 생성 가능(유니크 제약·트랜잭션 없음) — 빠른 이중 클릭 시 답변이 유령 스레드로 감
16. GET `/api/inquiry`가 읽음 처리(쓰기) 수행 → 이미지 태그 CSRF로 읽음 상태 조작
17. 거래번호 유효성 오라클(존재/부재가 응답으로 구분됨) + 제한 없음
18. 예외를 전부 삼켜 로그 0건 — Redis 장애 시 100% 실패해도 흔적 없음
19. 탈퇴해도 문의 본문·연락처 잔존(파기 정책 없음)
20. status 전이 미강제 — 답변 없이 "답변 완료"로 만들 수 있어 통계·안내가 거짓
21. 모든 공개 페이지 렌더마다 FAQ 쿼리 + 15초 폴링(쓰기 포함) 상시 부하

## B-4. 문의 기능에 빠진 것

파일 첨부, 답변 알림(이메일/푸시), 문의 유형 선택, 관리자 검색·담당자 배정, 답변 템플릿, 운영시간·예상 답변시간 안내.

## B-5. 문의 기능에서 잘 되어 있는 것

XSS 안전(전 구간 JSX 텍스트 보간), 타인 스레드 직접 열람 경로 없음(파라미터를 받지 않음), 게스트 토큰 엔트로피 충분(ULID·CSPRNG), 관리자 답변 액션의 권한·감사로그 정상, 답변 대기 우선 정렬·페이지네이션 정상.

## B-6. 권장 개편 방향

문의 채널을 **`SupportInquiry` 하나로 일원화**하고, `/support` 폼은 같은 모델에 첫 메시지로 저장(카테고리·거래번호를 컬럼으로 이관). `Report`는 순수 "신고"로 축소. 이 개편이 11·12번을 동시에 해소하고, 이후 검색·담당자·알림을 한 곳에만 붙이면 됩니다.

# C. MTONET 050 · MO 연동 준비

## C-1. 확인 상태

MTONET 사이트(`mtonet.co.kr/pages/mo`, `/pages/050service`)는 **자동 조회가 차단**(robots.txt 응답 타임아웃)되어 공식 규격을 직접 읽지 못했습니다. 우회 수집은 하지 않았습니다. 따라서 **연동규격서(PDF/문서) 제공이 필요**합니다.

다만 국내 050 MO 서비스는 대부분 **"URL 방식"(수신 즉시 고객사 URL로 HTTP 푸시)** 이며, 현재 기브싸인 MO 구조가 정확히 그 방식입니다. 즉 **아키텍처 변경 없이 어댑터 1개 추가로 연동 가능한 상태**입니다.

## C-2. 이미 준비된 것

- `MoAdapter` 인터페이스(`verify` + `parse`)와 정규화 타입 `MoInbound` 존재
- 웹훅 수신 라우트 + 서명 검증 + IP 허용목록 + 원문 서명 검사 골격 존재
- **050 번호 체계 이미 적용 완료** — 관리자 등록 검증 `^050[0-9]{7,10}$`, 시드 `05051001001`/`05059000000`, 화면 안내 문구까지 전환됨
- 사회복지기관별 고유번호(DEDICATED) / 대표번호+키워드(SHARED_PREFIX) 두 모드 모두 지원
- 중복 수신 3중 방어(providerMessageId 유니크 + moMessageId 유니크 + 멱등키)

## C-3. 연동 시 해야 할 작업

| # | 작업 | 내용 |
|---|------|------|
| 1 | `MtonetMoAdapter` 구현 | `src/server/adapters/mo/mtonet.ts` — MTONET 페이로드 → `MoInbound` 매핑, 서명/인증 검증, 응답 규격(성공 응답 본문) 준수 |
| 2 | 필드 매핑 확정 | 발신번호·수신050번호·본문·수신일시·메시지ID·타입(SMS/LMS/MMS)·첨부 필드명 |
| 3 | 수신 응답 규격 | MTONET이 요구하는 ACK 형식(예: `OK`/JSON) 반환 — 미준수 시 재전송 폭주 |
| 4 | 인증 방식 | 서명 헤더 / IP 허용목록 / Basic 인증 중 무엇인지 확정 → **fail-closed로 구현** |
| 5 | MT 회신 경로 | 050 번호로 회신(MT) 가능한지, 별도 발신번호가 필요한지 확정 (`MT_FROM_NUMBER` 정책) |
| 6 | 번호 발급 관리 | 사회복지기관 승인 시 050 번호 자동 배정 여부(수동 등록 유지 vs API 연동) |
| 7 | 운영 점검 | `assertProductionSafety()`에 MO 웹훅 시크릿·허용 IP 필수 검사 추가 |

## C-4. 규격서에서 확인이 필요한 항목 (요청 사항)

① 수신 푸시 방식(GET 쿼리 / POST form / POST JSON) ② 파라미터 필드명 전체 ③ 성공 ACK 응답 형식 ④ 재전송 정책(실패 시 몇 회·간격) ⑤ 인증·서명 방식과 발신 IP 대역 ⑥ MMS 첨부 전달 방식(URL/바이너리) ⑦ 050 번호당 월 수신 한도·요금 ⑧ MT 회신 API 규격(같은 사업자 사용 시)

# D. 헥토파이낸셜 내통장결제 연동 준비

## D-1. 확인된 실제 규격 (공식 개발자센터 기준)

**결제인증(결제창)**
- URL: 테스트 `https://tbezauth.settlebank.co.kr` / 운영 `https://ezauth.settlebank.co.kr`
- 호출: POST form + `SettlePay.js` SDK (`SettlePay.execute(form)`)
- 필수 파라미터: `hdInfo`(IA_AUTHPAGE_1.0_1.0), `apiVer`(2.0), `processType`(D), `mercntId`(8), `ordNo`(100, 거래일 내 유일), `custCi`(**AES-256 암호화**), `trDay`, `trTime`, `trPrice`(**AES-256 암호화**), `productNm`, `dutyFreeYn`, `callbackUrl`, `signature`
- signature = `SHA256(mercntId + ordNo + trDay + trTime + trPrice평문 + callbackUrlHost + hashKey)` — **callbackUrl은 프로토콜·포트 제외 도메인만**
- 콜백 응답: `resultCd`(0/-1), `errCd`, `resultMsg`, `mercntId`, `ordNo`, **`authNo`**, `trPrice`, `discntPrice`, `payPrice`, `trDay`, `trTime`, `mercntParam1/2`
- 옵션 `regularpayYn` → 자동결제(빌키) 발급용, **결제금액 0원이면 키발급만 진행**

**결제승인 API**
- URL: 테스트 `https://tbezauthapi.settlebank.co.kr/v3/APIPayApprov.do` / 운영 `https://ezauthapi.settlebank.co.kr:8081/v3/APIPayApprov.do`
- POST, `application/json; charset=UTF-8`
- 필수: `hdInfo`(IA_APPROV), `apiVer`(3.0), `mercntId`, `authNo`, `reqDay`, `reqTime`, `signature`
- signature = `SHA256(mercntId + authNo + reqDay + reqTime + hashKey)`
- 응답: `resultCd`, `errCd`, `resultMsg`, `trNo`(거래번호), `trPrice`/`payPrice`, `trDay`/`trTime`, `bankCd`/`bankAcctNo`(마스킹)
- **인증 유효기간 10분** — 초과 시 재인증

**자동결제(빌키)**
- URL: 테스트 `https://tbezauthapi.settlebank.co.kr/APIRegularpayKey.do` / 운영 `https://ezauthapi.settlebank.co.kr:8081/APIRegularpayKey.do`
- signature = `SHA256(mercntId + authNo + reqDay + reqTime + hashKey)`
- 응답: **빌키(최대 32자)**, 마스킹 계좌번호, 은행코드, 거래정보
- 별도 문서: 취소/환불 API, 에러코드

## D-2. 기브싸인 모델과의 적합성 — 결론: **구조가 맞습니다**

문자후원은 "문자 1통 = 즉시 출금"이라 매번 결제창을 띄울 수 없으므로 **자동결제(빌키)** 가 필수인데, 현재 결제 어댑터가 이미 **빌키 중심**으로 설계돼 있고 주석에도 "헥토파이낸셜 내통장결제 EzAuth 기준"이라고 명시돼 있습니다.

매핑:

| 기브싸인 | 헥토 EzAuth |
|---|---|
| `createRegistrationSession()` | 결제창 호출(0원 + `regularpayYn=Y`) |
| `completeRegistration()` | 콜백 `authNo` 수신 → `APIRegularpayKey.do` 로 **빌키 발급** |
| `approve()` | 빌키 기반 자동결제 승인 API |
| `inquire()` | 거래결과조회 API |
| `cancel()` | 취소/환불 API |
| `revokeBillKey()` | 빌키 해지 API |

## D-3. 지금 바로 정정이 필요한 것 (연동 전 준비)

1. **API 베이스 URL이 잘못됨** — `.env`의 `HECTO_API_BASE="https://tbgw.settlebank.co.kr"` 는 일반 PG 게이트웨이입니다. EzAuth는 **결제창 호스트와 API 호스트가 다르고 운영은 포트 8081**입니다. → `HECTO_EZAUTH_UI_BASE` / `HECTO_EZAUTH_API_BASE` 로 분리 필요.
2. **`custCi`(고객 CI) 필요** — 현재 기브싸인는 CI를 수집하지 않습니다. 결제창 자체 휴대폰 본인인증으로 대체 가능한지, 아니면 별도 본인확인 연동이 필요한지 **계약 시 확인 필요**(연동 방식이 갈리는 항목).
3. **AES-256 암호화 유틸** — `trPrice`, `custCi` 암호화 필요. `HECTO_AES_KEY` 키는 이미 존재하나 헥토 규격(IV/패딩/인코딩) 확인 후 구현.
4. **signature 유틸** — 두 가지 조합 규칙(결제창용/API용)을 각각 구현. callbackUrl **호스트만** 추출하는 처리 주의.
5. **`ordNo` 유일성** — "거래일 내 유일" 규칙에 맞게 `newOrderNo()` 점검.
6. **10분 제약** — 기브싸인 확인링크 TTL이 300초라 이미 안전 범위. (설계에 반영돼 있음 ✓)
7. **응답코드 매핑** — `resultCd`/`errCd` → 내부 실패 사유·재시도 정책 매핑 테이블 필요.

## D-4. 연동 전까지의 운영 원칙 (유지)

계약·키 발급 전까지는 **mock 어댑터 유지**하고 화면에 "모의(mock) 결제" 안내를 계속 노출합니다(가짜 성공 처리 금지 원칙). `SAFE_MODE`가 켜져 있으면 실결제를 자동으로 mock으로 강제하는 안전장치도 이미 동작합니다.
