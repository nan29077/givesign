# 후원자 닉네임 기능 검토서

- 작성일: 2026-08-27
- 상태: **검토 완료 · 개발 지시 대기**
- 결론: 기능의 뒷단은 이미 존재. **입력 화면만 만들면 되고, DB 마이그레이션 불필요.**

---

## 1. 배경 — 왜 필요한가

문자후원은 **휴대폰 번호만 수집**된다. 그래서 사회복지기관 화면·방송 오버레이·유튜브
라이브 채팅에 후원자가 `010-****-5678` 같은 번호로만 표시된다.

그런데 실제 후원은 **유튜브·인스타그램·틱톡 방송을 보다가** 일어난다.
사회복지기관 입장에서는 "평소 채팅에서 보던 그 시청자"인데 번호로만 뜨니 누구인지 알 수 없다.

→ **후원자의 방송 닉네임을 받아 번호와 매칭해 두고, 모든 화면에 닉네임으로 표시한다.**

---

## 2. 확정된 요구사항

| # | 내용 | 비고 |
|---|---|---|
| 1 | 도용 우려는 **배제** | 본인 확인 없이 자기 주장 그대로 수용 |
| 2 | 닉네임은 **여러 번 바꿀 수 있음** | 수시 변경 전제로 설계 |
| 3 | **마이페이지에서 수정 가능** | "닉네임이 후원자 이름으로 표시됩니다" 안내 포함 |
| 4 | **최초 등록 링크에 닉네임 입력칸(선택)** | 카드 빌링키 등록 화면이 **화이트라벨 → 제어 가능** |
| 5 | 헥토 계좌 등록은 나중에 | 제어 불가로 판명되면 그때 다른 방법 모색 |
| 6 | **후원 페이지 진입 시 안내** | 로그인 상태면 "번호 대신 닉네임으로 송출" 안내 + 수정 유도 |
| 7 | **기본값 = 전화번호 끝 4자리** | 닉네임 설정 전까지 |

### 적용 순서

**카드 빌링키 등록이 먼저**다. 이 링크는 **화이트라벨로 제공받아 우리가 제어 가능**하므로
닉네임 입력칸을 넣는 데 제약이 없다. 헥토 계좌 등록은 이후 단계에서 검토한다.

## 3. 현재 코드 상태 — 배관은 이미 깔려 있다

### 3-1. DB 컬럼이 이미 존재

`prisma/schema.prisma:398`

```prisma
model DonorProfile {
  ...
  displayName  String?  @map("display_name")   // ← 이미 있음. 지금은 아무도 채우지 않음
```

**마이그레이션이 필요 없다.**

### 3-2. 표시 로직이 이미 연결되어 있다

`src/server/services/donation-flow.ts:519`

```ts
const displayName = donor.displayName || maskPhone(inbound.fromNumber);
```

닉네임이 있으면 닉네임, 없으면 마스킹된 번호. 이 한 줄이 정한 값이 아래 전 구간으로 흐른다.

| 흐르는 곳 | 실제 출력 예시 |
|---|---|
| 방송 오버레이 배너 | `밤톨이님이 3,000원을 후원했습니다` |
| TTS 음성 안내 | `밤톨이님 3,000원 후원. 오늘 방송 재미있어요` |
| 유튜브 라이브 채팅 | `[기브싸인 후원 3,000원] 밤톨이: 오늘 방송 재미있어요` |
| 후원자 감사 문자 | `[기브싸인] 밤톨이님, 바람소리 사회복지기관에게...` |
| 사회복지기관·관리자 화면 | 후원 내역 목록의 후원자명 |

> **즉 "입력받는 입구"만 만들면 표시 쪽은 한 줄도 고칠 필요가 없다.**

### 3-3. 카드/계좌 구분도 이미 있다

`src/server/services/donor-registration.ts:112`

```ts
const method: PaymentMethodKind = input.method ?? 'ACCOUNT';   // 'CARD' | 'ACCOUNT'
```

카드 빌링키 우선 적용에 구조적 장애물이 없다.

### 3-4. 등록 화면은 우리 소유다

문자 링크를 누르면 이렇게 흐른다.

```
문자 링크 클릭
  → ① /r/{token}              ← 기브싸인 자체 페이지 (약관 동의·수수료 안내)  ★ 여기에 닉네임 칸
  → ② 결제사 화면              ← 카드사/헥토 (화이트라벨이면 제어 가능)
  → ③ /r/{token}/complete     ← 다시 기브싸인 페이지 (완료 안내)
```

**①번은 이미 100% 우리 통제 하에 있다.** 후원자는 어차피 여기서 약관에 동의하므로,
그 폼에 입력칸 하나를 추가하는 것뿐이다. 결제사 규격과 무관하고 협의도 필요 없다.

## 4. 결정이 필요한 사항 3가지

### (1) 기본 닉네임 형식

현재 `maskPhone()`은 **`010-****-5678`** 를 돌려준다 (`src/lib/crypto.ts:98`).
요청하신 "끝 4자리"와 다르므로 새 규칙이 필요하다.

| 후보 | 방송 출력 예시 | 평가 |
|---|---|---|
| `5678` | `5678님이 3,000원을 후원했습니다` | 숫자만 덩그러니 떠서 이름으로 안 읽힘 |
| **`후원자5678`** | `후원자5678님이 3,000원을 후원했습니다` | **권장.** 이름처럼 읽히고 끝 4자리만 노출 |
| `익명5678` | `익명5678님이 3,000원을 후원했습니다` | 가능. 다만 "익명"은 별도 익명 기능과 혼동 우려 |

**권장: `후원자5678`**

부수 효과로 **개인정보 노출이 줄어든다.** 지금은 앞자리 `010-`까지 방송에 나가는데,
끝 4자리만 남기면 노출 범위가 좁아진다.

### (2) 닉네임을 바꾸면 과거 후원 내역은?

`Donation.displayName` 은 후원 시점의 이름을 **박제(스냅샷)** 한다 (`schema.prisma:478`).

닉네임을 `밤톨이` → `겨울밤` 으로 바꾸면:

| 방식 | 과거 후원 내역 | 장점 | 단점 |
|---|---|---|---|
| **A. 스냅샷 유지** (현재 구조) | `밤톨이` 그대로 | 그때 방송에 나간 이름과 기록이 일치. 정산·분쟁 시 정확 | 사회복지기관가 "이 사람 누구지?" 헷갈릴 수 있음 |
| B. 항상 최신 닉네임 | 전부 `겨울밤` | 목록이 일관됨 | 실제 송출된 이름과 기록이 어긋남 |

**권장: A (현재 구조 유지)**

방송에 이미 나간 이름을 나중에 바꾸는 것은 기록 왜곡이다. 사회복지기관 화면에서
`밤톨이 (현재: 겨울밤)` 처럼 괄호로 함께 보여주면 헷갈림도 해결된다.

### (3) 닉네임 길이 제한

**권장: 2~20자.** 금칙어 필터는 기존 `content-filter` 를 그대로 재사용한다
(방송·유튜브 채팅에 그대로 노출되므로 필수).

## 6. 추가 권장 사항 2가지

### ① 등록 폼에 "미입력 시 결과" 미리보기

선택 항목이라 그냥 넘기기 쉽다. 결과를 미리 보여주면 입력률이 크게 올라간다.

```
방송에서 쓰는 닉네임 (선택)
[                    ]
비워두면 후원자5678 로 표시됩니다
```

### ② 마이페이지 안내는 "방송에 이렇게 뜹니다" 형태로

```
현재 닉네임: 밤톨이                            [수정]

방송·유튜브 채팅에 이렇게 표시됩니다
  → 밤톨이님이 3,000원을 후원했습니다

설정하지 않으면 휴대폰 번호 끝 4자리로 표시됩니다.
```

## 7. 채택하지 않은 대안 — 문자로 닉네임 요청

> "가입 안내 문자에 '닉네임을 함께 보내 달라'고 안내하는 방법"

**비권장.** 이유는 세 가지다.

1. **자유 텍스트에서 닉네임만 골라내는 것이 불안정하다.** "닉네임: 밤톨이" 형식을 지켜
   보내는 사람은 드물고, 응원 메시지와 섞이면 경계를 기계가 구분할 수 없다.
2. **대표번호+키워드 방식과 충돌한다.** 이미 문자 맨 앞을 키워드가 차지하고 있다.
3. **잘못 파싱된 단어가 닉네임으로 박제되면** 되돌리기가 더 번거롭다.

다만 **안내 문구로는 활용 가치가 있다.** 등록 안내 문자에
"등록 화면에서 방송 닉네임도 설정할 수 있어요" 정도를 넣으면 입력률이 올라간다. (작업 6번)
