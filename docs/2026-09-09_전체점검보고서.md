- 권장: `{ ...(body.data ?? {}), sandbox: true }` 로 순서 바꾸고, `eventId` 나 헤더에도 샌드박스 표식.

## 2. 중간 (17건)

### 파트너 API

**M-1. 멱등키 동시 요청이 500**
`src/server/services/merchant-mt.ts:316-322` — `findFirst` 로 확인 후 `create`. 같은 키 두 요청이 동시에 오면 둘 다 통과해 두 번째가 unique 위반(P2002)으로 500. 재시도 클라이언트가 가장 흔히 만드는 상황이다. → P2002 잡아서 기존 행을 돌려주면 된다.

**M-2. 웹훅 재전송 선점(claim)이 없어 중복 발송**
`webhooks.ts:230-245` `drainWebhookQueue` — `PENDING` 을 `findMany` 한 뒤 `deliverOnce` 만 부른다. 크론이 겹치거나 `deliveries/{id}/retry` 와 겹치면 같은 건이 두 번 나간다. → `updateMany(status: PENDING → SENDING)` 으로 선점 후 전송.

**M-3. 문서의 `live:false` 표시와 실제 발행이 다르다**
`webhooks.ts:36-37` 은 `payer.linked`·`product.stock_low` 를 `live:false` (준비 중) 로 표시하지만 `payers/link/route.ts:64`, `products/[id]/stock/route.ts:67` 은 실제로 발행한다. 사회복지기관은 "아직 안 온다"고 믿고 구독하지 않거나, 구독했는데 왜 오는지 모른다. → `live:true` 로 고치면 끝.

**M-4. 일일 발송 한도가 서버 시간대 기준**
`merchant-mt.ts:281-288` `start.setHours(0,0,0,0)` — 서버 TZ 가 UTC 면 한국 시간 오전 9시에 하루가 바뀐다. 문서는 KST 라고 안내. → `kstDateKey` 기준으로.

**M-5. 상품 bulk 동기화가 트랜잭션이 아니다**
`products/bulk/route.ts` — 100건 중 50번째에서 실패하면 앞 49건만 반영된다. `(merchantId, sku)` unique 도 없어 같은 sku 가 동시에 두 번 만들어질 수 있다. → `$transaction` + unique 인덱스.

**M-6. 플랫폼 차단 후원자 검사 누락**
`merchant-mt.ts:365-375` 는 사회복지기관별 차단(`payerBlockedAt`, `blockedPayer`)만 본다. `PayerProfile.blockedAt` (플랫폼 전체 차단)은 안 본다. → 조건 하나 추가.

### 관리자 콘솔

**M-7. 관리자 수동 "지급 완료" 가 결제 건을 `SETTLED` 로 안 바꾼다**
`src/app/actions/admin/settlement.ts:64-67` (단건), `:186` (일괄) — `markSettlementPaid` 만 부른다. 자동 지급(`auto-settlement.ts:242`) 과 재시도(`:406`) 는 결제 건을 `SETTLED` 로 바꾸는데 수동 경로만 빠져 있다. 결과: 수동 지급한 회차의 결제 건은 `settlementRequestId` 가 걸린 채 영원히 `SETTLEMENT_PENDING` 으로 남는다(다음 회차에도 안 잡히고, 사회복지기관 화면엔 "정산 대기"로 보임).

**M-8. `PAYOUT_FAILED` 회차는 영원히 반려할 수 없다**
`settlement.ts:54-56` — `payoutIssuedAt` 이 있으면 REJECTED/REVIEWING 을 막는다. 그런데 `markSettlementPayoutFailed` 는 `payoutIssuedAt` 을 지우지 않으므로 "실패 → 반려" 경로가 없다. 실패 회차를 버리고 다시 요청받으려면 DB 를 직접 만져야 한다. (일괄 처리 `:161-164` 도 동일)

**M-9. `PAYOUT_FAILED` 이후 반려해도 결제 건이 풀리지 않는다**
M-8 이 풀린다 해도 `:84-90` 의 REJECTED 처리는 `settledAt: null` 인 건만 `settlementRequestId` 를 지운다. 자동 지급 경로에서 이미 `SETTLED` 로 바뀐 건은 되돌아오지 않는다.

**M-10. 환불 승인 재진입 경쟁**
`transactions.ts` 환불 승인 — 상태 확인과 원장 분개가 한 트랜잭션에서 `updateMany where status` 로 잠기지 않아, 관리자 둘이 동시에 승인하면 반대분개가 두 번 남을 수 있다. (원장은 append-only 라 지울 수도 없다.)

**M-11. 관리자 목록 `?role=toString` 이 500**
`src/app/admin/users/page.tsx:43-44` — `sp.role in roleLabel` 은 프로토타입 체인까지 본다. `?role=constructor`, `?status=toString` 이면 Prisma 에 잘못된 enum 이 넘어가 500. → `Object.hasOwn`.

### 결제·정산

**M-12. 환불 시 한도 롤백이 다른 달에 빠진다**
`src/server/services/refund.ts:168-174` — 같은 트랜잭션 안에서 이미 `paymentTransaction.status` 를 `CANCELED` 로 바꾼 **뒤에** `status: 'APPROVED'` 로 찾으므로 `approvedTxn` 은 항상 null. 결국 주석이 "쓰면 안 된다"고 한 `charge.paidAt` 으로 롤백한다. 월말·월초 경계에서 결제한 건을 환불하면 엉뚱한 달 카운터에서 뺀다.

**M-13. 승인 트랜잭션 커밋 후 예외가 나면 한도·재고가 묶인다**
`charge-flow.ts:1126-1173` — 한도 예약·재고 차감 트랜잭션이 끝난 뒤 `setStatus`·`paymentAttempt.count` 가 실패하면 결제사 승인은 안 갔는데 `PENDING` 거래가 남는다. 대사(`payment-reconcile.ts:38`) 는 `UNKNOWN`/`TIMEOUT` 만 다뤄 이 건은 영원히 못 푼다.

**M-14. PIN 세션을 선점한 뒤 예외가 나면 결제가 멈춘다**
`pin-authorization.ts:156-177` — 세션을 `COMPLETED` 로 바꾼 뒤 `executePayment` 가 **던지면**(반환값 `!ok` 가 아니라 예외) 세션은 완료, 결제는 `PENDING_PIN`. 후원자는 다시 인증할 수도, 관리자가 대사할 수도 없다. → try/catch 로 세션을 `PENDING` 으로 되돌리거나 `FAILED` 표시.

### 공개·인증

**M-15. Redis 재연결을 5번만 시도하고 포기한다**
`src/server/redis.ts:184` `retryStrategy: (times) => (times > 5 ? null : ...)` — 약 4.5초 이상 끊기면 ioredis 가 영구 포기. 이후 프로세스가 재시작될 때까지 한도 카운터·속도 제한·OTP 가 모두 실패(또는 인메모리 폴백으로 조용히 전환). ElastiCache 페일오버(보통 30초~1분)만으로 발생한다.

**M-16. OTP 시도 횟수 경쟁 + TTL 연장**
`web-charge.ts:164-170`, `charge-lookup.ts:144-150`, `phone-link.ts:157-163` — 읽고(`at`) 빼고 다시 쓰는 방식이라 동시 요청이면 5회 제한을 넘길 수 있고, 틀릴 때마다 `kv.set(..., TTL)` 로 **만료 시각이 새로 시작**된다. 6자리 코드를 무기한 시도할 수는 없지만(5회 제한 자체는 대부분 동작) 방어가 느슨하다. → `DECR` 원자 연산, TTL 은 `KEEPTTL`.

**M-17. 웹 결제 PIN 요청이 "가입된 번호" 오라클 + 임의 결제 생성**
`web-charge-pin.ts:106-138` — 누구나 아무 번호를 넣으면 응답이 "가입 안내" / "PIN 문자 발송" 으로 갈리고, 가입된 번호면 **그 사람 앞으로 결제(PENDING_PIN) 가 만들어지고 PIN 문자가 간다.** 번호당 10분 5회 제한이 있어 대량 살포는 막히지만, 특정인 괴롭히기·가입 여부 확인은 가능하다. 결제 페이지 특성상 완전히 막기는 어려우니 최소한 응답 문구를 통일하고 미결제 PIN 건 자동 정리를 확인해야 한다.
