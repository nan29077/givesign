## 4단계 — 외부 연동 준비 (완료)

계약 진행 중이므로 **서명·암호화·파싱 로직은 완성하고 단위 테스트로 검증**했으며, 규격서와 대조가 필요한 값은 한 곳에 모아 두었습니다.

### 4-1. 헥토파이낸셜 내통장결제 (`src/server/adapters/payment/hecto.ts`)

**가장 중요한 수정**: 기존 `HECTO_API_BASE="https://tbgw.settlebank.co.kr"` 는 **일반 PG 게이트웨이 주소**로, 내통장결제(EzAuth) 주소가 아니었습니다. 그대로 두면 연동 첫날 전건 실패합니다. 두 호스트로 분리했습니다.

- 결제창(UI): `HECTO_AUTH_UI_BASE` = `https://ezauth.settlebank.co.kr`
- 서버 API: `HECTO_AUTH_API_BASE` = `https://ezauthapi.settlebank.co.kr:8081`

구현·검증한 내용:

- 서버 API 서명 `SHA256(mercntId+authNo+reqDay+reqTime+hashKey)` — 재료 순서 회귀 테스트 포함
- 결제창 해시 `SHA256(mercntId+ordNo+trDay+trTime+**평문금액**+callbackUrl호스트+hashKey)` — 암호문을 넣으면 검증 실패하므로 평문 사용을 테스트로 고정
- AES-256 암복호화 왕복 + 키 길이(32byte) 미달 시 즉시 실패
- KST 기준 `yyyyMMdd`/`HHmmss` (자정 경계 포함 검증)
- 결제인증 10분 제한을 세션 만료에 반영
- 승인/조회/취소/빌키 발급·해지 전 구간
- **fail-closed**: 키가 하나라도 없으면 mock 으로 조용히 대체하지 않고 `AdapterNotConfiguredError`

### 4-2. MTONET 050 MO (`src/server/adapters/mo/mtonet.ts`)

국내 050 MO 표준인 "URL 방식"(수신 즉시 HTTP 푸시)을 전제로 구현했습니다. 현재 기브싸인 MO 구조가 정확히 그 방식이라 아키텍처 변경은 없었습니다.

- 필드명 후보를 `FIELD_ALIASES` 한 표에 모음 → 규격서 수령 시 그 표만 수정
- `data`/`result` 래핑 payload 대응
- 하이픈·공백 제거, KST 시각 3종 표기 해석
- **필수값 누락 시 기본값으로 때우지 않고 실패** (관대하게 처리하면 엉뚱한 사회복지기관에게 후원이 꽂힘)
- **050 이 아닌 수신번호는 거절** (라우팅 사고 차단)
- SMS/LMS/MMS 판정(표기 없으면 90바이트 기준 추정), LMS 제목 병합
- 공용 fail-closed 검증 통과 필수

### 4-3. 계약 후 필요한 자료

1. **헥토**: 상점 연동규격서(엔드포인트 경로·필드명·응답코드표), 테스트베드 MID/HASH/AES 키, 콜백 URL 등록
2. **MTONET**: MO 연동규격서(푸시 payload 필드명·인증 방식·성공 응답 형식), 발신 IP 대역(→ `MO_ALLOWED_IPS`), 계정 정보
3. 확보 후 `HECTO_SPEC` / `FIELD_ALIASES` 두 블록만 대조·수정하면 실연동 전환됩니다.

## 참고: 이번에 확인된 사항

`preview.bat` 처럼 로컬에서 프로덕션 빌드를 띄우는 방식은 그대로 동작합니다. 처음에 `NODE_ENV=production` 만으로 운영 환경으로 단정하도록 만들었더니 로컬 미리보기가 기동을 거부해서, **명시적으로 지정한 `APP_ENV` 를 우선 존중**하고 미설정·오타일 때만 안전한 쪽으로 판정하도록 조정했습니다. `.env` 에 `APP_ENV="local"` 이 있으므로 PC 미리보기는 지금과 동일하게 동작합니다.

배포 시에는 `APP_ENV=prod` 와 함께 아래가 모두 갖춰져야 서버가 뜹니다(하나라도 빠지면 기동 중단).

```
CRYPTO_PROVIDER=aws-kms
SESSION_SECRET / PHONE_HASH_SECRET   (기본값 금지)
ALLOW_INMEMORY_FALLBACK=false
MO_ALLOWED_IPS / MO_WEBHOOK_SECRET
PAYMENT_PROVIDER=hecto + HECTO_MID / HECTO_HASH_KEY / HECTO_AES_KEY
APP_BASE_URL=https://...
```

- 프로필 캐릭터 자동 생성 컴포넌트 (`ProfileAvatar`)
- 후원 설정 탭 UI (후원금 / 결제 모드 / 문자번호 / 후원페이지)
- 후원페이지 공유 카드 + QR (`DonationPageShare`, `qrcode` 의존성)
- 공개 주소 헬퍼 (`getPublicBaseUrl`)
- 관리자 사이드바 아이콘
- 라이브 플랫폼(유튜브·인스타그램·틱톡) 선택 — **미완성 상태**

제가 파일을 덮어쓰면서 이 중 일부가 사라졌습니다. **모두 복구했습니다.**

## 복구 내역

| 항목 | 처리 |
|------|------|
| `schema.prisma` 라이브 컬럼 4개 | 복원 (`livePlatform`, `youtubeLiveUrl`, `instagramLiveUrl`, `tiktokLiveUrl`) |
| 알림 시스템 5개 파일 | 클라우드로 복원 후 유지 |
| 사회복지기관 승인 알림 (`notifyUser`) | `accounts.ts` 에 복원 |
| 문의 답변 알림 | 제가 직접 넣었던 코드를 공용 `notifyUser` 로 통일 |
| 새 문의 관리자 알림 (`notifySuperAdmins`) | `inquiry.ts` 에 복원 |
| 아바타·탭 UI·공유 카드·사이드바 아이콘 | PC 버전을 그대로 채택 |
| `qrcode` 의존성 | 클라우드에도 설치 |

## 함께 고친 것

**라이브 플랫폼 기능이 PC에서도 동작하지 않는 상태였습니다.** 화면에는 유튜브·인스타그램·틱톡 선택 UI가 있었지만, 저장 액션(`updateDonationPageAction`)이 그 값을 저장하지 않아 무엇을 골라도 반영되지 않았습니다. 마저 붙였습니다.

- 선택한 플랫폼과 3개 주소를 모두 저장
- **플랫폼별 호스트 검증** — 인스타그램 칸에 다른 사이트 주소를 넣으면 거절 (엉뚱한 주소가 저장되면 후원자가 빈 페이지로 이동)
- 스위치를 켤 때 선택한 플랫폼의 주소가 비어 있으면 안내 후 차단
- 후원샵 온에어 버튼이 **선택한 플랫폼의 라이브로 연결**

E2E 7건으로 검증했습니다(선택 저장 · 재진입 유지 · 잘못된 호스트 거부 · 후원샵 링크 연결 등).

## 추가로 발견한 것

**고객센터 폼(`/support`) 접수는 관리자에게 알림이 가지 않았습니다.** 위젯 문의만 알림이 발송되어, 폼으로 들어온 문의는 관리자가 목록을 직접 열어보기 전까지 알 수 없었습니다. `notifySuperAdmins` 를 추가했습니다.

## 남은 참고 사항

후원페이지 설정 폼은 **검증 실패 시 입력값이 DB 값으로 되돌아갑니다.** (플랫폼 선택·주소를 다시 입력해야 합니다) 문의 위젯의 전송 실패 시 본문 유실과 같은 원인이며, 2차 감사의 중간 등급 항목입니다. 다음 진행 시 함께 고치겠습니다.

## 앞으로의 권장 사항

이번 유실의 원인은 **PC와 클라우드 두 곳에서 각각 작업이 진행된 것**입니다. 재발을 막으려면 작업 시작 전에 PC의 최신 상태를 클라우드로 한 번 내려받는 절차가 필요합니다. 다음 작업 시작 시 제가 먼저 PC 상태를 확인하고 시작하겠습니다.
