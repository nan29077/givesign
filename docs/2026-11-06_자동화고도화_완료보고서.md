## 0. 한 줄 결론

## 2. 단계별 결과

### 1단계 — 자동 실행 기반 (`20261106100000_domain_events`)
- `domain_event` / `domain_event_delivery`: 업무 트랜잭션 안에서 기록(유니크 키), (이벤트, 소비자) 1회 처리, 실패 소비자만 백오프 재시도, 겹친 배치 안전(조건부 선점). 이벤트 22종(결제·환불·약정 6종·봉사 7종·영수증·캠페인·콘텐츠·서명).
- 기본 소비자: 기관 실시간 알림(후원·봉사 신청·약정·목표 달성·영수증 준비·서명 완료), 명단 사후 연결, 캠페인 목표 달성(`goal_reached_at`) 1회.
- 배치 레지스트리 `cron-registry.ts` + `cron_heartbeat`. 5개 배치를 공용 실행기로 통일(웹훅 잠금 추가, EMMA 수신 잠금 소유자 확인), 관리자 자동화 > **배치·이벤트** 탭(지연·실패·재처리).
- `approval_request` + `approvals.ts`(조건부 선점, 처리기 실패 시 되돌림).
- 고친 것: 봉사 신청서 열람 링크 미발송, 감사로그 누락 4곳, 미사용 `bullmq` 제거.

## 5. 알려진 한계·판단

- 네이버 블로그·카카오 채널은 공식 공개 게시 API 가 없어 자동 게시를 만들지 않았다(블로그 글쓰기 API 종료, 카카오 채널 API 는 관계·고객파일만).
- 실명 검사(AI 대본·캠페인 초안)는 "성+이름+호칭" 어림 규칙이라 띄어 쓴 표현은 놓칠 수 있다 — 최종 확인은 담당자 승인.
- 발급 문서 열람 횟수는 문자 링크 미리보기 봇도 1회로 셀 수 있다(추정).
- 결제 연동 문서 작성 화면(`/doc/[token]`, `FEATURE_GOODS` 전용)에는 머지 필드를 적용하지 않았다.
- 저니가 서명 문서(약정서·신청서)를 따로 보내지 않는다 — 약정서 서명은 약정 시점에 `agreements.ts` 가 한 번만 요청한다(중복 서명 방지).
- 외부 연동은 모두 가짜 `fetch` 로 요청 형태·서명·오류 처리를 검증했다. 키를 넣은 뒤 스테이징에서 가이드의 "확인 순서"를 먼저 밟아야 한다.
