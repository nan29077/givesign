## 1차 보고서 정정

### 철회: H-9 "부분 유니크 인덱스 6개가 다음 `db:migrate` 때 DROP 될 수 있다"

**재현되지 않는다.** 실제로 확인한 절차:

```
$ npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
-- This is an empty migration.

# 스키마에 필드를 하나 추가한 뒤 다시:
$ npx prisma migrate diff --from-config-datasource --to-schema <patched> --script
-- AlterTable
ALTER TABLE "system_setting" ADD COLUMN     "audit_probe" TEXT;
```

Prisma 7.10 은 데이터모델에 없는 부분 인덱스를 DROP 대상으로 잡지 않는다. `20260821090000_audit_fixes` 주석이 기록한 과거 사고는 이전 Prisma 버전의 동작이다. **조치 불필요.** (다만 Prisma 메이저 업그레이드 시에는 이 diff 를 한 번 다시 확인하는 게 좋다.)

## 신규 — 치명

### N-1 ✔실행입증 동시 MO 문자로 후원자 생성이 충돌한다 — 저장소의 테스트가 실제로 실패한다
`src/server/services/charge-flow.ts:243-255`

```ts
async function getOrCreatePayer(phone: string) {
  const ph = hashPhone(phone);
  return prisma.payerProfile.upsert({ where: { phoneHash: ph }, update: {}, create: {...} });
}
```

Prisma 의 `upsert` 는 이 형태에서 원자적이지 않다. 같은 새 번호로 MO 가 동시에 들어오면 두 요청이 모두 "행 없음"을 보고 INSERT 해 `payer_profile_phone_hash_key` 유니크 위반이 난다.

**실행 결과:** `tests/payer-onboarding.test.ts > 가입 전 MO가 겹쳐도 가입 링크 MT는 최초 1건만 발송한다` 를 3회 돌려 **1회 실패**했다(약 1/3 확률).

```
PrismaClientKnownRequestError:
Invalid `prisma.payerProfile.upsert()` invocation in charge-flow.ts:245
Unique constraint failed on the constraint: `payer_profile_phone_hash_key`
 ❯ processMoRow src/server/services/charge-flow.ts:420
```

바로 아래 `claimRegistrationGuide`(`:258-264`)는 "같은 전화번호의 동시 MO 중 한 요청만 발송권을 얻는다"고 조건부 `updateMany` 로 정교하게 막아 놨는데, **그 앞 단계인 후원자 행 생성 자체가 경합에 열려 있다.** 운영에서는 그 문자가 `result=ERROR` 로 기록되고 후원자는 아무 응답을 못 받는다(재전송하면 복구되긴 한다 — `charge-flow.ts:313-315`).

**조치:** `create` 를 try/catch 로 감싸 P2002 이면 `findUnique` 로 재조회하거나, `$executeRaw` 로 `INSERT ... ON CONFLICT (phone_hash) DO NOTHING` 후 조회한다.

**부수 효과:** 지금 `도구_테스트실행.bat` 은 3번에 1번꼴로 빨간불이 뜬다. 이걸 "가끔 그러는 것"으로 넘기면 진짜 회귀도 같이 묻힌다.

### N-2 ✔ 정지시킨 회원·사회복지기관이 문자후원는 계속 받는다 (제재 우회)

## 테스트가 무엇을 보장하고 무엇을 못 하는가

270개가 **결제 수신 경로는 두텁게** 덮는다 — MO 수신부터 원장 반영까지, 멱등·중복 방어, 원천징수 금액, 파트너 API 서명, 로그 마스킹, PIN 콜백 중복·만료. `paymentTransaction.count()`·`settlementLedger.count()` 로 "출금이 일어나지 않았음"을 직접 확인하는 방식도 좋다.

못 하는 것이 구조적이다:

- **mock 이 실패하지 않아서** 지급대행 unknown 분기(N-16), 결제 UNKNOWN 분기(N-17), 환불 PG 취소 실패(N-18), MT 발송 실패 분기가 전부 도달 불가다. 하필 전부 **돈이 새는 경로**다.
- **서버 액션 26개 중 직접 테스트되는 것은 2개**(`web-charge`, `web-charge-pin`). `studio.ts`(1,276줄)와 `admin/*`(2,100여 줄)은 0건 — N-3·N-9·N-10 이 그 직접적 결과다.
- **화면 렌더 테스트 0건.** N-7·N-8·N-19·N-20 같은 화면-동작 불일치는 원리적으로 안 잡힌다.
- `vi.useFakeTimers` 사용 0건 — 시간 의존 테스트가 실제 `new Date()` 를 쓴다.

**가장 위험한 회귀 3가지** (테스트가 절대 못 잡고, 터지면 돈이 새는 것):
1. 지급대행 unknown 응답 처리 변경 → 같은 회차 이중 이체
2. 결제 UNKNOWN 처리의 강등(→ 정산 누락) 또는 승격(→ 받지 않은 돈 지급)
3. 지급일 계산 회귀 또는 `settlementDays` 과소값 → PG 정산 전 선지급

가장 비용 대비 효과가 큰 보강은 여전히 **서버 액션 권한 경계 테스트**(비인증·타 사회복지기관·READ_ONLY/SUPPORT 세션으로 호출해 거절되는지)이고, 그 다음이 **mock 어댑터에 실패 주입 스위치**를 넣는 것이다.

## 잘 되어 있는 점

1차에서 적은 것에 더해, 이번 점검에서 새로 확인한 것:

- **마이그레이션 41개가 빈 DB 에서 실제로 전부 적용된다.** 개명 마이그레이션이 부분 유니크 인덱스 6개를 온전히 보존했고, Prisma 7 의 diff 도 깨끗하다. 스키마 관리가 정확하다.
- **결제 핫패스에 외부 호출이 없다.** PG 승인, Redis 속도제한, 지급대행 이체가 모두 트랜잭션 경계 밖이고 그 이유가 주석으로 남아 있다. 한도 판정도 charge 스캔이 아니라 `charge_counter` 집계 행 + 유니크 키로 O(1) 이다.
- **사회복지기관·후원자 격리는 빈틈이 없다.** 스튜디오 액션 25개와 `/studio/**` 전 페이지, CSV 내보내기까지 모든 DB 접근에 `merchantId` 가 걸려 있고, update 조건에 소유권을 함께 넣는 패턴이 일관된다. IDOR 누락 0건.
- **이중 결제 방어가 UI·서버·DB 3중이다.** 제출 중 버튼 비활성 + 클라이언트 멱등키 + `consumeSecureLink` + 조건부 `updateMany` + 부분 유니크 인덱스.
- 링크 오류 화면이 사유별(EXPIRED/USED/NOT_FOUND)로 갈리며 매번 "**결제는 진행되지 않았습니다**" 와 다음 행동을 함께 준다. 금융 서비스에서 가장 중요한 문구가 제자리에 있다.
