# 사회복지기관 콘솔 "API 문서" 메뉴 — 이해한 내용과 설계안

작성일 2026-09-05 · **보고 전용. 개발 착수 안 함.**

---

## 0. 제가 이해한 지시

사회복지기관 콘솔(스튜디오) 메뉴 **하단에 "API 문서"를 새로 만들고**, 기브싸인가 사회복지기관에 줄 수 있는 연동 규격서를 **항목별로 정리한 문서 허브**로 만든다. 사회복지기관이 자기 사이트를 직접 운영하면서

- MO·MT 를 자기 사이트에 직접 연동하거나
- 실물/비실물 상품을 MO 와 연동하거나
- 그 밖에 기브싸인가 제공할 수 있는 연동을

스스로 문서를 열어 붙일 수 있게 한다. 페이지는 보기 좋게 꾸미고, **나중에 기브싸인 기능이 고도화돼도 그 API 가 문서에 바로 반영되어** 사회복지기관이 곧바로 쓸 수 있어야 한다.

---

# 1. 지금 상태 (코드 확인 결과)

## 1-1. 메뉴에 API 문서가 없다

사이드바는 4개 그룹입니다 — **현황 / 판매 / 정산 / 계정**. 그 아래는 프로필·메인으로·로그아웃이 붙는 고정 영역입니다(`src/app/studio/layout.tsx`, `src/components/layout/console-shell.tsx`).

API 문서로 가는 길은 **후원 설정 → 연동 탭 안의 링크 하나**뿐입니다. 메뉴에 없으니 사회복지기관이 찾지 못합니다.

## 1-2. 문서 페이지는 1개, 그것도 원문 그대로

`/studio/docs/partner-api` 하나뿐이고, `docs/연동규격서_사회복지기관API.md` 파일을 읽어 **마크다운 원문을 `<pre>` 로 그대로** 뿌립니다. 목차·앵커·검색이 없습니다.

렌더링을 안 하는 건 의도된 선택입니다 — 주석에 *"마크다운 렌더러를 넣으면 코드 블록의 서명 예시가 조용히 바뀔 수 있어 연동 규격서로는 위험하다"* 고 적혀 있습니다. 문서가 여러 개로 늘어나면 이 방식은 읽기 어려워집니다(3-3 에서 다룹니다).

## 1-3. 실제로 제공 중인 API 는 4개뿐

| 엔드포인트 | 하는 일 | 서명 |
|---|---|---|
| `GET /api/partner/v1/ping` | 키가 유효한지, 어느 사회복지기관인지 확인 | 불필요 |
| `GET /api/partner/v1/charges` | 결제 완료 건 조회(커서 페이징, pending/all) | 불필요 |
| `POST /api/partner/v1/charges/ack` | 포인트 지급 처리 결과 통보(멱등) | **필수** |
| `POST /api/partner/v1/charges/shipment` | 배송 상태·송장 등록(멱등) | **필수** |

인증은 API 키(Bearer) + HMAC-SHA256 서명 + IP 허용목록입니다. 키는 `MerchantApiKey` 에 해시로 저장하고 원문은 발급 시 1회만 보여줍니다.

**즉 현재 연동 모델은 "사회복지기관이 주기적으로 가져가는(pull)" 방식 하나뿐입니다.**

# 2. 지시하신 것 중 **지금 없는 것** ★ 가장 먼저 보고드릴 부분

요청하신 세 가지는 문서를 쓴다고 해결되지 않습니다. **API 자체가 아직 없습니다.**

### ① MO 를 사회복지기관 사이트에 직접 연동 — 없음

지금 MO 는 `통신사 → 기브싸인 웹훅(/api/webhooks/mo)` 까지만 옵니다. 여기서 **사회복지기관 서버로 밀어주는(push) 경로가 없습니다.** `MerchantProfile` 에 웹훅 URL 필드조차 없습니다.

사회복지기관이 MO 를 실시간으로 받으려면 **아웃바운드 웹훅**을 새로 만들어야 합니다 — 재시도 정책, 서명 검증, 순서 보장, 실패 적재와 재발송까지 한 세트입니다.

### ② MT 를 사회복지기관이 직접 발송 — 없음

MT 는 기브싸인 내부 흐름(등록 안내 / 금액 선택 / PIN 요청 / 감사 / 실패)에서만 나갑니다. 사회복지기관이 원하는 문구를 원하는 번호로 보내는 API 는 없습니다.

이건 개발 난이도 문제가 아니라 **규제 문제**입니다.
- 발신번호 사전등록(전기통신사업법)
- 광고성 정보 사전 동의·수신거부·야간 발송 제한(정보통신망법)
- 스팸 신고가 쌓이면 제재받는 건 사회복지기관이 아니라 **우리 대표번호**입니다

열려면 발송 승인·건수 쿼터·문구 검수·즉시 차단 장치가 함께 있어야 합니다.

### ③ MO 로 상품 연동 — 절반만 있음

"문자를 보내면 상품·금액을 고르는 링크가 간다"는 흐름은 이미 있습니다(`SELECT_AMOUNT` 안내 문자, 상품 목록이 문자에 실립니다). 실물/비실물 구분, 즉시 지급(`FULFILLMENT_INSTANT`), 배송 등록도 있습니다.

없는 것은 **상품 동기화 API** 입니다. 지금은 사회복지기관이 자기 사이트와 별개로 **기브싸인 콘솔에 상품을 손으로 또 등록**해야 합니다. 상품·옵션·재고·품절을 API 로 맞추는 경로가 필요합니다.

> **그래서 문서 허브에는 "제공 중 / 준비 중" 상태 표시가 반드시 필요합니다.** 없는 API 를 규격서에 그럴듯하게 적어 두면, 사회복지기관이 개발에 착수했다가 중간에 막힙니다. 이건 신뢰 문제입니다.

# 3. 설계안

## 3-1. 메뉴 — 사이드바 맨 아래 "개발자" 그룹 신설

```
현황 · 판매 · 정산 · 계정
└ 개발자          ← 신설
   ├ API 문서     /studio/docs
   └ API 키       /studio/settings?tab=api  (기존 화면으로 연결)
```

후원 설정 연동 탭의 기존 링크는 그대로 둡니다(진입로가 둘이어도 무방합니다).

## 3-2. 문서 허브 `/studio/docs`

**화면 구성**
- 상단 요약 카드: 내 API 키 상태(발급됨/없음) · 기본 URL · 현재 API 버전 · 최근 변경일
- 좌측 카테고리 목차 + 우측 본문, 문서 내 앵커 이동, 검색

**카테고리 8개 (제안)**

| # | 카테고리 | 담기는 내용 | 현재 상태 |
|---|---|---|---|
| 1 | 시작하기 | 개요, 역할 분담, 연동 순서, 용어 | 기존 문서에서 분해 |
| 2 | 인증 | 키 발급, Bearer, HMAC 서명, IP 제한 | **제공 중** |
| 3 | 결제 연동 | 충전 건 조회 · 처리 결과 통보(ack) | **제공 중** |
| 4 | 주문·배송 | 송장 등록, 반품·교환 상태 | 일부 제공 |
| 5 | 상품 연동 | 상품·옵션·재고 동기화 | 준비 중 |
| 6 | MO 수신 연동 | 아웃바운드 웹훅, 서명 검증, 재시도 | 준비 중 |
| 7 | MT 발송 연동 | 발송 API, 템플릿, 규제 준수 | 준비 중 |
| 8 | 공통 규약 | 응답 형식, 오류 코드표, 멱등성, 환불·정산, 개인정보 | 기존 문서에서 분해 |

각 문서마다 **상태 배지**(제공 중 / 베타 / 준비 중 / 지원 종료), **버전**, **최종 수정일**을 답니다.

## 3-3. 렌더링 방식 — 결정이 필요합니다 ★

지금은 안전을 위해 마크다운을 렌더링하지 않습니다. 문서가 8개로 늘면 원문 `<pre>` 는 읽기 어렵습니다.

**제안:** 본문(제목·표·설명)은 렌더링하되 **코드 블록만은 원문 그대로 보존**하는 방식으로 갑니다. 코드 블록마다 복사 버튼을 붙이고, 문서 전체 원문 복사와 `.md` 다운로드도 남깁니다. 이러면 읽기 쉬우면서 서명 예시가 훼손될 위험은 없습니다.

# 4. "기능이 고도화돼도 문서가 바로 따라오게" ★ 이번 요청의 핵심

이 요구가 가장 중요하고, 이걸 안 잡으면 **석 달 뒤 문서와 코드가 어긋납니다.** 손으로 쓴 규격서는 반드시 뒤처집니다.

**방법: 문서를 사람이 쓰지 않고, 코드가 진실의 원천이 되게 한다.**

`src/server/api-docs/registry.ts` 한 곳에 엔드포인트 메타를 선언합니다 — 경로, 메서드, 카테고리, 상태(제공 중/준비 중), 버전, 요약, 요청·응답 스키마, 예시, 필요한 권한.

그 다음이 핵심입니다.

1. **라우트 핸들러가 이 레지스트리를 실제 검증 스키마로 사용한다.** 스키마를 고치면 문서가 같이 바뀝니다. 문서용 사본을 따로 두면 반드시 어긋나므로, 한 벌만 둡니다.
2. **문서 화면은 레지스트리를 읽어 목록·파라미터 표를 생성한다.** 새 API 를 추가하면 메뉴와 표가 저절로 생깁니다.
3. **OpenAPI(JSON) 를 같은 레지스트리에서 뽑아 공개한다.** 사회복지기관이 Postman·코드 생성기에 바로 넣을 수 있습니다.
4. **테스트로 강제한다** — "레지스트리에 등록되지 않은 `/api/partner/*` 라우트가 있으면 테스트 실패". 이러면 **새 API 를 만들면서 문서를 빠뜨리는 것이 불가능**해집니다.
5. 서술형 설명(왜 이렇게 하는지, 주의사항)만 마크다운으로 두고, 표와 스키마는 생성된 것을 씁니다.

**부수 효과:** 지난번에 말씀하신 페이사인 같은 **파트너용 규격서**도 같은 레지스트리에서 대상만 바꿔 뽑을 수 있습니다. 문서를 두 벌 쓰지 않아도 됩니다.

# 5. 결정이 필요한 것

| # | 결정할 것 | 왜 |
|---|---|---|
| 1 | 준비 중 API 를 문서에 **미리 공개**할지, 만들어진 것만 노출할지 | 미리 공개하면 사회복지기관이 준비할 수 있지만, 일정이 밀리면 신뢰를 잃습니다 |
| 2 | **MT 발송 API 를 열지** | 가장 무겁습니다. 규제·스팸 대응 세트가 통째로 따라옵니다 |
| 3 | MO 아웃바운드 웹훅의 우선순위 | 지금의 pull 방식으로 충분한지, 실시간이 꼭 필요한지 |
| 4 | 문서 공개 범위 | 로그인한 사회복지기관만 볼지, 공개 문서 사이트도 둘지. 공개하면 영업에 유리하지만 스펙이 드러납니다 |
| 5 | 마크다운 렌더링 도입 여부 (3-3) | 읽기 편함 vs 코드 블록 훼손 위험 |
| 6 | **샌드박스·테스트 키** 제공 여부 | 없으면 사회복지기관이 실서비스 키로 테스트합니다 — 실제 문자가 나가고 실제 결제가 잡힙니다 |
| 7 | 이번 범위 | 문서 허브만 먼저인지, 없는 API 개발까지인지 |

# 6. 권장 순서 (제안, 미승인)

| 단계 | 내용 | 규모 |
|---|---|---|
| 1 | **문서 허브 + 레지스트리 + 현재 4개 API 문서화.** 기존 규격서를 카테고리로 분해 | 작음 |
| 2 | 상품 동기화 API (사회복지기관 사이트 ↔ 기브싸인 상품 일치) | 중간 |
| 3 | MO 아웃바운드 웹훅 (실시간 수신 전달) | 중간 |
| 4 | MT 발송 API + 규제·스팸 대응 장치 | 큼 |

1단계를 먼저 하시길 권합니다. **레지스트리를 먼저 깔아 두면 2~4단계에서 만드는 API 들이 문서에 자동으로 올라옵니다.** 순서를 바꾸면 나중에 문서를 손으로 따라 쓰게 됩니다.

**개발은 지시하실 때까지 진행하지 않습니다.**
