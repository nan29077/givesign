### 전반 평가

인가(authorization) 골격은 견고합니다. 서버액션 65개 전부가 공용 래퍼(`run()` → `requireWriteAdmin`, `withMerchant()` → `requireMerchant`) 또는 1회용 링크 토큰·OTP 중 하나를 통과하며, **가드가 빠진 액션은 한 건도 없었습니다.** 사회복지기관 콘솔의 IDOR도 24개 액션 전수 확인 결과 없습니다(모두 `merchantId` 소유 재검증). 멱등 4중 방어, 정산 원장 append-only(앱 코드에 `settlementLedger.update/delete` 없음 + DB 트리거 설치 확인), 개인정보 3분리 저장·마스킹도 대부분 규칙대로입니다.

문제는 **다른 층에 몰려 있습니다.**

1. **폼과 액션 사이의 계약이 끊어진 곳** — 체크박스가 저장되지 않고, 폼에 없는 필드를 액션이 읽어 0으로 덮어씁니다. 코드는 컴파일되고 테스트도 통과하지만 사용자가 누른 것이 저장되지 않습니다.
2. **저장은 되는데 아무도 읽지 않는 설정** — 후원 설정의 직접 입력 범위·마케팅 수신 동의가 그렇습니다. 화면은 "지금 적용 중"이라고 단언합니다.
3. **요약 수치와 목록의 모집단 불일치** — `take: N` 으로 자른 배열의 `length` 를 건수로 쓰거나, 타일에만 `where` 를 빠뜨린 곳이 9군데입니다.
4. **실패 경로의 복구 수단 부재** — 환불 승인이 중간에 실패하면 관리자 화면에서 되살릴 방법이 없습니다.

## 3. 높음 (15건)

### H-1. 환불 승인이 중간에 실패하면 결제 건이 복구 불가능한 상태로 고착된다

- **위치** `src/server/services/refund.ts:75-102`, `:22-24`, 화면 `src/app/admin/refunds/page.tsx:186-209`
- **현상** `approveRefund()` 는 PG 취소 호출 **전에** 환불을 `APPROVED` 로 선점한 뒤, 그다음에 승인 거래를 찾는다. 여기서 실패하거나 PG 취소가 실패하면 환불은 `APPROVED`/`FAILED`, 결제는 `REFUND_REQUESTED` 로 남는다.
- **근거**
  ```ts
  const claimed = await prisma.refund.updateMany({ where: { id: refundId, status: 'REQUESTED' }, data: { status: 'APPROVED' } }); // :75
  const txn = refund.charge.transactions.find((t) => t.status === 'APPROVED');
  if (!txn) throw new Error('승인된 결제 거래가 없습니다.');                                                                        // :84
  ```
  화면은 `r.status === 'REQUESTED'` 일 때만 승인/거절 버튼을 그린다. 재요청도 막힌다 — `requestRefund` 의 환불 가능 상태 목록(`refund.ts:22`)에 `REFUND_REQUESTED` 가 없고, 기존 refund 가 `APPROVED` 면 중복 차단에도 걸린다.
- **영향** 후원자 돈은 돌아가지 않고 결제 건은 정산 파이프라인에서도 빠진다. 관리자 화면에 되살릴 버튼이 없어 DB 직접 수정이 유일한 복구 수단. `refund.ts:95` 주석의 "관리자 화면에서 재시도(신규 환불 요청)로 이어갈 수 있도록"은 실제로 성립하지 않는다.
- **제안** ① 승인 거래 존재 확인을 선점 **이전으로** 옮긴다. ② PG 취소 실패 시 `charge.status` 를 `chargeStatusLog.fromStatus` 로 되돌린다(거절 경로와 동일). ③ `FAILED`/`APPROVED` 환불에 "재시도 / 요청 상태로 되돌리기" 액션을 화면에 추가한다.

### H-2. 미래 시행일로 약관을 등록하면 그 순간 현행 약관이 공개 화면에서 사라진다

- **위치** `src/app/actions/admin/policy.ts:178-184`, 화면 `src/app/admin/terms/page.tsx:83`
- **현상** 등록 폼은 "시행일 (KST)" 을 받는데, 액션은 시행일과 무관하게 같은 유형의 기존 버전을 **즉시** `active=false` 로 내린다.
  ```ts
  await tx.termsVersion.updateMany({ where: { type, active: true }, data: { active: false } });
  return tx.termsVersion.create({ data: { ..., effectiveFrom, active: true } });
  ```
  반면 공개 조회는 `active: true` **와** `effectiveFrom <= now` 를 동시에 요구한다 (`app/terms/page.tsx:16`, `terms/e-finance/page.tsx:17`, `r/[token]/page.tsx:182`).
- **영향** 10월 1일 시행 개정안을 9월에 미리 등록하면 9월 내내 `/terms`·`/terms/e-finance` 가 "현재 게시된 약관이 없습니다" 로 뜨고, **결제 링크에서 필수 동의 항목이 통째로 사라진다.** 전자금융거래 약관 미게시 상태로 결제가 계속 처리된다.
- **참고** `app/privacy/page.tsx:16` 은 `effectiveFrom` 필터가 아예 없어 세 공개 페이지의 기준이 서로 다르다.
- **제안** 기존 버전은 `active` 대신 `effectiveTo`(= 새 버전의 `effectiveFrom`)로 마감하고, 공개 조회는 `effectiveFrom <= now` 중 최신을 고르도록 통일한다.

### H-3. 상품 "결제 화면에 노출" 체크박스가 동작하지 않는다 — 항상 노출로 저장된다

- **위치** `src/app/actions/studio.ts:569`, 폼 `src/components/studio/product-form.tsx:122`
- **근거**

### H-7. 수수료 상한(cap) 적용 시 공급가액·부가세가 보정되지 않아 원장에 틀린 부가세가 확정 기록된다

- **근거** `pgFee`/`platformFee` 는 결제 금액을 넘지 않도록 잘라내지만, 함께 반환되는 `pgFeeSupply`/`pgFeeVat`/`platformFeeSupply`/`platformFeeVat`/`vat` 는 **보정 전 값 그대로**다.
  ```ts
  const pgFeeCapped = pgFee > amount ? amount : pgFee;
  const platformFee = platformFeeRaw > room ? room : platformFeeRaw;
  return { pgFee: pgFeeCapped, pgFeeSupply, pgFeeVat, platformFee, platformFeeSupply, platformFeeVat, vat: pgFeeVat + platformFeeVat, ... };
  ```
  재현: 1,000원 결제 / 부가세 별도 49.9%+49.9%(`createFeePolicy` 의 합계 검사를 통과) → `platformFee=452` 인데 `platformFeeSupply(499) + platformFeeVat(49) = 548`.
- **영향** 이 값들은 화면용이 아니라 **저장된다**(`charge-flow.ts:1163`, `payment-reconcile.ts:149` 가 `feeVat` 로 Charge 에 기록, `settlement.ts:289` 가 원장 메모에 "(부가세 N원 포함)"). "공급가액 + 부가세 = 차감액" 불변식이 깨진 채 **append-only 원장에 확정**되고, 원장은 정정이 불가능하다. CLAUDE.md 절대 규칙 8 위반이며 세금계산서 근거로 쓸 수 없다.
- **제안** 잘린 뒤 `supply = capped*10/11`, `vat = capped - supply` 로 재산출하고, 잘림 발생 시 경고 로그를 남긴다. 부수적으로 `pgFixedFee` 에 상한이 없다(`actions/admin/shared.ts:69`).

## 7. 확인 결과 문제가 없었던 항목

검수 중 **의심했다가 소스로 확인해 결함이 아님을 확정한** 항목들입니다. 다음 점검에서 다시 파고들 필요가 없습니다.

- **서버액션 인가** — 65개 전부 가드 통과. 가드 없는 액션 0건.
- **사회복지기관 콘솔 IDOR** — 24개 액션 전수 확인, 모두 `merchantId` 소유 재검증. 결제자 액션도 클라이언트 `userId` 를 받지 않는다.
- **정산 원장 append-only** — 앱 코드에 `settlementLedger.update/delete/upsert` 없음. DB 트리거(`20260831200000_rename_domain_models/migration.sql:78`) 설치 확인. 정정은 반대 분개로 처리.
- **멱등 4중 방어** — `providerMessageId` UNIQUE / `idempotency_key` / PIN 세션 `updateMany` 원자적 선점 / 주문번호 재사용+거래결과조회 모두 코드에서 성립. 이중결제 경로를 찾지 못했다.
- **`status=pending` 에 실물 주문 혼입** — 없음. `charge-select.ts:359` 가 금액 확정 시점에 `PHYSICAL → SKIPPED` 로 못박고 파트너 API 가 이를 존중한다.
- **퍼센트↔소수 변환** — 여러 케이스 직접 실행 검증, 100배·0.01배 오류 없음.
- **자동 지급 이중 실행** — advisory lock + `{merchantId}:{dateKey}` 멱등키 + 트랜잭션 내부 재조회로 보호.
- **금융·개인정보 마스킹** — 계좌 `accountEnc`+`accountTail4`+`holderMasked` 3분리, 주민번호 `residentEnc`/`residentMasked`, 전화번호 `phoneMasked`. 화면 경로에 복호화 호출 없음(파트너 API 반출만 예외이며 이는 계약된 동작).
- **파트너 API 키** — 원문은 발급 응답 1회만, DB에는 `keyHash`/`signingEnc`. `safeEqual` 타이밍 안전 비교, 커서 소유권 확인.
- **`media/[name]` 경로 탈출** — 없음. 32hex 정규식 + `nosniff` + `CSP: sandbox`.
- **인메모리 폴백** — 운영에서 `ALLOW_INMEMORY_FALLBACK=true` 는 기동 실패로 처리, `degrade()` 재던짐. 닫혀 있다.
- **오픈 리다이렉트** — `safeNextPath` 가 `//`·`/\`·`/api/`·`/login` 차단.
- **로그 개인정보** — `scrubText` 가 전화번호 마스킹 + URL 제거, `SENSITIVE_KEYS` 에 secret/signature/token 포함.
- **cron/dev 라우트** — `CRON_SECRET` Bearer + `safeEqual` + 실행 잠금(fail-closed), dev 는 `isLocal` 게이트(APP_ENV 오타 시 prod 판정하는 안전한 기본값).
- **미await Promise** — 전 범위에서 의도적인 1건(`partner-auth.ts:235`, `.catch` 있음) 외 없음.
- **깨진 링크 / 고아 페이지** — 0건. `/support`·`/faq`·`/how-it-works`·`/terms/e-finance` 등 전부 실재.
- **이모지** — 0건.
- **KST 처리** — `kstDateKey/kstMonthKey/formatKst` 가 UTC+9 고정 오프셋으로 일관 처리. 예외는 H-8 의 CSV 라우트 한 곳뿐.
- **환불 시 한도 차감 복원** — `refund.ts:166` 이 `rollbackCounters` 를 호출한다(화면 안내와 일치).
