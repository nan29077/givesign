### [심각도: 중간] 승인 후 DB 오류 시 결제 거래가 REQUESTED 로 영구 고착 — 대사 큐·정기후원 모두 복구 경로 없음
- 위치: `src/server/services/charge-flow.ts:1287-1323` (approve 예외 처리), `src/server/services/payment-reconcile.ts:39` (`RECONCILABLE = ['UNKNOWN','TIMEOUT']`), `src/server/services/recurring.ts:461-464`, `src/server/services/pin-authorization.ts:183-206`
- 내용: approve 예외(타임아웃) 처리 블록 안의 DB 쓰기(`paymentAttempt.create`, `paymentTransaction.update({status:'TIMEOUT'})`)가 다시 실패하면 예외가 그대로 밖으로 나간다.
  ```ts
  } catch (e) {
    const isTimeout = ...;
    await prisma.paymentAttempt.create({ ... });            // 1290
    attemptNo += 1;
    await prisma.paymentTransaction.update({ where: { id: txn.id }, data: { status: 'TIMEOUT' } }); // 1298
  ```
  이때 상태는 charge=PENDING_PAYMENT, paymentTransaction=REQUESTED(기본값), 한도 카운터는 예약된 채, 결제사 승인 여부는 미확인. PIN 경로는 세션을 PENDING 으로 되돌리지만(`pin-authorization.ts:186`) 다음 콜백은 `charge.status !== 'PENDING_PIN'` 으로 INVALID_STATE 가 되어 재시도 불가. 수동 대사는 UNKNOWN/TIMEOUT 만 받고, 정기후원 `resolveCharge` 는 REQUESTED 를 PENDING 으로 보아 매일 하루씩 미루기만 한다(`postponeOneDay`).
- 영향: 결제사 승인이 실제로 났을 수 있는 건이 관리자 화면 어디에도 잡히지 않고, 정기후원이면 그 약정은 영원히 다음 출금을 만들지 못한다. 발생 조건은 "승인 직후 DB 쓰기 2회 연속 실패"로 드물지만, 돈이 빠졋을 수 있는 건이 복구 불가능하다는 점이 문제.
- 수정 제안: (a) catch 블록 내부 DB 쓰기를 `.catch` 로 감싸고 최종적으로 `UNKNOWN` 전이와 `raiseUnknownPaymentAlert` 를 보장, (b) 대사 대상에 "REQUESTED 이면서 N분 경과" 를 포함하거나 정리 배치에서 그런 건을 UNKNOWN 으로 올린다.
- 확신도: 확인됨

### [심각도: 중간] EMMA 폴링 경로에서 MO 행 생성 중 일시 오류가 "중복(DUPLICATE)" 으로 둔갑해 문자가 소실된다
- 위치: `src/server/services/charge-flow.ts:493-503`, `src/server/services/emma-mo-ingest.ts:50-69`
- 내용:
  ```ts
  try { moRow = await createOrReuseMoRow(inbound, routed, ph, dup?.id ?? null); }
  catch {   // 동시 재전송 경합
    const again = await prisma.moInboundMessage.findUnique({ where: providerKey, select: { id: true } });

  }
  ```
  P2002 만이 아니라 모든 예외(DB 순단, `encrypt` 실패 등)를 중복으로 처리한다. EMMA 수신기는 "예외를 던지면 되돌려 재시도, 결과 코드를 돌려주면 처리 완료"로 설계돼 있어, 이 경로에서는 저장되지 않은 문자가 처리 완료로 소비된다(`moMessageId: undefined`). HTTP 웹훅 경로는 사업자 재전송으로 회복되지만 EMMA DB 폴링은 재전송이 없다.
- 영향: 후원자가 문자를 보냈는데 결제 링크도, 수신 기록도 없이 사라진다. 로그에도 "중복"으로 남아 원인 추적이 어렵다.
- 수정 제안: `error.code === 'P2002'` 일 때만 DUPLICATE 로 처리하고 그 외는 재던진다. 기록 조회가 null 이면 DUPLICATE 로 보지 않는다.
- 확신도: 확인됨

- 확신도: 추정 (MTONET 이 1588 번호를 담당하는지 계약 정보가 코드에 없음)

### [심각도: 낮음] 웹 후원 결제 건에 `paymentMode = DIRECT_TRIGGER` 가 기록될 수 있으나 실제 흐름은 PIN
- 위치: `src/server/services/web-charge.ts:150`
- 내용: `resolvePaymentMode(merchant.paymentMode)` 결과를 그대로 저장하지만 이후 분기는 `resolveWebChargeChannel()`(PIN/LEGACY) 만 본다. `ALLOW_DIRECT_TRIGGER=true` + 기관 DIRECT_TRIGGER 이면 PIN 으로 결제된 건이 "즉시형" 으로 표시된다. MO 경로는 `'CONFIRM_LINK'` 고정이라 DIRECT_TRIGGER 실행 경로는 사실상 없다.

## 확인했으나 문제 없음 (참고)

- MO 중복: `moInboundMessage (providerCode, providerMessageId)` 유니크 + `charge` 멱등키(`merchant:provider:msgId`) + PENDING_AMOUNT 금액 0 생성 — 재전송·동시 수신 모두 1건.
- PIN 콜백: `paymentPinSession PENDING→COMPLETED` 조건부 갱신으로 선점, 실패 통지(`failPinAuthorization`)는 COMPLETED 를 덮지 않음, 만료 콜백은 승인하지 않음. 서명·IP·결과코드 fail-closed.
- 한도 판정: 후원자 행 `FOR UPDATE` 안에서 집계 읽기+예약(`commitCounters`), 실패 시 `rollbackCounters`(0 하한), UNKNOWN 은 되돌리지 않음(설계 의도 명시).
- 승인 기록·정산 3분개·후원자-기관 누적은 한 트랜잭션, 실패 시 UNKNOWN 으로 대사 큐 이관. 원장은 append-only, 수수료는 공급가액/부가세 분리(`splitSupplyVat`, 상한 보정 후 재분리).
- 정기후원: `recurring:{id}:{cycleMonth}` 멱등키(62일), PENDING 실행은 키를 지우지 않고 다음 배치에서 결제 건 상태로 확정, `channel/paymentMode = RECURRING`, `pointStatus = SKIPPED`, `ALLOW_RECURRING_DEBIT` 미설정 시 mock 외 SKIPPED. 크론 잠금은 owner 비교로 해제.
- 환불: 요청 선점(트랜잭션), 승인 선점 → PG 취소 → `processedAt` 재확인 후 DONE+반대분개 한 트랜잭션, 수수료 환입은 원 분개 비율로 산출, 영수증 VOID 시도 실패 시 관리자 알림, 한도 롤백은 `requestedAt` 기준.
- 자동 정산: 사회복지기관·일자 멱등키, 이체 전 `payoutIssuedAt` 기록, 실패 시 키 유지(재이체 금지), 재시도는 조회 우선, 결제 건은 `settlementRequestId` 로 고정.
- 크론 인증: 모두 `CRON_SECRET` Bearer + `safeEqual`, 비설정 시 로컬만 허용.
- 시간대: 날짜 키는 전부 KST 문자열(`kstDateKey`, `toDateKey`), DATE 컬럼은 UTC 자정으로 일관.
- 금액: BigInt 일관, `applyRate` 는 마이크로 단위 정수 연산·0 이상·결제액 이하 clamp.
