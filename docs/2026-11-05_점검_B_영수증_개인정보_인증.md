## 높음

### [심각도: 높음] 후원자 회원 탈퇴 시 기부금영수증 정보(주민번호 암호문)가 삭제되지 않고, 탈퇴한 후원자 명의로 영수증 발급·홈택스 명세 생성이 계속 가능
- 위치: `src/app/actions/payer.ts:282-376` (`withdrawAccount`), `src/server/services/receipts.ts:183-209` (`receiptCandidates`), `src/server/services/receipts.ts:258-270` (`issueReceipt`)
- 내용: 탈퇴 처리는 `payerProfile` 의 `userId/phoneHash/displayName` 과 `user` 행만 정리한다. `payerReceiptProfile`(`legalName`, `residentNoEnc`, `residentNoHash`, `address`, `hometaxOptIn`) 은 어디서도 삭제·무효화하지 않는다.
  ```ts
  // actions/payer.ts:340-369 — payerReceiptProfile 에 대한 처리 없음
  prisma.payerProfile.updateMany({ where: { userId: user.id }, data: { userId: null, onboardingStatus: 'WITHDRAWN', phoneHash: `withdrawn:...`, displayName: null, snsPlatform: null } }),
  prisma.user.update({ ... status: 'WITHDRAWN' ... }),
  ```
  한편 기관 콘솔의 발급 대기 목록·일괄 발급은 `onboardingStatus` 를 보지 않는다.
  ```ts
  // receipts.ts:186
  where: { merchantId, isTest: false, status: { in: PAID_STATUSES }, receiptId: null, paidAt: yearRange(taxYear), payerId: { not: null } },
  // receipts.ts:204  ready: profMap.has(g.payerId!)
  ```
  따라서 탈퇴 뒤에도 (1) 주민번호 암호문이 활성 레코드로 남고, (2) 기관이 "정보 등록됨" 으로 보고 영수증을 발급하며, (3) 그 영수증이 홈택스 명세 CSV 에 주민번호 원문으로 실린다. 영수증 발급 동의(`RECEIPT_ISSUANCE`)를 철회한 것도 아니어서 `deleteReceiptProfile` 의 철회 기록 경로도 타지 않는다.
- 영향: 탈퇴(개인정보 처리 목적 종료) 이후 민감정보(주민등록번호) 보관·이용이 계속됨. 개인정보보호법상 보유기간·목적 외 이용 문제, 그리고 본인이 더 이상 통제할 수 없는 상태(마이페이지 접근 불가)에서 국세청 제출까지 이어질 수 있다. 이미 발급된 영수증 스냅샷의 법정 보존과는 별개 문제다.
- 수정 제안: `withdrawAccount` 트랜잭션에 `deleteReceiptProfile(payerId)` 호출(또는 `payerReceiptProfile.deleteMany`) 과 철회 `consentRecord(agreed:false)` 기록을 포함하고, `receiptCandidates`/`eligibleCharges` 에서 `payer.onboardingStatus = 'WITHDRAWN'` 인 후원자를 "발급 불가(탈퇴)" 로 분리한다. 탈퇴 전 미발급 금액이 있으면 화면에서 먼저 안내하는 것도 고려.
- 확신도: 확인됨

## 중간

### [심각도: 중간] 주민등록번호 등록이 자기 신고만으로 끝나고, 중복 검사가 트랜잭션·유니크 제약 없이 이루어지며, 실패한 시도는 일일 횟수 제한에 잡히지 않음
- 위치: `src/server/services/receipts.ts:62-126` (`upsertReceiptProfile`), `prisma/schema.prisma:2430-2449` (`PayerReceiptProfile`, `@@index([residentNoHash])` 만 있음)
- 내용:
  ```ts
  const taken = await prisma.payerReceiptProfile.findFirst({ where: { residentNoHash: hash, payerId: { not: payerId } } });
  if (taken) return { ok: false, message: '이미 다른 계정에 등록된 주민등록번호입니다...' };
  const changesToday = await prisma.consentRecord.count({ where: { ..., type: 'RECEIPT_ISSUANCE', agreed: true, createdAt: { gte: ... } } });
  ```
  (a) 중복 검사와 upsert 가 같은 트랜잭션이 아니고 `residentNoHash` 유니크 제약이 없어 동시 요청 두 건이 같은 번호를 두 계정에 등록할 수 있다(TOCTOU). (b) "다른 계정에 등록됨" 으로 거절되는 경우 `consentRecord` 가 생기지 않아 하루 3회 제한에 포함되지 않는다 — 이 서버 액션(`saveReceiptProfileAction`)에는 별도 속도 제한도 없어, 특정 주민번호가 이 서비스에 등록돼 있는지(=후원자인지)를 무제한으로 확인하는 오라클이 된다. (c) 먼저 타인 번호를 등록한 쪽이 진짜 본인을 막는다(코드 주석에서 실명확인 미연동을 인지하고 있음).
- 영향: 타인 명의 영수증 발급·국세청 명세 등재, 주민번호 등록 여부 탐지.
- 수정 제안: `residentNoHash` 에 부분 유니크(`payerId` 당 1건은 PK 로 보장되므로 `residentNoHash` 자체 UNIQUE) 추가 후 P2002 를 잡아 거절; 거절된 시도도 카운터(`kv.incr('receipt-profile:try:<payerId>')`)에 포함; 서버 액션에 IP/계정 속도 제한 추가; 실명확인(본인인증) 연동 전까지는 등록 시 휴대폰 OTP 재확인을 요구하는 것을 검토.
- 확신도: 확인됨 (a, b) / 설계 한계 (c)

### [심각도: 낮음] 통합 로그인 `/api/auth/login` 은 존재하지 않는 계정에 대해 bcrypt 비교를 건너뛰어 응답 시간으로 계정 존재 여부가 드러남
- 위치: `src/app/api/auth/login/route.ts:75-78`
- 내용:
  ```ts
  const user = await prisma.user.findUnique({ where: { email } });
  if (!user || !(await verifyPassword(parsed.data.password, user.passwordHash))) { return fail('invalid', ...) }
  ```
  `verifyPassword` 는 `hash` 가 null 이면 즉시 false 를 돌려준다(`src/server/auth.ts:41-44`). 기관 후원회원 로그인(`donor-members.ts:36,147`)은 `DUMMY_HASH` 로 상수 시간을 맞춰 두었는데 통합 로그인은 그렇지 않다.
- 영향: 계정(이메일) 열거. 속도 제한(계정 10/10분, IP 50/10분)이 있어 대량 열거는 어렵다.
- 수정 제안: `verifyPassword(pw, user?.passwordHash ?? DUMMY_HASH)` 패턴으로 통일.
- 확신도: 확인됨

- 확신도: 확인됨

- 확신도: 확인됨

### [심각도: 낮음] 업로드 문서 서식(PDF·DOCX·HWP 등)이 `/api/media/<난수>.<ext>` 로 인증 없이 공개 서빙됨
- 위치: `src/app/api/media/[name]/route.ts:36-68`, `src/app/api/upload/document/route.ts:106-108`
- 내용: 파일명이 128비트 난수라 추측은 불가하고, 문서는 `Content-Disposition: attachment` + `nosniff` + `CSP sandbox` 로 내려간다. 다만 링크를 아는 사람은 누구나 받을 수 있고 `Cache-Control: public, max-age=31536000` 이라 중간 캐시에 남는다.
- 영향: 기관이 올린 서식(내부 양식)이 링크 유출 시 영구 공개. 후원자 개인정보가 담긴 제출본은 이 경로가 아니라 `valuesEnc` 로 암호화 저장되므로 영향은 서식 원본에 한정된다.
- 수정 제안: 문서 확장자는 기관 세션(`requireMerchant`) 또는 서명 토큰(`signBasePdf` 처럼)을 요구하고 `Cache-Control: private, no-store` 로 변경. 이미지는 현행 유지.
- 확신도: 확인됨

### [심각도: 낮음] 홈택스 명세 1회용 토큰이 GET 쿼리스트링(`?t=`)으로 전달됨
- 위치: `src/app/actions/fundraising.ts:347`, `src/components/studio/hometax-export-form.tsx:17-18`, `src/app/api/studio/receipts/export/route.ts:42`
- 내용: `window.location.assign('/api/studio/receipts/export?year=...&t=<token>')`. 토큰은 5분·1회용·사용자/기관/연도 바인딩이라 재사용 위험은 낮지만, 웹서버·프록시 접근 로그와 브라우저 히스토리에 남는다.
- 영향: 로그를 볼 수 있는 운영자가 5분 안에 같은 기관 세션을 갖고 있어야 악용 가능 — 사실상 낮음.
- 수정 제안: `fetch(POST)` 로 토큰을 본문에 담아 받고 Blob 으로 저장하거나, 토큰을 짧은 수명의 httpOnly 쿠키로 전달.
- 확신도: 확인됨

### [심각도: 낮음] 기관 코드 재발급 시 기관 후원회원 세션 쿠키 이름이 바뀌어 기존 쿠키가 고아로 남음
- 위치: `src/server/services/donor-members.ts:40-42` (`donorCookieName`), `src/app/actions/admin/accounts.ts:504-541` (`reissueMerchantCode`)
- 내용: 쿠키 이름이 `givesign_donor_<코드>` 이므로 코드가 바뀌면 회원은 전부 로그아웃되고(기능상 의도일 수 있음), 옛 이름의 쿠키와 그에 대응하는 `donorSession` 행은 폐기되지 않은 채 30일간 남는다. `getDonorMember` 는 `merchantId` 를 다시 검증하므로 다른 기관으로 섞이지는 않는다.
- 영향: 보안상 교차 접근은 없음. 다만 세션 행 정리와 사용자 안내가 빠져 있다.
- 수정 제안: 코드 재발급 액션에서 해당 `merchantId` 의 `donorSession` 을 revoke 하고, 쿠키 이름을 코드 대신 `merchantId` 기반으로 바꾸는 것을 검토.
- 확신도: 확인됨

## 확인했으나 문제 없음 (참고)

- 세션 쿠키(`givesign_session`, `givesign_donor_*`, `givesign_social_*`, `givesign_inquiry`): 모두 `httpOnly`, `sameSite: 'lax'`, 운영 https 에서 `secure`. 토큰 원문은 쿠키에만, DB 는 HMAC 해시(`tokenHash`). (`src/server/auth.ts:59-68`, `donor-members.ts:70-77`)
- 비밀번호 재설정: 토큰 해시 저장, 1시간 만료, `updateMany(usedAt:null)` 선점으로 1회성 보장, 성공 시 전 세션·잔여 토큰 폐기, 링크는 로컬에서만 출력(`password-reset.ts:150-203`). 확인 액션은 IP 20/10분 fail-closed(`actions/password-reset.ts:94`).
- 홈택스 관문: 비밀번호 재확인(시간당 5회) → 사유 → 하루 5회 → 5분 1회용 토큰(`setnx` 로 동시 소비 차단) → 사용자/기관/연도 대조 → 복호화는 `buildHometaxExport` 안에서만 → 감사로그 실패 시 파일 미반출. 우회 경로 없음.
- 영수증 금액: `PAID_STATUSES` 만 합산, `REFUNDED`/`REFUND_REQUESTED` 제외, 연도 경계 `+09:00` 고정, 환불 승인 시 `voidReceiptForRefundedCharge` 자동 무효, 실패 시 최고관리자 알림. 발급 번호는 `@@unique([merchantId, taxYear, seq])` + `receiptNo @unique` 이고 VOID 행이 남으므로 재사용되지 않는다. 기관 행 `FOR UPDATE` + `updateMany(receiptId:null)` 건수 대조로 동시 발급·발급 중 환불을 되돌린다.
- 발급 조건: `issuerReadiness` 가 `designatedDoneeVerifiedAt` 과 `designatedDoneeUntil`(KST 날짜 비교) 을 매 발급·재발급마다 확인. 기관이 지정 정보를 바꾸면 `verifiedAt` 이 초기화된다(`actions/fundraising.ts:207-211`).
- DonorMember: 세션 행에 `merchantId` 기록, 읽을 때 `s.merchantId !== org.id || s.member.merchantId !== org.id` 면 비로그인. 모든 액션이 폼의 `code` 로 기관을 다시 찾는다. 로그인 실패 더미 해시 적용, 이메일별 8/15분 + IP 20/분.
- 열린 리다이렉트: `/api/auth/login` `safeNextPath` 는 `//`·`/\` 거절, `/api/`·`/login` 제외. 기관 후원 `safeNext`/`safeDonorNext` 는 `/donate/<코드>` 접두 강제.
- CSRF: 서버 액션 외 상태 변경 라우트(`login`, `logout`, `upload`, `upload/document`, `notifications PATCH`, `inquiry GET`, `receipts/export`)는 `isSameOrigin` (Origin→Referer, 둘 다 없으면 거절).
- 업로드: 매직바이트 판정, 5MB/10MB, 저장 파일명 난수, `/api/media` 는 `^[a-f0-9]{32}\.(ext)$` 정규식으로 경로 탐색 차단, 글꼴(TTF/OTF)은 서빙 목록에 없음, SVG 미허용.
- 로그: `logger` 가 URL·전화번호 패턴과 민감 키를 가린다. 주민번호·영수증 정보는 로그에 마스킹 값만 남긴다(`receipts.ts:118-124`).
- `/api/health`: 비관리자에겐 `{ok}` 만.
- 암호화 키: `CRYPTO_MASTER_KEY` 32바이트 base64 아니면 SHA-256 파생(개발 편의), 운영은 `CRYPTO_PROVIDER=aws-kms` 강제이며 미주입 시 부팅 거부(`instrumentation.ts`, `env.ts:352`).
