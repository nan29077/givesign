# 문자후원 결제 흐름 — PIN 인증 구조 검토서

- 일자: 2026-08-21
- 배경: "문자 발송 = 결제 의사 표시일 뿐, 실제 출금은 후원자가 PIN을 입력해야 완료된다"는 지시 사항 검토
- **개발은 진행하지 않았습니다.** 현재 상태 진단과 필요한 변경 범위만 정리했습니다.

---

## 1. 결론부터

**말씀하신 구조가 맞습니다. 현재 기브싸인는 그 구조가 아닙니다.**

지금 코드는 *두 번째 문자부터는 서버가 빌키로 바로 출금한다*는 전제로 짜여 있습니다. 후원자가 PIN을 입력하는 단계가 **결제 경로 어디에도 없습니다.** PIN 화면은 최초 계좌 등록 때 딱 한 번만 나옵니다.

이대로 헥토 실연동에 들어가면 **두 번째 문자부터 전건 실패**합니다.

---

## 2. 헥토 공식 문서 확인 결과

헥토파이낸셜 개발자센터 내통장결제(EzAuth) 문서에서 확인한 내용입니다.

| 항목 | 헥토 문서 내용 |
|---|---|
| 일반결제 | 매 거래마다 결제창에서 고객이 **PIN을 입력해 인증** |
| 자동결제(빌키) | 최초 1회 계좌 등록 후, **"이후에는 PIN만 입력해"** 간편하게 결제 |
| 사회복지기관 단독 출금 | **"사회복지기관이 사용자 개입 없이 일방적으로 출금하는 것은 불가능"** |
| 결제창 역할 | **인증까지만** 처리. 인증 결과가 콜백으로 오면 결제창 종료 |
| 승인 | 그 뒤 사회복지기관 **서버가 결제승인 API 호출**해 최종 출금 |
| 시간 제약 | 결제인증 완료 후 **10분 이내** 승인 API 호출 |

즉 **인증(PIN, 사용자) → 승인(API, 서버)** 2단계이고, 앞 단계를 건너뛸 수 없습니다.

카드 빌키(정기결제)는 사용자 개입 없이 서버가 바로 승인할 수 있지만, **내통장결제는 계좌 출금이라 성격이 다릅니다.** 전자금융거래법상 출금 시마다 후원자 인증이 필요한 구조로 보입니다.

## 3. 지금 기브싸인가 실제로 하는 일

### 3-1. 최초 문자 (여기는 맞게 되어 있습니다)

```
MO 수신 → 미등록 후원자 판정
        → 보안링크 발급 (REGISTER_ACCOUNT, 30분)
        → MT 발송: "최초 문자는 후원 처리되지 않았습니다. 계좌 등록 후..."
        → 후원자가 링크 클릭 → 헥토 결제창(계좌 인증 + PIN 설정 + 출금이체 동의)
        → 빌키 발급 → 저장
```

### 3-2. 두 번째 문자부터 (여기가 문제입니다)

현재 두 가지 모드가 있는데, **둘 다 PIN 단계가 없습니다.**

**DIRECT_TRIGGER 모드** — `donation-flow.ts:543`
```
MO 수신 → 한도·금칙어 검사 → executePayment()
        → adapter.approve({ orderNo, amount, billKey })   ← 서버가 바로 승인 API 호출
        → 성공하면 결제 완료
```

**CONFIRM_LINK 모드 (기본값)** — `donation-flow.ts:515`
```
MO 수신 → 보안링크 발급 (CONFIRM_PAYMENT, 5분)
        → MT 발송: "확인하려면 링크를 누르세요"
        → 후원자가 링크 클릭 → **기브싸인 자체 확인 페이지**
        → "확인" 버튼 클릭 → confirmDonation() → executePayment()
        → adapter.approve(...)                            ← 결국 서버가 바로 승인
```

CONFIRM_LINK가 "확인 링크"라는 이름 때문에 PIN 흐름처럼 보이지만, **그 링크가 여는 건 헥토 결제창이 아니라 기브싸인가 만든 확인 페이지**입니다. 버튼을 누르면 곧바로 서버가 승인 API를 호출합니다. 후원자는 PIN을 입력하지 않습니다.

이 모드는 원래 "금융사 심사 대응용으로 후원자의 명시적 의사를 한 번 더 받는다"는 목적으로 만든 것이고, 헥토 PIN 인증과는 별개입니다.

### 3-3. PC 웹 후원도 동일

`web-donation.ts:114` 에서 똑같이 `executePayment()` 를 호출합니다. 같은 문제입니다.

### 3-4. 어댑터 인터페이스 자체에 자리가 없습니다

`payment/index.ts` 의 `PaymentAdapter` 인터페이스:

| 메서드 | 용도 |
|---|---|
| `createRegistrationSession` | **등록용** 결제창 URL 생성 |
| `completeRegistration` | 등록 콜백 → 빌키 발급 |
| `approve` | 빌키로 즉시 승인 |
| `inquire` / `cancel` / `revokeBillKey` | 조회·취소·해지 |

**"결제용 인증창(PIN) URL을 만드는 메서드가 없습니다."** 등록용만 있습니다.

### 3-5. 결제창 콜백을 받을 라우트가 없습니다

`.env.example` 에는 이렇게 적혀 있습니다.

```
HECTO_CALLBACK_URL="${APP_BASE_URL}/api/payments/hecto/return"
HECTO_NOTI_URL="${APP_BASE_URL}/api/payments/hecto/notify"
```

그런데 **`/api/payments/` 경로 자체가 존재하지 않습니다.** 현재 API 라우트 전체 목록에 없습니다. 등록 완료는 서버 액션(`/r/[token]/complete` 페이지)으로 처리하고 있어서, 헥토가 콜백을 보낼 수 있는 엔드포인트가 아직 하나도 없는 상태입니다.

PIN 흐름을 넣으려면 이 콜백 인프라부터 만들어야 합니다.

## 4. 지시하신 올바른 흐름

```
① 후원자가 사회복지기관 번호로 문자 발송
        │   (= "이 금액을 후원하겠다"는 의사 표시)
        ▼
② 기브싸인: 사회복지기관 라우팅 → 한도·금칙어 검사 → 후원 거래 생성
        │
        ▼
③ 기브싸인 → 헥토: "이 빌키로 N원 결제하려 한다. 인증창 URL을 달라"
        │
        ▼
④ 헥토 → 기브싸인: PIN 입력 페이지 URL 반환
        │
        ▼
⑤ 기브싸인 → 후원자: **MT 문자로 PIN 입력 링크 발송**
        │
        ▼
⑥ 후원자: 링크 클릭 → 헥토 PIN 화면 → PIN 입력
        │
        ▼
⑦ 헥토 → 기브싸인: 인증 완료 콜백 (authNo 등)
        │
        ▼
⑧ 기브싸인 → 헥토: 결제승인 API 호출 (**10분 이내**)
        │
        ▼
⑨ 출금 완료 → 원장 기록 → 사회복지기관 정산 반영
        │
        ├──▶ 후원자에게 결제 완료 안내
        └──▶ 방송 오버레이 + 유튜브 채팅 송출
```

핵심 차이는 **③④⑤⑥⑦ 다섯 단계가 통째로 없다**는 점입니다.

## 5. 바꿔야 할 범위

개발 지시를 주실 경우를 대비해 범위만 정리했습니다.

### 5-1. 어댑터 계층

- `PaymentAdapter` 인터페이스에 **결제 인증창 생성** 메서드 추가
  (등록용 `createRegistrationSession` 과 별개)
- `approve()` 시그니처 변경 — 빌키가 아니라 **인증 결과(authNo)** 를 받아 승인
- mock 어댑터도 PIN 단계를 흉내내도록 재작성 (E2E 유지를 위해 필수)

### 5-2. 콜백 인프라 (신규)

- `/api/payments/hecto/return` — 후원자 브라우저가 돌아오는 곳
- `/api/payments/hecto/notify` — 헥토 서버가 결과를 통지하는 곳
- 서명 검증, 중복 콜백 방지(멱등), 위조 차단

### 5-3. 상태 기계

- `DonationStatus` 에 **PIN 인증 대기** 상태 추가 필요
  (`PENDING_CONFIRM` 은 기브싸인 자체 확인용이라 의미가 다릅니다. 재사용할지 새로 만들지 결정 필요)
- `PaymentTransaction` 에 인증 세션 정보(인증 URL, 만료, authNo) 저장할 자리 필요
- **미입력 방치 건 자동 취소** 배치 (지금 `expireStaleConfirmations` 와 유사한 것)

### 5-4. 문자 발송

- **PIN 링크 안내 MT 템플릿 신규**
- 후원 1건당 MT가 **1통 → 2통**으로 늘어납니다 (PIN 링크 + 완료 안내)
  → **문자 발송 비용이 약 2배**가 됩니다. 사업성 검토가 필요한 부분입니다.

### 5-5. 한도·중복 처리

- 한도 검사 시점 재설계 — 지금은 접수 시 1회 + 결제 직전 1회입니다. PIN 대기 중인 건을 한도에 어떻게 반영할지 결정 필요
- 같은 후원자가 PIN을 안 누르고 문자를 여러 통 보내면 인증 링크가 계속 쌓입니다. 이 처리 규칙 필요

### 5-6. PC 웹 후원

- 웹은 문자와 달리 **브라우저가 이미 열려 있으므로** PIN 화면으로 바로 리다이렉트하면 됩니다 (문자 링크 불필요)
- 다만 같은 승인 로직을 공유해야 하므로 함께 손봐야 합니다

### 5-7. 제품 안내 문구 전면 수정

현재 후원샵·이용방법·FAQ에 이렇게 적혀 있습니다.

> "문자 1통을 보내면 3,000원이 등록된 내통장결제 계좌에서 결제됩니다"

**사실과 달라집니다.** "문자를 보내면 결제 링크를 문자로 보내드리고, PIN을 입력하면 결제가 완료됩니다"로 바꿔야 합니다. 후원샵 히어로 문구, 최초 안내, FAQ, 이용약관 결제 조항까지 영향이 갑니다.

### 5-8. 테스트

- 유닛 116건 / E2E 215건 중 **결제 흐름을 타는 테스트 전부** 재작성 대상입니다
- mock 어댑터가 PIN 단계를 흉내내야 E2E가 유지됩니다

## 6. 결정이 필요한 사항

개발 착수 전에 정해주셔야 하는 것들입니다.

**① 헥토 연동규격서 확보**
지금 어댑터는 공개 문서 기준으로 만든 것이고, 실제 상점별 규격서와 필드명이 다를 수 있습니다. **PIN 인증창 생성 API의 정확한 엔드포인트·파라미터·콜백 규격**이 있어야 정확히 만들 수 있습니다. 구두 계약은 끝났다고 하셨으니 규격서를 받아주시면 그에 맞춰 설계하겠습니다.

**② "결제 완료 푸시"의 의미**
"핀 번호를 입력해야 다시 결제 완료 푸시를 보내는 구조"라고 하셨는데, 이 푸시가
- (가) 기존처럼 **MT 문자**인지
- (나) 앱 **푸시 알림**(모바일 앱이 별도로 있어야 함)인지
- (다) 헥토가 후원자에게 직접 보내는 것인지

어느 쪽인지에 따라 구현이 달라집니다.

**③ CONFIRM_LINK 모드를 어떻게 할지**
PIN 화면이 곧 후원자 확인 절차가 되므로, 지금의 기브싸인 확인 페이지는 중복입니다.
- (가) 없애고 PIN 흐름 하나로 통일
- (나) 유지해서 2단계 확인 (문자 → 기브싸인 확인 → 헥토 PIN) — 금융사 심사에 유리할 수 있으나 이탈률이 올라갑니다

**④ MT 비용 2배 증가 수용 여부**
후원 1건당 문자가 2통이 됩니다. 단가·수수료 구조에 반영이 필요합니다.

**⑤ 미완료 건 처리 기준**
PIN을 안 누른 후원은 몇 분 뒤 자동 취소할지, 재발송을 허용할지.

## 7. 이 문제의 심각도

**치명(오픈 차단급)으로 봅니다.** 이유는 세 가지입니다.

1. **현재 구조로는 실연동 시 두 번째 문자부터 전건 실패합니다.** mock 어댑터에서는 잘 돌기 때문에 지금까지 드러나지 않았을 뿐입니다.
2. **제품의 핵심 약속("문자 한 통이면 후원")이 사실과 다릅니다.** 마케팅·약관·화면 문구 전반에 영향이 갑니다.
3. **되돌리기 어려운 시점이 다가옵니다.** 정산·오버레이·유튜브 송출이 모두 "결제 성공" 이벤트에 걸려 있어서, 결제 흐름이 바뀌면 그 하위가 다 흔들립니다. 실서비스 데이터가 쌓이기 전에 잡는 게 훨씬 쌉니다.

다만 **다행인 점**도 있습니다. 결제 성공 이후의 로직(원장 3분개, 정산, 오버레이, 유튜브, 한도, 멱등성)은 그대로 재사용됩니다. 바뀌는 건 **"결제 성공"에 도달하는 앞부분**뿐입니다. 어댑터·콜백·상태 3개 층에 집중되어 있어 범위가 명확합니다.

---

## 8. 제안

지시를 주시면 아래 순서로 진행하겠습니다.

1. 헥토 연동규격서 대조 → 정확한 API 스펙 확정
2. 어댑터 인터페이스 재설계 (mock 포함)
3. 콜백 라우트 + 상태 기계
4. 문자 템플릿 + 안내 문구
5. 테스트 전면 재작성
6. E2E로 전 구간 재검증

규격서가 아직이면 **공개 문서 기준으로 뼈대만 먼저 잡고 규격서 수령 시 SPEC 블록만 교체**하는 방식도 가능합니다. 지금 어댑터가 이미 그런 구조로 되어 있습니다(`HECTO_SPEC` 블록).
