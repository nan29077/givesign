## 2. 목표 흐름 (확정안)

```
① 후원자 → 사회복지기관 번호로 문자 발송
        │  "3000원 오늘도 화이팅"  (= 결제 의사 표시)
        ▼
② 기브싸인 : MO 수신 → 사회복지기관 라우팅 → 금칙어·한도 검사
        │            → 후원 거래 생성 (상태: 인증 대기)
        ▼
③ 기브싸인 → 헥토 : "빌키 XXX 로 3,000원 결제하려 한다. 인증창을 달라"
        ▼
④ 헥토 → 기브싸인 : PIN 입력 페이지 URL + 인증세션ID (유효 10분)
        ▼
⑤ 기브싸인 → 후원자 : MT 문자 ①  "결제하려면 PIN을 입력해 주세요 → [링크]"
        ▼
⑥ 후원자 : 링크 클릭 → 헥토 PIN 화면 → PIN 입력
        ▼
⑦ 헥토 → 기브싸인 : 인증 완료 콜백 (authNo)
        │              · 브라우저 리턴 + 서버 통지 두 경로 모두 수신
        ▼
⑧ 기브싸인 → 헥토 : 결제승인 API (authNo 기준, 인증 후 10분 이내)
        ▼
⑨ 출금 완료
        ├─ 결제 승인 기록 + 정산 원장 3분개  (같은 트랜잭션)
        ├─ MT 문자 ②  "후원이 완료되었습니다. 누적 N원"
        └─ 방송 오버레이 + 유튜브 라이브 채팅 송출

   ⑥에서 10분 안에 PIN을 안 넣으면 → 자동 취소 + MT 안내(선택)
```

**PC 웹 후원**은 ⑤⑥이 빠집니다. 브라우저가 이미 열려 있으므로 PIN 화면으로 **바로 리다이렉트**합니다. ⑦⑧⑨는 동일합니다.

## 3. 상태 기계 설계

### 기존 상태를 재사용합니다 (마이그레이션 최소화)

`PENDING_CONFIRM` 의 **의미만 바꿉니다.**

| 상태 | 기존 의미 | 새 의미 |
|---|---|---|
| `PENDING_CONFIRM` | 기브싸인 확인 페이지 대기 | **헥토 PIN 인증 대기** |
| `PENDING_PAYMENT` | 결제 승인 요청 중 | 그대로 (인증 완료 후 승인 API 호출 중) |
| `PAYMENT_SUCCESS` 이후 | — | 그대로 |

새 enum 값을 추가하지 않는 이유:

- 관리자 화면·라벨·필터·통계가 이미 `PENDING_CONFIRM` 을 다루고 있습니다
- **자동 취소 배치(`expireStaleConfirmations`)가 이미 이 상태를 대상으로 동작합니다** — ⑤번 결정사항을 공짜로 얻습니다
- DB 마이그레이션에서 enum 값 추가는 되돌리기가 번거롭습니다

바뀌는 건 "그 상태에서 후원자가 무엇을 보는가"뿐입니다. 기브싸인 확인 페이지 대신 헥토 PIN 화면으로 갑니다.

### 전이도

```
RECEIVED
   ├─(미등록)→ UNREGISTERED        ← 최초 문자. 계좌 등록 링크
   ├─(한도)→   LIMIT_BLOCKED
   ├─(금칙어)→ CONTENT_BLOCKED
   └─(정상)→   PENDING_CONFIRM     ← PIN 인증 대기 + MT 링크 발송
                    │
                    ├─(10분 경과)→ PAYMENT_FAILED  ← 자동 취소
                    │
                    └─(PIN 완료)→ PENDING_PAYMENT
                                       │
                                       ├─(승인 실패)→ PAYMENT_FAILED
                                       ├─(결과 미확인)→ PENDING_PAYMENT 유지 + 관리자 큐
                                       └─(승인 성공)→ SETTLEMENT_PENDING → 송출
```

## 4. 데이터 모델 변경

### `PaymentTransaction` 에 인증 세션 정보 추가

| 컬럼 | 용도 |
|---|---|
| `authSessionId` | 헥토 인증 세션 식별자 |
| `authUrl` | PIN 입력 페이지 URL (재발송·재시도용) |
| `authExpiresAt` | 인증창 만료 시각 (자동 취소 기준) |
| `authNo` | PIN 완료 후 헥토가 준 인증번호 (승인 API 재료) |
| `authCompletedAt` | 인증 완료 시각 (10분 제한 계산 기준) |

### `PaymentTxStatus` 에 인증 대기 값 추가

현재: `REQUESTED / APPROVED / FAILED / CANCELED / TIMEOUT / UNKNOWN`
추가: **`AUTH_PENDING`** (인증창 발급 후 PIN 대기)

여기는 새 값이 필요합니다. 결제 거래 단위로 "인증 대기"와 "승인 요청"을 구분해야 관리자 화면에서 어디서 막혔는지 보입니다.

### 마이그레이션

- 컬럼 5개 추가 (전부 nullable, 기존 행 영향 없음)
- enum 값 1개 추가
- **기존 데이터 손실 없음.** 되돌리기 쉬운 형태입니다

## 5. 어댑터 설계

### 인터페이스 변경

```
[추가] createPaymentAuth({ orderNo, amount, billKey, productName, buyerName, returnUrl })
         → { authUrl, authSessionId, expiresAt }
       "이 빌키로 이 금액을 결제할 건데, PIN 받을 화면을 만들어 달라"

[변경] approve({ orderNo, authNo, amount })
         → { providerTid, approvedAt, amount }
       기존: approve({ orderNo, amount, billKey })  ← 빌키로 바로 승인
       변경: 인증번호(authNo)로 승인

[유지] createRegistrationSession / completeRegistration / inquire / cancel / revokeBillKey
```

### mock 어댑터

E2E 215건을 살리려면 mock이 PIN 단계를 흉내내야 합니다.

- `createPaymentAuth` → 기브싸인 내부의 가짜 PIN 화면 URL 반환 (`/dev/pin/<세션>`)
- 그 화면에서 아무 6자리나 넣으면 콜백을 쏘는 구조
- 금액 끝자리 규칙(999 실패 / 888 타임아웃후승인 / 777 타임아웃후실패)은 **승인 단계에 그대로 유지**
- 여기에 **PIN 단계 시나리오**를 추가: 끝자리 `666` = PIN 미입력 방치 (자동 취소 검증용)

### 실어댑터 (hecto.ts)

`HECTO_SPEC` 블록에 결제 인증창 경로를 추가하고, `approve` 의 요청 본문을 authNo 기준으로 바꿉니다. **정확한 필드명은 셀러브릭스 연동 코드 대조 후 확정합니다.**

## 6. 콜백 설계 (신규)

### 두 경로를 모두 받습니다

| 경로 | 누가 부르나 | 역할 |
|---|---|---|
| `/api/payments/hecto/return` | **후원자 브라우저** | 화면 안내용. 결과 페이지로 이동 |
| `/api/payments/hecto/notify` | **헥토 서버** | **정본.** 브라우저가 안 돌아와도 결제는 진행 |

둘 다 같은 함수를 부르고, 그 함수는 **멱등**합니다. 후원자가 뒤로가기를 누르거나 헥토가 통지를 재전송해도 결제는 한 번만 일어납니다.

브라우저 리턴만 믿으면 안 되는 이유는 명확합니다. 후원자가 PIN 입력 직후 앱을 닫거나 지하철에서 신호가 끊기면 리턴이 오지 않는데, 헥토 쪽에서는 인증이 완료된 상태입니다. 서버 통지가 없으면 그 건은 영영 미처리로 남습니다.

### 보안

- **서명 검증 필수** — 콜백 본문 해시를 재계산해 대조. 위조 콜백으로 결제를 조작할 수 없게 합니다
- 세션ID ↔ 후원 거래 매핑을 서버에 저장해 두고, 콜백의 주문번호가 그 매핑과 일치할 때만 처리
- 콜백 수신 로그(`WebhookLog`)에 원문 저장 — 분쟁 시 근거

## 7. 자동 취소 설계

### 규칙

- PIN 링크 유효시간 **10분** (헥토 인증창 유효시간과 동일하게 맞춤, 환경변수로 조정 가능)
- 만료된 `PENDING_CONFIRM` 건은 **1분 간격 배치**로 `PAYMENT_FAILED` 처리
- 취소 시 MT 안내는 **보내지 않는 것을 권장**합니다 — PIN을 일부러 안 넣은 사람에게 문자가 또 가면 스팸으로 느낍니다. (원하시면 켤 수 있게 설정으로 빼겠습니다)

### 기존 자산 재사용

`expireStaleConfirmations()` 가 이미 `PENDING_CONFIRM` 만료 건을 정리하고 있습니다. 만료 판정 기준만 보안링크 만료 → **인증창 만료(`authExpiresAt`)** 로 바꾸면 됩니다.

### 대기 건이 쌓이는 문제

같은 후원자가 PIN을 안 넣고 문자를 계속 보내면 인증 링크가 무한히 쌓입니다. 제안:

- **동시 대기 건 상한 3건.** 초과하면 "이전 후원의 PIN 입력을 먼저 완료해 주세요" MT 발송
- 만료 전 같은 사회복지기관·같은 금액 재요청은 **기존 링크 재사용** (새 인증창을 만들지 않음)

## 8. ⚠ 남은 1건 — 셀러브릭스 헥토 연동 코드 대조

셀러브릭스에 이미 연동해 두셨다고 하셨는데, **그 프로젝트가 지금 세션에 연결돼 있지 않습니다.** 현재 연결된 폴더는 `기브싸인` 하나뿐이라 코드를 볼 수 없습니다.

### 연결 방법

Claude 데스크톱 앱에서 **폴더 추가(폴더 선택기)** 로 셀러브릭스 프로젝트 폴더를 이 세션에 연결해 주세요. 연결되면 제가 바로 읽고 대조하겠습니다.

### 연결되면 확인할 것

| 확인 항목 | 왜 필요한가 |
|---|---|
| 결제 인증창 생성 **엔드포인트 경로** | `HECTO_SPEC` 에 넣을 정확한 URL |
| 인증창 요청 **파라미터 이름·순서** | 필드명 하나 틀리면 전건 실패 |
| **해시/서명 재료 조합** | 위변조 검증에 실패하면 결제창이 안 열림 |
| 콜백 **응답 필드명** (authNo 등) | 승인 API 재료 |
| 승인 API가 **빌키 기준인지 authNo 기준인지** | 설계의 근간. 이것만 확인되면 나머지는 파생됨 |
| 자동결제 전용 경로 유무 | 일반결제와 다른 엔드포인트일 수 있음 |
| 실패 코드 체계 | 사용자에게 보여줄 안내 문구 분기 |

**이 대조 없이 착수하면** 공개 문서 기준으로 만들었다가 규격서와 달라 다시 뜯어야 할 수 있습니다. 어댑터가 `HECTO_SPEC` 블록으로 분리돼 있어 그 경우도 수습은 되지만, 처음부터 맞추는 편이 훨씬 낫습니다.

## 9. 화면·문구 변경

### 후원샵 (`/c/[code]`)

현재: "문자 1통을 보내면 3,000원이 등록된 내통장결제 계좌에서 결제됩니다"
변경: "문자를 보내면 결제 확인 문자가 옵니다. PIN을 입력하면 후원이 완료됩니다"

후원 방법 안내(1·2·3단계)도 **4단계**로 늘어납니다.

### 결과 페이지 (신규)

PIN 완료 후 후원자가 돌아오는 화면. 승인 성공/실패/처리중 3가지 상태를 보여줍니다.
승인이 아직 안 끝났으면 "처리 중입니다" 로 두고 폴링합니다.

### 영향 받는 곳

- 후원샵 히어로·후원 방법
- 이용방법(`/how-it-works`)
- FAQ
- **이용약관 결제 조항** — 결제 절차가 바뀌므로 법적 고지 대상입니다
- 최초 등록 안내 MT 문구
- 사회복지기관 스튜디오의 후원 상태 설명

### PC 웹 후원 패널

"결제하고 후원하기" 버튼 → PIN 화면으로 리다이렉트. 버튼 문구도 "PIN 입력하고 후원하기" 로 바꾸는 게 정직합니다.

## 10. 테스트 계획

### 새로 검증할 것

| 시나리오 | 확인 내용 |
|---|---|
| 정상 | 문자 → 인증창 생성 → MT 링크 → PIN → 콜백 → 승인 → 원장·오버레이·유튜브 |
| PIN 미입력 | 10분 후 자동 취소, 원장 기록 없음, 잔액 변동 없음 |
| 콜백 중복 | 같은 콜백 2번 와도 결제 1회, 분개 1세트 |
| 브라우저 리턴 없음 | 서버 통지만으로 결제 완료 |
| 위조 콜백 | 서명 불일치 → 거부, 결제 안 됨 |
| 인증 후 10분 초과 | 승인 실패로 확정, 후원자 안내 |
| 승인 타임아웃 | 기존 UNKNOWN 처리로 관리자 큐 |
| 동시 대기 상한 | 4번째 문자 차단 안내 |
| 한도 재검사 | 인증 대기 중 한도가 소진되면 승인 단계에서 차단 |

### 기존 테스트 영향

- 유닛 116건 중 **결제 흐름을 타는 약 40건** 재작성
- E2E 215건 중 **결제를 실행하는 스위트 5개** 재작성
- 정산·오버레이·유튜브·금칙어 테스트는 **결제 성공 이후**라 그대로 유지됩니다

## 12. 위험 요소

**① 규격 불일치**
필드명 하나만 달라도 전건 실패합니다. 셀러브릭스 대조가 이 위험을 대부분 없앱니다.

**② 콜백 미수신**
헥토 서버 통지가 방화벽·인증서 문제로 안 들어오면 결제가 붕 뜹니다.
→ 대응: 인증 완료 후 일정 시간 응답이 없는 건을 **주기적으로 `inquire()` 로 조회**해 확정하는 보정 배치를 함께 넣겠습니다.

**③ 이탈률 상승**
문자 → 링크 클릭 → PIN 입력으로 단계가 늘어 후원 완료율이 떨어집니다. 이건 기술이 아니라 **제도상 불가피한 부분**입니다. 다만 MT 문구를 짧고 명확하게 만들어 이탈을 줄일 수 있습니다.

**④ 10분 제한**
후원자가 문자를 늦게 확인하면 만료됩니다. 자동 취소 후 재시도 안내를 어떻게 할지는 운영 정책 영역입니다.

## 13. 요약
