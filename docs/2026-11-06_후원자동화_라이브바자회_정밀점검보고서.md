## 3. 높음 — 후원 자동화

### A-1. 승인 요청이 "처리 중"에 멈추면 되살릴 방법이 없고, 그 기관의 연간 영수증 준비가 영구히 멈춤
- 위치: `src/server/services/approvals.ts:115-145, 165-167`, `receipt-batch.ts:60-61`
- 상황: 담당자가 "N년 영수증 M건 발급"을 승인 → 서버 액션 안에서 수백 건 발급·문자 발송 중 배포·재시작·시간 초과로 끊김 → 요청이 `PROCESSING` 에 남음. 승인 대기함은 `PENDING` 만 보여 화면에서 사라지고, 연간 준비 배치는 `PROCESSING` 이 있으면 새 요청을 만들지 않는다.
- 영향: 영수증 일부만 발급된 채 아무도 모르게 정지. 회수 경로 없음.
- 수정: 오래된 `PROCESSING` 을 `PENDING` 으로 되돌리는 정리(발급은 `receiptId:null` 조건부라 재실행 안전), 대량 발급은 승인만 기록하고 배치가 실행, 관리자 화면에 정체 표시.

### A-2. 관리자 수동 확정(결과 미확인 → 승인)에는 `charge.paid` 가 발생하지 않음
- 위치: `src/server/services/payment-reconcile.ts:126-208` (이벤트 발생 코드·import 자체가 없음). 정상 경로는 `charge-flow.ts:1585-1604`.
- 상황: 결제사 시간 초과·정산 기록 실패로 UNKNOWN 이 된 건(정기후원 포함)을 관리자가 승인 확정 → 원장·누적은 반영되지만 기관 알림·명단 연결·캠페인 목표 달성·후원 감사 저니가 하나도 돌지 않음.
- 수정: `confirmApproved` 트랜잭션 안에서 같은 payload 로 `emitDomainEvent('charge.paid', tx)` (중복 키라 두 번 불러도 1건). payload 생성은 공용 함수로.

### A-3. 이벤트·저니 선점 시각이 "배치 시작 시각" → 오래 걸린 배치에서 같은 일을 두 번 처리
- 위치: `events.ts:178,198`(`lockedAt: now` = 함수 시작 시각), `journeys/engine.ts:212-221, 327, 343`, `cron-registry.ts:191-193`(잠금 240초 < 선점 유지 300초)
- 상황: 배치가 4분 넘게 돌면 다음 배치가 시작되고, 앞 배치가 막 잡은 건도 "선점 만료"로 보여 가로챔 → 기관 알림·저니 문자(영수증 정보 안내·재개 안내·봉사 감사·전날 안내)가 후원자에게 두 번 나감.
- 수정: 선점 시 `lockedAt: new Date()`, 배치 처리 시간 상한, 문자 단계에 `journey:{runId}:{stepKey}` 발송 중복 키.

### A-4. 연말 감사장이 "매월 발급" 기관에서는 첫 영수증 때 한 달 금액으로 나가고, 영수증 번호가 항상 빈칸
- 위치: `journeys/definitions.ts:335-354`(트리거 `receipt.issued`, 주기 조건 없음, 키 `year-end:{기관}:{후원자}:{연도}`), `receipts.ts:403-412`(payload 에 `receiptNo` 없음), 기본 서식 `documents.ts:582`
- 상황: MONTHLY 기관 후원자는 1~2월 첫 월별 영수증과 동시에 "한 해 동안 보내 주신 후원" 감사장을 그 달 금액으로 받는다. 같은 해에는 키 때문에 진짜 연말 감사장이 다시 안 나감. 수동 개별 발급도 같다. 모든 기관의 기본 문구는 "기부금영수증()은 …"으로 깨진다.
- 수정: `receiptCycle=YEARLY` 일 때만 시작(또는 payload 에 cycle 을 넣고 거름), MONTHLY 는 연말 1회 별도 계산. payload·context 에 `receiptNo` 추가.

### A-5. 알림톡이 접수 뒤 카카오 전달에 실패해도 문자 대체가 나가지 않음 (실연동 켰을 때)

## 4. 높음 — 라이브 바자회

### B-1. 마이너스 정산이 "확정"에 영구히 묶이고 다음 달로 넘어가지 않음 → 기관 과지급
- 위치: `services/bazaar.ts:1282`(지급은 0원 이하 거절 — 문구 "다음 달 정산과 함께 처리"), `:1262-1273`(확정은 음수도 허용), `:1049-1057`(확정된 달 건너뜀), `:1240`(확정 정산 재계산 안 함)
- 예: 10월 판매 100,000원 → 70,000원 지급. 11월에 10월분 환불 5,000원만 들어옴 → 순판매 −5,000, 수수료 환입 −1,500, 지급액 −3,500원. 11월 정산은 확정되지만 지급도 이월도 안 됨.
- 영향: 3,500원 영구 미회수(기관 과지급), 미지급 건수·합계에 계속 잡힘.
- 수정: 0 이하 확정 시 다음 달 원장에 이월 행(`carry:{settlementId}`) + 상태 CARRIED, 화면 문구를 실제 동작과 일치.

### B-2. 판매 결과 승인과 정산 확정이 동시에 일어나면 그 판매가 어느 정산에도 안 들어감 → 기관 미지급
- 위치: `bazaar.ts:1191`(승인 트랜잭션 안 `openMonthFor`, 정산 행 잠금 없음), `:1262-1273`(확정이 트랜잭션 밖에서 합계 계산)
- 예: A 가 11월 판매 50,000원 승인 중(미커밋) → B 가 11월 정산 확정(그 행을 못 봄) → A 커밋. 11월 원장에 순 35,000원이 생기지만 확정 정산은 다시 계산되지 않음.
- 수정: (기관, 월) 정산 행 `FOR UPDATE`(또는 advisory lock)로 승인·확정을 직렬화, 확정을 한 트랜잭션으로.

### B-3. 가액 "수락"이 화면에서 본 제안이 아니라 수락 순간의 마지막 제안을 확정 → 영수증 과다 발급 위험
- 위치: `bazaar.ts:534-539`(제안 id 없이 `createdAt desc` 첫 행), `:495-521`(제안 생성에 잠금 없음)
- 예: 기관 화면에 기부자 제안 100,000원 → 기관이 확정을 누르기 직전 기부자가 1,000,000원으로 재제안 → 1,000,000원이 확정되고 그대로 영수증 금액 기준이 됨.
- 수정: 화면이 본 제안 id 를 넘기고 트랜잭션 안에서 "마지막 제안 = 그 id"일 때만 확정, 제안 생성도 기부 건 잠금 아래에서.

### B-4. 사진·근거 파일 업로드가 서버 액션 기본 1MB 제한에 걸림
- 위치: `next.config.ts`(`serverActions.bodySizeLimit` 설정 없음), `components/bazaar/donation-form.tsx:112-113`(안내 "한 장 5MB 이하"), `actions/bazaar-giver.ts:123-124,151`, 관리자 검수 사진 `actions/admin/bazaar.ts:157-159`, 판매 CSV `:305`(2MB 허용)

- 수정: `experimental.serverActions.bodySizeLimit` 를 업로드 상한에 맞게 설정하거나 업로드를 전용 API 로 분리, 안내 문구 일치.

### B-5. 참여가 "정지"된 기관도 진행 중 건의 매칭 수락·가액 확정·검수 확정(영수증 발급)·편성 승인을 계속할 수 있음

## 7. 정상 동작 확인(요지)

- **결제·이벤트:** 정상 결제 경로의 `charge.paid` 는 승인·정산 원장과 같은 트랜잭션. 이벤트 중복 키·(이벤트, 소비자) 1회·백오프 재시도·관리자 재처리 정상. 배치 10개 경로 등록·인증·소유자 잠금·실행 기록 일치.
- **저니:** (저니, 이벤트) 유일, 야간 21~9시 KST 계산·탈퇴/차단/수신 거부 정지 정상. 연간 영수증 준비는 KST 1~2월·전년 귀속·승인 후 발급.
- **전자문서:** 열람 토큰 32바이트·HMAC 해시만 저장·30일 만료·재발송 시 교체. `/my/documents` 는 본인 것만. 머지 값 이스케이프·주민번호/전화 마스킹, 봉투 생성과 요금 차감 한 트랜잭션·같은 발송 키 1회.
- **영수증:** 결제 성공·미발급 건만 합산, 조건부 묶기, 기관 행 잠금 일련번호, 환불 시 무효, 공익법인 확인·탈퇴자 제외.
- **SNS·알림:** OAuth state HMAC·10분·기관 일치·nonce 쿠키·구글 PKCE, 토큰 암호화. mock 이 게시 주소·지표를 꾸미지 않음. `/go` 오픈 리다이렉트 없음. 솔라피·SES 서명 규격 일치. 봉사 정원 원자적 증감·KST 회차 계산·후원자 병합 순환 방지.
- **바자회:** 수수료 계산 예시(판매 100,000 − 환불 5,000 → 수수료 28,500 / 귀속 66,500) 정확, 상태 전이는 모두 `transition()` 경유, 검수 확정·판매 승인·지급 이중 처리 방지, 원장·상태 이력 append-only 트리거, 홈택스는 발급 상태만·복호화는 명세 생성 지점만. 스위치 가드는 화면·액션·API 빠짐없음, 기부자·기관 범위(IDOR) 정상, CSV 수식 주입 방지, 업로드 매직바이트 검사.
