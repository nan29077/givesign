# 후원 항목 선택 결제 개발 완료 보고서

작성일: 2026-08-31
범위: 문자PG 전환 3단계 — 금칙어 정책 완화 · 후원 항목 · MO 금액 선택 흐름 · 충전 반영 연동(mock)

---

## 0. 요약

문자 1건 = 고정 금액이던 구조를 걷어내고, **후원자가 금액을 고르는 구조**로 바꿨습니다.

```
[MO 문자]  금액 없음 → 결제 건 생성(금액 0 · PENDING_AMOUNT) + 선택 링크 MT 1통
   ↓
[한 화면]  사회복지기관이 등록한 후원 항목 선택 또는 직접 입력 → 금액 확정
   ↓       (문자를 한 번 더 보내지 않고 그대로 이어짐)
[PIN]      결제사 PIN 입력 → 콜백 → 승인 → 정산 분개
   ↓
[반영]     사회복지기관에 충전 반영 요청 (후원자 휴대폰 번호로 회원 매칭)
```

PC 결제 페이지도 같은 상품 목록을 쓰므로 모바일·PC 의 금액 결정 방식이 하나로 합쳐졌습니다.

---

## 1. 만든 것

### 1-1. 후원 항목 (`charge_product`)

- 사회복지기관이 상품을 등록한다: 이름 · 금액 · 노출 순서 · 사용 여부. **금액 = 지급 포인트(1:1)** 이므로 금액 컬럼 하나만 둡니다.
- 지난 결제가 금액을 참조하므로 **삭제 대신 보관(archive)** 합니다.
- 사회복지기관 콘솔: `결제 설정 → 후원 항목` 탭에서 추가·수정·순서·사용·보관, 직접 입력 허용 여부 설정.
- `creator_profile.donation_amount`(문자 1건당 고정 금액)는 폐기했고, 기존 값은 마이그레이션에서 **첫 상품으로 옮겼습니다.**
- 직접 입력 범위는 사회복지기관별입니다(`min_amount` ~ `max_amount` ∩ 한도 정책).

### 1-2. MO → 금액 선택

- MO 를 받으면 결제 건을 **금액 0 · `PENDING_AMOUNT`** 로 만들고 `SELECT_AMOUNT` 보안링크를 보냅니다.
- 금액이 정해지는 시점에 **한도를 확인**합니다(금액 없이는 한도를 볼 수 없습니다).
- 금액 확정 즉시 결제사 PIN 세션을 만들고 **화면이 그대로 PIN 으로 이동**합니다. PIN 링크 문자는 보내지 않습니다.
- 링크 유효시간은 10분(`PAYMENT_SELECT_TTL_SEC`, 기본 600초)입니다. 금액 선택 + PIN 입력을 한 번에 끝내는 시간입니다.

### 1-3. 이중 결제 방어 (가장 중요한 부분)

| 상황 | 막는 방법 |
|---|---|
| 같은 MO 재전송 | 기존 멱등키(`donation:<사회복지기관>:<메시지ID>`) 그대로 |
| 선택 링크 두 번 클릭 | 링크 1회용 선점(`consumeSecureLink`) |
| 동시 클릭(두 요청 동시 도착) | 금액 확정을 `status = PENDING_AMOUNT` 조건부 갱신으로 처리 — 한 쪽만 성공 |
| 같은 결제로 PIN 재요청 | `payment_pin_session.donation_id` UNIQUE 유지 |

### 1-4. 금칙어 정책 완화

- 문자 본문은 외부에 노출되지 않고 사회복지기관·최고관리자만 문자 관리에서 봅니다. 그래서 **금칙어는 결제를 막지 않고 기록만 마스킹**합니다.
- 지난 정책으로 남은 `BLOCK` 규칙도 마스킹으로 취급하며, 마이그레이션에서 `MASK` 로 옮겼습니다.
- 화면에서 차단 선택지를 없앴고, 과거 차단 이력 화면은 "지난 이력" 으로 남겨 두었습니다.

### 1-5. 충전 반영 연동 (mock)

- `src/server/adapters/charge-reflect/` — 어댑터 인터페이스 + mock. 실제 계약 전이므로 **성공을 꾸며내지 않고 mock 임을 로그·화면에 남깁니다.**
- **계정 식별은 후원자 휴대폰 번호**입니다. 사회복지기관가 같은 번호로 회원을 찾습니다.
- 결제 성공 후 호출하며, **반영 실패가 결제 결과를 뒤집지 않습니다.** `donation.reflect_status` 로만 남겨 관리자가 확인·재시도합니다.

---

## 2. 없앤 것

- **`DIRECT_TRIGGER`(MO 수신 즉시 결제)** — 금액이 정해지지 않은 상태에서 출금할 수 없습니다.
- 구(舊) 확인 링크(`CONFIRM_PAYMENT`) 발급 — MO 경로에서 더 이상 만들어지지 않습니다. 해석 코드는 남겨 두었습니다.

## 3. 검증

리눅스 환경(내장 DB PGlite)에 실제로 설치해 돌린 결과입니다.

- **마이그레이션**: 빈 DB 에서 35개 전부 순서대로 적용 성공.
- **타입 검사**: 통과 (오류 0).
- **프로덕션 빌드**(`next build`): 성공. 삭제된 방송 화면이 라우트 목록에서 사라진 것도 확인했습니다.
- **테스트**: 205건 중 204건 통과.
  - 새로 쓴 충전 선택 회귀 테스트 14건 전부 통과 — 링크 1회성, 동시 클릭, 범위 밖 금액, 다른 사회복지기관 상품, 사용 중지 상품, 만료 링크, 상품 없음, 차단 후원자, 충전 반영 성공/실패.
  - 남은 1건(`[15] 환불하면 정산 원장에…`)은 **내장 DB 의 트랜잭션 5초 제한** 때문입니다. 변경 전 코드(HEAD)로도 같은 환경에서 동일하게 실패하는 것을 확인했으므로 이번 변경과 무관합니다. 실제 PostgreSQL 에서 확인이 필요합니다.
  - `[6] 속도 제한` 은 전체 실행 중 간헐적으로 같은 이유로 실패하고, 단독 실행에서는 통과합니다.

## 4. 확인이 필요한 운영 사항

1. **선택 링크를 놓치면 문자를 다시 보내야 합니다.** PIN 링크를 문자로 보내지 않기로 했으므로(한 화면에서 이어짐), 후원자가 화면을 닫으면 그 링크는 이미 사용된 상태입니다. 문자를 다시 보내면 새 링크가 갑니다.
2. **한도 초과 안내가 문자에서 화면으로 옮겨졌습니다.** 금액을 고르는 그 화면에서 즉시 알려 주므로 별도 안내 문자를 보내지 않습니다.
3. **기존 로컬 DB 는 재생성이 필요합니다**: `도구_DB시작.bat` → `npm run db:reset`.
4. E2E 스크립트는 아직 옛 화면 기준입니다(`e2e/README.md` 참고).
