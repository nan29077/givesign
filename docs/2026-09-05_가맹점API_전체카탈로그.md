# 1. 인증·키 (Auth)

## 1-1. 키 체계 — LIVE / TEST 두 종류로 나눈다

지금은 키가 한 종류입니다. 샌드박스를 주려면 **키 자체에 모드가 있어야** 합니다.

| 모드 | 접두사 | 동작 |
|---|---|---|
| 운영 | `gs_live_...` | 실제 결제·실제 문자·정산 대상 |
| 테스트 | `gs_test_...` | 테스트 데이터에서만 동작. **문자 안 나감, 돈 안 빠짐, 정산 제외** |

접두사를 다르게 두는 이유는, 사회복지기관 개발자가 실수로 운영 키를 테스트 코드에 넣었을 때 **눈으로 바로 구분**되게 하기 위해서입니다. 사고의 대부분이 여기서 납니다.

## 1-2. 이미 되어 있는 것

사회복지기관별 API 키 발급은 **이미 동작합니다.** 후원 설정 → 연동 탭에서 키 이름과 허용 IP 를 넣고 발급하면, API 키와 서명 비밀키가 **그 자리에서 한 번만** 표시됩니다(`issueMerchantApiKey`, `MerchantApiKey` 테이블, 원문은 해시로만 저장).

새로 필요한 것은 **TEST 모드 키**와 키 관리 API 뿐입니다.

## 1-3. 엔드포인트

| 상태 | 메서드·경로 | 설명 |
|---|---|---|
| **제공 중** | `GET /api/partner/v1/ping` | 키 유효성·소속 사회복지기관 확인 |
| 준비 중 | `GET /api/partner/v1/me` | 사회복지기관 프로필·결제 모드·수신번호·한도 조회 |
| 준비 중 | `GET /api/partner/v1/keys` | 발급된 키 목록(원문 제외) |
| 준비 중 | `POST /api/partner/v1/keys/rotate` | 키 무중단 교체(구키 유예 24시간) |
| 준비 중 | `DELETE /api/partner/v1/keys/{prefix}` | 키 폐기 |

**문서에 반드시 들어갈 것:** Bearer 헤더, HMAC-SHA256 서명 생성 절차(타임스탬프·논스·바디 해시), 허용 IP, 시계 오차 허용범위, 서명 실패 오류코드, Node/PHP/Python 서명 예제.

# 2. MT 발송 (문자 보내기) — "최대한 가볍게" 의 구체안 ★

지시하신 대로 **규제 부담이 붙는 부분을 잘라내고** 여는 안입니다. 핵심은 기능을 줄이는 게 아니라 **범위를 좁혀서 규제가 아예 적용되지 않게** 만드는 것입니다.

## 2-1. v1 을 가볍게 만드는 4가지 제약

| 제약 | 그래서 없어지는 부담 |
|---|---|
| **발신번호는 기브싸인 번호 고정** (사회복지기관 번호 등록 불가) | 발신번호 사전등록을 사회복지기관이 하지 않아도 된다. 우리가 이미 등록한 번호를 쓴다. |
| **정보성 문자만** — 거래·주문·지급과 직접 관련된 안내로 한정. 광고·홍보 문구 금지 | 광고성 정보 사전동의, 야간(21~08시) 발송 제한, 수신거부 문구 의무가 **적용 대상이 아니게 된다.** |
| **수신자는 그 사회복지기관에 거래 이력이 있는 후원자만** (`payerRef` 로만 지정, 임의 번호 입력 불가) | 콜드 발송이 원천 차단된다. 스팸 신고가 사실상 생기지 않는다. |
| **템플릿 기반** — 사회복지기관이 등록한 템플릿 + 치환자만. 자유 본문 금지 | 문구 검수를 발송 때가 아니라 등록 때 한 번만 하면 된다. |

이 네 가지면 **v1 은 "우리 번호로, 우리 고객에게, 거래 안내를, 검수된 문구로" 보내는 것**이 됩니다. 규제 세트가 통째로 빠지고, 남는 건 발송량 쿼터와 로그뿐입니다.

## 2-2. v2 로 미루는 것 (준비 중 표시)

사회복지기관 발신번호 등록 / 자유 본문 / 광고성 발송 / 대량 캠페인 / 예약 발송 / 카카오 알림톡 대체발송. 이건 별도 계약과 심사가 붙습니다.

## 2-3. 엔드포인트

| 상태 | 메서드·경로 | 설명 |
|---|---|---|
| 준비 중 | `POST /api/partner/v1/mt/messages` | 템플릿 + 치환값으로 1건 발송 (멱등키 필수) |
| 준비 중 | `GET /api/partner/v1/mt/messages/{id}` | 발송 상태(접수/발송/도달/실패) 조회 |
| 준비 중 | `GET /api/partner/v1/mt/messages` | 발송 이력 목록(기간·상태 필터) |
| 준비 중 | `GET /api/partner/v1/mt/templates` | 등록된 템플릿과 치환자 목록 |
| 준비 중 | `POST /api/partner/v1/mt/templates` | 템플릿 등록·검수 신청 |
| 준비 중 | `GET /api/partner/v1/mt/quota` | 남은 발송 한도 |
| 준비 중 (v2) | 자유 본문·광고성·대량 발송 | 별도 계약 |

# 3. MO 수신 (문자 받기)

## 3-1. 두 가지 방식을 함께 준다

사회복지기관 서버 사정에 따라 고를 수 있게 합니다.

- **웹훅(push)** — 실시간. 수신 서버가 있어야 한다.
- **조회(pull)** — 수신 서버 없이 주기적으로 가져간다. 지금 결제 API 와 같은 방식.

## 3-2. 엔드포인트

| 상태 | 메서드·경로 | 설명 |
|---|---|---|
| 준비 중 | `GET /api/partner/v1/mo/messages` | 수신 문자 조회(커서 페이징) |
| 준비 중 | `GET /api/partner/v1/mo/messages/{id}` | 수신 문자 1건 |
| 준비 중 | `GET /api/partner/v1/mo/numbers` | 내게 배정된 수신번호·상태 |
| 준비 중 | `POST /api/partner/v1/mo/keywords` | 키워드 라우팅 규칙 등록 |

# 11. 샌드박스 (테스트 모드) ★ 신규

## 11-1. 원칙

**테스트 키로 하는 모든 호출은 실제 세계에 아무 영향이 없어야 합니다.** 문자가 나가지 않고, 돈이 빠지지 않고, 정산에 잡히지 않습니다.

## 11-2. 설계 결정이 하나 필요합니다 ★

테스트 데이터를 **① 같은 테이블에 `isTest` 플래그로 둘지**, **② 별도 공간(스키마/DB)으로 둘지** 입니다.

- ①은 개발이 빠르지만, **통계·정산·한도 집계에서 테스트 건을 빠뜨리지 않고 제외해야** 합니다. 한 군데라도 빠지면 정산에 테스트 금액이 섞입니다.
- ②는 안전하지만 마이그레이션과 운영이 무거워집니다.

지금 코드 구조(집계 쿼리가 여러 곳에 흩어져 있음)를 보면 **①로 가되, "테스트 건은 집계에서 제외"를 테스트로 강제**하는 방식을 권합니다.

## 11-3. 엔드포인트 (테스트 키로만 호출 가능)

| 준비 중 | `POST /api/partner/v1/sandbox/charges/{no}/succeed` | 모의 결제 성공 처리 |
| 준비 중 | `POST /api/partner/v1/sandbox/charges/{no}/fail` | 모의 결제 실패(사유 지정) |
| 준비 중 | `GET /api/partner/v1/sandbox/outbox` | 모의 발송함 — 나갔을 문자 전문 확인 |

**엔드포인트 6종 (전부 제공 중)**
`POST /mt/messages` · `GET /mt/messages` · `GET /mt/messages/{id}` · `GET /mt/templates` · `POST /mt/templates` · `GET /mt/quota`

**설계상 짚어 둘 것**
- 발송 요청에 `Idempotency-Key` 헤더가 **필수**다. 재시도로 같은 문자가 두 번 나가면 후원자는 그것을 스팸으로 받아들인다. 같은 키로 다시 보내면 처음 결과를 그대로 돌려준다.
- `payerRef` 는 HMAC 이라 되돌릴 수 없어 `payer_merchant_link.payer_ref` 에 저장해 찾는다. 기능 이전에 만들어진 옛 행은 비어 있으므로, 못 찾으면 그 사회복지기관의 빈 행만 한 번 채우고 다시 찾는다(자기 치유). 결제 경로는 건드리지 않았다.

### 4단계 — 웹훅

사회복지기관 서버로 이벤트를 밀어 준다. 설계에서 지킨 두 가지가 핵심이다.

- **발행이 본 흐름을 막지 않는다.** `emitMerchantEvent` 는 전송 건을 적재만 하고, 전송은 따로 돈다. 어떤 경우에도 예외를 밖으로 던지지 않는다 — 사회복지기관 서버가 죽어도 결제 성공 처리가 실패하면 안 되기 때문이다.
- **중복 도착을 전제로 한다.** 실패 시 재전송하므로 같은 이벤트가 두 번 갈 수 있다. 받는 쪽이 `eventId` 로 걸러야 하며 문서에 그렇게 적었다.

재시도는 30초 → 2분 → 10분 → 1시간 → 6시간. 다 쓰면 DEAD 가 되고 수동 재전송으로 되살릴 수 있다. 배치는 `/api/cron/webhooks`.

수신 URL 은 **https 만** 받고 내부망 주소는 거부한다(우리 서버가 내부망을 긁는 통로가 되는 것을 막기 위해서다). 서명은 `{timestamp}.{eventId}.{본문 원문}` 의 HMAC-SHA256 이며, 문서에 Express 검증 예제를 넣었다.

실제로 발생하는 이벤트는 6종(charge.succeeded / charge.failed / mo.received / shipment.updated / product.stock_low / payer.linked). 나머지 4종은 구독은 되지만 아직 발행 지점이 없고, 레지스트리의 `live: false` 로 표시해 문서가 그대로 읽는다.

### 5단계 — 상품 동기화 · 후원자 연결

- 상품은 **삭제하지 않는다.** DELETE 는 판매 중지(보관 처리)다. 지난 결제가 상품을 참조하므로 지우면 주문 내역이 깨진다.
- 일괄 동기화는 `sku` 를 열쇠로 쓴다. `archiveMissing` 을 주면 목록에 없는 상품을 내린다.
- 후원자는 `payerRef` 로만 다룬다. 휴대폰 원문은 어떤 응답에도 나가지 않는다. 사회복지기관 회원 ID 를 연결해 두면 회원 상세 화면에 결제 이력을 그대로 붙일 수 있다.

### 6단계 — 정산·통계·OpenAPI

정산 회차·상세·CSV·수수료율, 일별·상품별·문자 집계. 그리고 **`GET /api/partner/v1/openapi.json`** 을 레지스트리에서 생성한다. 손으로 쓰지 않으므로 문서 화면과 규격 파일이 어긋날 수 없고, 준비 중 항목도 `x-status` 로 구분해 함께 담는다. 인증 없이 열린다(연동 시작 전에 도구에 먼저 넣어 보는 경우가 많다).
