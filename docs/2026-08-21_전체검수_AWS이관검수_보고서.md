# 1. AWS 실서버 이관 — DB 형식 적합성 (가장 먼저 물어보신 부분)

## 결론: **DB 형식은 맞춰져 있습니다. 형식 때문에 이관이 막히는 일은 없습니다.**

걱정하신 "DB 형식이 다르면 어렵다"는 상황(예: 로컬은 SQLite/MySQL인데 운영은 PostgreSQL, 또는 DB 전용 함수·확장에 묶여 있는 경우)은 **해당되지 않습니다.** 실행으로 확인한 근거는 아래와 같습니다.

| 점검 항목 | 결과 | 확인 방법 |
|---|---|---|
| DB 엔진 일치 | PostgreSQL 16 → RDS/Aurora PostgreSQL **동일 엔진** | `schema.prisma` provider, `migration_lock.toml` |
| 빈 DB 재생 | 마이그레이션 11개 **전량 성공** | 신규 DB 생성 후 `migrate deploy` 실행 |
| PostgreSQL 확장 의존 | **0건** (`CREATE EXTENSION` 없음) | 마이그레이션 SQL 전수 검색 — RDS는 확장 설치가 제한되는데 하나도 안 씁니다 |
| 시각 컬럼 형식 | **127개 전부 `timestamp with time zone`**, naive timestamp 0건 | 실제 DB `information_schema.columns` 조회 |
| 금액 형식 | `bigint` 31개 + 요율 `numeric` — **금액에 부동소수점 0건** | 동상. `double precision` 2개는 TTS 속도·볼륨뿐 |
| ID 생성 | 앱에서 ULID 생성 → `gen_random_uuid()` 등 **DB 함수 의존 0** | 스키마 전수 |
| 서버 타임존 의존 | **없음.** 화면 시각은 `formatKst()` 가 +9h 오프셋 연산 | `src/lib/datetime.ts` — AWS 컨테이너 기본 UTC여도 표시가 틀어지지 않습니다 |
| 커넥션 풀러 호환 | `pg_advisory_xact_lock` (**트랜잭션 스코프**) 사용 | RDS Proxy·PgBouncer transaction pooling 과 호환. 세션 스코프였다면 깨졌을 부분입니다 |
| 원장 무결성 트리거 | 표준 plpgsql만 사용, 신규 DB에도 정상 생성 | 트리거 존재 확인 |

즉 **"스키마를 새로 짜야 한다"는 상황은 아닙니다.** 다만 이관 전에 반드시 처리해야 할 항목 6가지가 나왔습니다.

## AWS 이관 전 반드시 처리할 항목

### A-1. 스키마 드리프트 3건 — 배포하면 인덱스가 조용히 사라집니다 【높음】

`prisma migrate diff` 실행 결과(종료코드 2 = 차이 있음):

```
[*] Changed the `donation` table
  [-] Removed index on columns (creator_id, status)
  [-] Removed index on columns (paid_at)
[*] Changed the `mt_outbound_message` table
  [-] Removed index on columns (creator_id, created_at)
```

`20260819100100_guards_and_indexes/migration.sql:53-55` 에서 raw SQL로 만든 인덱스 3개가 `schema.prisma` 에는 선언돼 있지 않습니다. 이 상태에서 **다음번에 `prisma migrate dev` 를 한 번이라도 돌리면 이 3개를 DROP 하는 마이그레이션이 자동 생성**되고, 그게 AWS에 배포되면 후원 목록·정산 조회의 핵심 인덱스가 사라집니다. 데이터 건수가 커진 운영 DB에서 발견하면 늦습니다.

→ 조치: `schema.prisma` 해당 모델에 `@@index([creatorId, status])`, `@@index([paidAt])`, `@@index([creatorId, createdAt])` 3줄 추가. (SQL 변경 불필요, 5분)

### A-2. `DIRECT_DATABASE_URL` 이 배선돼 있지 않습니다 【높음】

`.env.example`, `src/server/db.ts:8`, `src/app/admin/system/page.tsx:250` 세 곳에 "마이그레이션은 DIRECT_DATABASE_URL 로 수행한다"고 쓰여 있는데, 실제 `prisma.config.mjs` 는 `process.env.DATABASE_URL` 만 읽습니다. `env.directDatabaseUrl` 값도 어디서도 소비되지 않습니다.

AWS에서 `DATABASE_URL` 을 RDS Proxy로 잡으면 **마이그레이션이 풀러를 통과**하게 됩니다. DDL + advisory lock 조합이라 실패하거나 중간에 멈출 수 있습니다.

→ 조치: `prisma.config.mjs` 의 datasource url 을 `process.env.DIRECT_DATABASE_URL || process.env.DATABASE_URL` 로 변경.

### A-3. 업로드 이미지가 서버 로컬 디스크입니다 — 이관의 실질적 선행 조건 【높음】

`src/server/uploads.ts:10` → `path.join(process.cwd(), 'var', 'uploads')`.

- ECS/Fargate/Elastic Beanstalk 에서 **인스턴스를 2대 이상 띄우면** A에 올린 이미지가 B 요청에서 404
- **재배포·오토스케일 축소 시 업로드 이미지 전량 소실** (컨테이너 파일시스템은 휘발성)

지난번에 "지금은 서버 저장, S3는 추후"로 정하셨는데, **AWS 이관 시점에는 S3가 선택이 아니라 필수**입니다. 다행히 교체 지점은 `uploads.ts` + `/api/upload` + `/api/media` 3개 파일로 이미 격리돼 있어 작업량 자체는 작습니다.

### A-4. 원장 append-only 트리거를 앱 계정이 끌 수 있습니다 【중간】

정산 원장은 트리거로 UPDATE/DELETE를 막고 있지만, **테이블 소유자는 `ALTER TABLE ... DISABLE TRIGGER` 로 해제할 수 있습니다.** 앱이 마이그레이션까지 같은 롤로 돌리면 앱 롤이 곧 소유자입니다.

→ 조치: RDS에서 마이그레이션 롤(소유자)과 앱 런타임 롤(DML만)을 분리. 회계 감사 대응에도 이 분리가 필요합니다.

### A-5. `output: 'standalone'` 미설정 【중간】

`next.config.ts` 에 없습니다. 컨테이너 이미지에 `node_modules` 전체가 들어가 이미지가 수백 MB 커지고 콜드스타트가 느려집니다. 한 줄 추가로 해결됩니다.

### A-6. 헬스체크가 매 호출마다 Redis에 씁니다 【낮음】

`/api/health` 가 `kv.set` 을 수행합니다. ALB 헬스체크 주기(기본 30초 × 인스턴스 수 × AZ)만큼 불필요한 쓰기가 발생합니다. 읽기 전용 ping 으로 바꾸는 편이 좋습니다.

**참고(정상):** `ALLOW_INMEMORY_FALLBACK` 기본값이 `true` 이지만, `assertBootSafety()` 가 운영 환경에서 이 값을 검사해 기동을 중단시킵니다(`src/lib/env.ts:195`). 오버레이 버스도 Redis pub/sub 이 붙어 있어 다중 인스턴스에서 정상 동작합니다. 이 둘은 문제없습니다.

# 2. 치명 결함 4건

## CRIT-1. 결제 결과 미확인(UNKNOWN) 건이 즉시 "실패"로 덮어써집니다

**위치:** `src/server/services/donation-flow.ts:554-566`

타임아웃 후 거래결과조회까지 실패하면 555행에서 트랜잭션 상태를 `UNKNOWN` 으로 올바르게 기록합니다. 그런데 **바로 아래 564행이 조건 없이 `FAILED` 로 덮어씁니다.**

```
554:  failure = { code: 'UNKNOWN', ... };
555:  await ...update({ data: { status: 'UNKNOWN' } });   ← 올바른 기록
...
564:  data: { status: 'FAILED', ... }                      ← 무조건 덮어씀
```

**실제로 벌어지는 일:**
- 후원자 통장에서 돈이 빠져나갔는데 앱은 "결제 실패"로 기록 → 원장 분개 없음 → **사회복지기관에게 정산되지 않음**
- 후원자에게 "결제에 실패했습니다" 문자 발송 (돈은 나갔는데)
- `registerFailure()` 가 실패 카운터를 올려 **정상 후원자가 계정 잠금**
- **`/admin/payments` 의 "확인 필요" 큐가 영구히 0건** — 이 큐는 `status IN ('UNKNOWN','TIMEOUT')` 으로 조회하는데(`admin/payments/page.tsx:155`) 둘 다 FAILED로 덮이므로 관리자가 수동 대사할 수단 자체가 없습니다

실 결제(헥토) 연동 직후 첫 타임아웃에서 바로 터지는 문제이고, 사후 복구가 가장 어려운 유형(돈은 나갔고 기록은 없음)입니다. **오픈 전 최우선 수정 대상입니다.**

## CRIT-2. 주민등록번호 평문 CSV를 READ_ONLY 관리자가 받을 수 있습니다

**위치:** `src/app/api/admin/settlements/withholding/route.ts:24-27`

```ts
const admin = await requireAdmin();
if (admin.adminPermission === 'SUPPORT') { return 403; }
```

`SUPPORT` 만 막습니다. 그런데 `AdminPermission` 의 **기본값이 `READ_ONLY`** 입니다(`schema.prisma:347`). 즉 갓 만든 조회 전용 관리자 계정이 `/api/admin/settlements/withholding` 을 직접 호출하면 **복호화된 주민등록번호 전체 명단**을 CSV로 받습니다. 감사 로그도 남지 않습니다.

주민번호는 "원천징수 신고 목적으로만 쓰고 신고 후 파기한다"고 사회복지기관에게 안내하고 받은 정보입니다. 이 안내와 실제 접근통제가 어긋나 있습니다.

→ 조치: `FINANCE` / `SUPER_ADMIN` **화이트리스트**로 전환 + 다운로드 시 `writeAudit()` 기록(누가·언제·몇 건).

## CRIT-3. 계좌번호·실명 CSV가 `requireAdmin()` 만으로 열립니다

**위치:** `src/app/api/admin/settlements/payout/route.ts:25`

```ts
await requireAdmin();   // 권한 등급 검사 없음
```

내려주는 내용은 **복호화된 계좌번호 + 예금주 실명 + 금액** 입니다. 관리자 등급 무관하게 누구나 받을 수 있고, 역시 감사 로그가 없습니다. CRIT-2와 같은 조치가 필요합니다.

## CRIT-4. MO 번호 라우팅 충돌 — 후원이 엉뚱한 사회복지기관에게 들어갑니다

**위치:** `prisma/schema.prisma` `CreatorMoNumber.@@unique([phoneNumber, keyword])` / `src/app/actions/admin/transactions.ts:35` / `src/server/services/donation-flow.ts:135-152`

같은 전화번호에 **DEDICATED(전용, keyword=NULL)** 행과 **SHARED_PREFIX(대표번호+키워드)** 행이 동시에 존재할 수 있습니다. 중복 검사가 `(phoneNumber, keyword)` 조합이라 keyword 값이 다르면 통과하기 때문입니다.

그리고 `routeCreator()` 는 **DEDICATED를 무조건 먼저** 조회합니다(135행). DEDICATED가 하나라도 매칭되면 키워드를 아예 보지 않고 즉시 반환합니다.

→ 그 대표번호를 공유하던 **모든 사회복지기관의 후원이 전부 DEDICATED 사회복지기관 1명에게 들어갑니다.** 후원자는 정상 문자를 보냈고 결제도 정상이라 아무도 이상을 눈치채지 못합니다.

**추가로**, DB 유니크가 이걸 막아주지도 못합니다. PostgreSQL은 NULL을 서로 다른 값으로 취급하므로 DEDICATED 행(keyword NULL)은 몇 개든 들어갑니다. 실제 재현했습니다:

```sql
CREATE UNIQUE INDEX ON t(a,b);
INSERT INTO t VALUES ('0501234', NULL);
INSERT INTO t VALUES ('0501234', NULL);   -- 통과. 2행 존재
```

같은 마이그레이션 파일 안에서 `banned_word` 는 **이 함정을 알고 부분 유니크 인덱스로 이미 해결**해 뒀습니다(`... ON banned_word(word) WHERE creator_id IS NULL`). MO 번호에만 같은 처리가 빠졌습니다.

→ 조치: `CREATE UNIQUE INDEX ... ON creator_mo_number(phone_number) WHERE keyword IS NULL` 부분 인덱스 추가 + 번호 등록 시 "같은 번호에 모드 혼재 금지" 검사.

# 5. 정상 확인된 부분

검수 과정에서 **문제없음이 확인된 항목**도 함께 남깁니다. 여기는 손대지 않아도 됩니다.

- **문자후원 상태 기계** — PENDING_PAYMENT → PAYMENT_SUCCESS → SETTLEMENT_PENDING → SETTLED 전이와 상태 로그가 일관됩니다
- **멱등성** — `(scope, key)` UNIQUE 로 MO 중복 수신·중복 결제 요청을 차단합니다
- **개인정보 3분리** — 전화번호·계좌·주민번호 모두 해시 + 암호화 + 마스킹으로 분리 저장, 화면에 원문 노출 경로 없음
- **금칙어** — 차단/마스킹/표시 3방식, 스코프 격리, 우회표기(`바 보`, `바.보`) 대응, 오탐 방지 모두 정상 (유닛 검증)
- **CSV 인젝션 방어** — `=`, `+`, `-`, `@` 시작 셀 이스케이프 처리됨
- **업로드 검증** — 매직바이트로 실제 형식 판정(확장자·MIME 위조 무력화), 5MB 제한, 랜덤 파일명, 동일출처 검사
- **헥토 EzAuth 호스트 분리** — 결제창(`ezauth`)과 서버 API(`ezauthapi:8081`) 가 별도 상수로 분리돼 있습니다. 합쳐지면 전건 실패하는 부분인데 정확히 처리돼 있습니다
- **부팅 안전장치** — `instrumentation.ts` 가 운영 환경의 위험 설정(기본 시크릿, 인메모리 폴백, MO IP 미설정)을 잡아 기동을 중단시킵니다
- **오버레이 다중 인스턴스** — Redis pub/sub + 중복 재생 방지 처리됨
- **한도 정책 시행일** — `effectiveFrom <= now < effectiveTo` 필터로 예약 정책의 조기 적용을 막습니다
