## 0. 총평

핵심 결제·정산·개인정보 설계(멱등 3중 방어, 확인링크 원자적 1회 소비, append-only 원장 + DB 트리거, 전화번호 3분리 저장, 1회용 비밀값 해시 저장)는 견고합니다. 그러나 이번 감사에서 **운영을 즉시 마비시키는 치명 결함 4건**과, **금전·개인정보에 직접 영향을 주는 높음 결함 다수**가 확인되었습니다. 특히 두 건은 실제 실행으로 재현했습니다.

- **감사로그가 금액이 포함되면 무조건 실패** → 환불·정산·한도 등 돈을 다루는 관리자 액션이 "오류"로 표시되고 기록이 안 남음 `[검증됨]`
- **정산 계좌를 "인증 완료"로 만드는 코드가 아예 없음** → 원장에 잔액이 쌓여도 정산 요청이 영구 불가 `[검증됨]`

여러 감사관이 **독립적으로 중복 지적**한 항목(신뢰도 높음)은 각 항목에 `★중복지적` 으로 표시했습니다.

## 1. 치명 (P0 — 운영 차단 / 금전 사고 직결)

### C-1. 감사로그 저장이 BigInt에서 예외 → 금액 관련 모든 관리자 액션이 실패로 표시 `[검증됨]`
- 위치: `src/server/auth.ts:writeAudit` (`beforeValue/afterValue` 를 Json 컬럼에 저장)
- 호출부: `admin/transactions.ts:46,137,193`(monthlyCost·amount), `admin/accounts.ts`(minAmount/maxAmount/donationAmount), `admin/settlement.ts`, `admin/policy.ts` 등
- 내용: `after: { amount: 3000n }` 처럼 BigInt가 담긴 객체를 Prisma Json 컬럼에 저장하면 `JSON.stringify` 단계에서 `TypeError: Do not know how to serialize a BigInt` 가 발생합니다. 실행 재현 결과 `prisma.adminAuditLog.create()` 가 예외를 던지는 것을 확인했습니다.
- 실패 시나리오: 관리자가 환불 "승인" → PG 취소·원장 반대분개는 이미 완료 → `writeAudit`에서 예외 → `run()`이 잡아 화면에 "처리 중 오류가 발생했습니다" 표시. 관리자는 실패로 알고 **재클릭**(→ C-3 이중환불로 연결), 감사로그에는 아무 기록도 남지 않습니다.
- 영향 범위: MO 번호 등록, 후원자 한도 저장, 1건 후원금 범위 변경/일괄적용, 정산 상태 변경, 수수료·한도 정책 저장, 환불 승인/직접환불 등 금액을 audit에 넣는 액션 전부.
- 권고: `writeAudit` 내부에서 BigInt→string 정규화(`JSON.parse(JSON.stringify(v, (_,x)=>typeof x==='bigint'?x.toString():x))`) 후 저장. 미지정 시 `null` 대신 `Prisma.DbNull` 사용.

### C-2. 정산 계좌를 `verified=true`로 전환하는 경로가 존재하지 않음 → 정산 구조적 불가 `[검증됨]`
- 위치: `src/server/services/settlement.ts:createSettlementRequest`(인증 계좌 요구), `src/app/actions/studio.ts:saveSettlementAccountAction`(항상 `verified:false` 저장)
- 내용: 전 코드베이스에서 `settlementAccount` 의 `verified` 를 `true`로 **쓰는** 코드가 없습니다(검색 결과는 모두 `select`). 관리자 계좌 관리 액션(`admin/accounts.ts`)에도 계좌 인증 처리가 없습니다.
- 실패 시나리오: 사회복지기관가 계좌 등록 → 관리자 화면엔 "미인증" 배지만 있고 전환 버튼 없음 → 정산 요청 시 항상 "정산 계좌 인증이 완료되지 않았습니다"로 실패. 원장 잔액이 아무리 쌓여도 출금 불가.
- 권고: 관리자용 `verifySettlementAccountAction`(FINANCE 권한 + `writeAudit`) 신설. 계좌 변경 시 자동 미인증 전환(현 동작)은 유지.

### C-3. 환불 승인에 상태 가드·직렬화 락 부재 → 이중 환불·이중 반대분개 `★중복지적(후원/정산/관리자)`
- 위치: `src/app/actions/admin/transactions.ts:approveRefundAction`, `src/server/services/refund.ts:approveRefund`
- 내용: `rejectRefundAction`은 `status !== 'REQUESTED'` 를 검사하지만 `approveRefundAction`엔 없음. `approveRefund`도 `DONE`만 조기반환하고 `REJECTED/FAILED` 재승인을 막지 않으며, `withAdvisoryLock`·조건부 UPDATE도 없음.
- 실패 시나리오: (a) 거절된 환불을 다른 탭에서 승인 → PG 취소 실행 + 환불 분개 추가. (b) 이중 클릭/동시 처리 → `adapter.cancel` 2회, `postRefundSettlement` 2회 → append-only 원장에 환불 분개 중복(되돌리기 불가) + `rollbackCounters` 2회로 카운터 음수화(한도 추가 개방). C-1과 결합 시 관리자가 "오류"로 오인해 재클릭하며 발생 확률이 높음.
- 권고: `approveRefund` 전체를 `$transaction + withAdvisoryLock('refund:'+id)` 로 감싸고 진입 시 `status==='REQUESTED'` 만 허용.

### C-4. 확인대기(PENDING_CONFIRM) 건이 한도에 예약되지 않아 일/월 한도 무제한 우회 `[추정]`
- 위치: `src/server/services/limits.ts:checkLimits`(카운터만 읽음), `donation-flow.ts:commitCounters`(결제 성공 시에만 증가), `executePayment`(결제 직전 한도 재검사 없음)
- 내용: CONFIRM_LINK 모드에서 카운터는 결제 성공 시점에만 증가. 확인 대기 중인 건은 어떤 한도에도 안 잡히고, `executePayment`는 한도를 다시 확인하지 않음.
- 실패 시나리오: 일 한도 10만원 후원자가 60초마다 5만원 문자 3건씩 반복 → 매번 카운터 0이라 전부 통과 → 확인 링크 30장 발급 → 순차 클릭 시 150만원 결제(한도 15배).
- 권고: PENDING_CONFIRM 생성 시 예약(pending) 카운터 증가(만료/실패 시 롤백), 또는 `executePayment` 진입 직후 `checkLimits` 재실행.

- 내용: `where:{active:true}` + `orderBy effectiveFrom desc`로 첫 행 선택. `effectiveFrom<=now`, `effectiveTo` 조건 없음. "9/1부터" 예약 등록이 즉시 적용되고 원장에 잘못된 수수료가 확정 기록(append-only라 반대분개로만 정정).
- 권고: `effectiveFrom:{lte:now}` + `OR:[{effectiveTo:null},{effectiveTo:{gt:now}}]` 추가.

### H-13. 환불 수수료 환입을 "현재" 정책으로 재계산 → 원 분개와 금액 어긋남 `★중복지적(후원/정산)`
- 위치: `refund.ts:70`(`calculateFees(creatorId, refund.amount)`), `settlement.ts:postRefundSettlement`
- 내용: 원 거래 확정 수수료(`donation.pgFee/platformFee`)를 쓰지 않고 환불 시점 정책으로 재계산. 요율 변경 후 환불하면 사회복지기관 잔액에 설명 불가능한 잔여 발생. `/admin/fees`의 "소급 안 됨" 안내와 모순.
- 권고: `postRefundSettlement`가 `donationId`의 기존 분개 합계를 환입하도록 변경.

### H-14. `vatIncluded`/`smsCost`가 정산 계산에 미반영(입력·표시만 됨)
- 위치: `settlement.ts:calculateFees`(pgFee/platformFee만 사용), schema/`admin/fees`/`studio/settlement`에서 입력·표시
- 내용: 문자 원가·부가세 필드가 DB·UI엔 있으나 어떤 계산에도 안 쓰임. 사회복지기관에게 고지한 명세와 실제 차감 불일치.
- 권고: 계산에 반영하거나(별도 entryType 권장) 스키마·UI에서 제거.

### H-15. 정산 요청 목록에 페이지네이션(skip) 없음 → 오래된 요청 처리 불가 `★중복지적(정산/관리자)`
- 위치: `admin/settlements/page.tsx`(요청 목록 `take`만, `Pager`는 원장에만 연결)
- 내용: PAGE_SIZE 초과 요청은 화면에서 밀려나 승인/반려 접근 불가. 요청시각 내림차순이라 **가장 오래 기다린 건**부터 잠김. 해당 금액은 `pending`으로 사회복지기관 `available`에서 영구 차감.
- 권고: 요청/원장 목록에 각각 `skip`+별도 Pager, 기본 정렬 오래된 순.

### H-16. `/api/health`가 무인증으로 DB/Redis 원문 에러·운영 설정 노출
- 위치: `src/app/api/health/route.ts`
- 내용: 인증·rate limit 없이 예외 메시지(호스트·포트·DB명·사용자명 포함) + `productionWarnings` + provider 모드 반환. `error.tsx`가 이 URL을 사용자에게 링크로 안내.
- 권고: 공개 응답은 `{ok:boolean}`로 축소, 상세는 관리자 세션/내부망 전용.

### H-17. 지급 시점에 정산 가능금·계좌 인증 재검증 없음 → 승인 후 환불 시 초과 지급
- 위치: `settlement.ts:markSettlementPaid`
- 내용: 요청 시점에만 `available` 검사. 승인~지급 사이 환불/조정 미반영. `available`은 음수면 0으로 clamp되어 화면에서 초과 상태가 숨겨짐.
- 권고: `markSettlementPaid` 내부에서 요약 재조회 후 `balance>=req.amount` + 계좌 verified 재검증.

### H-18. 정산 요청 상태 전이 TOCTOU + `markSettlementPaid`의 APPROVED 미검증 `★중복지적(정산/관리자)`
- 위치: `admin/settlement.ts:updateSettlementRequestStatus`, `settlement.ts:markSettlementPaid`
- 내용: before 조회와 update가 별 트랜잭션, update에 상태 조건 없음. `markSettlementPaid`는 `PAID`만 검사하고 `APPROVED` 재확인 안 함(락은 잡지만 검증 없어 무의미). 동시 "지급"·"반려" 시 반려 건에 실제 지급 가능.
- 권고: 전이를 `$transaction+advisory lock`으로 감싸고 `updateMany({where:{id,status:expectedFrom}})`의 count로 충돌 판정, `markSettlementPaid`에서 `status!=='APPROVED'` throw.

### H-19. 캘린더 `PAID_STATUSES`가 공용 상수와 달라 월 합계 과소집계 `★중복지적(정산/앱전반)`

## 5. 정상 확인된(잘 설계된) 사항

1. MO 재전송 3중 방어(providerMessageId·moMessageId·idempotency_key 유니크 + 경합 폴백) — 테스트로 검증됨.
2. 확인 링크 원자적 1회 소비(`updateMany where usedAt:null` + count 확인), 토큰은 HMAC 해시만 저장.
3. 결제 성공 건만 송출, 유튜브/오버레이 실패가 결제 결과를 뒤집지 않음.
4. 정산 원장 append-only(DB 트리거로 UPDATE/DELETE 차단), 지급/요청 advisory lock 직렬화 — 테스트 검증됨.
5. 개인정보 3분리(phoneHash/phoneEnc/phoneMasked) + 계좌 원문 미저장 + 로그 마스킹 + 빌키 승인 직전에만 복호화.
6. 세션 토큰 CSPRNG 32B + DB엔 HMAC 해시만, 탈퇴 계정 재로그인·재가입 차단 정상.
7. 미구현 연동(소셜·헥토·KMS)을 성공으로 위장하지 않고 예외 처리, SAFE_MODE가 실결제를 mock 강제.
8. 최고관리자 안전장치(본인 권한변경·마지막 SUPER_ADMIN 강등·사회복지기관 겸직·비활성 승격 금지) 서버 검사.
9. 즉시형 결제(DIRECT_TRIGGER)가 서면승인 플래그로 이중 봉인.
10. 시드가 실제 파이프라인(handleMoInbound→executePayment→requestRefund)으로 데이터 생성.

## 6. 권장 수정 순서(제안)

1. **P0 즉시**: C-1(감사로그 BigInt) → C-2(정산 계좌 인증) → C-3(환불 이중처리) → C-4(확인대기 한도).
2. **P1 보안·금전**: H-1/H-2(운영 시크릿 fail-open), H-3(사회복지기관 상태검사), H-4/H-6(웹 후원 멱등·마스킹), H-5(웹훅), H-7(로그인 CSRF), H-8(인증번호), H-11(후원자 차단 무효), H-12~H-19(정책·정산 정합).
3. **P2**: 원장 트랜잭션·유니크(M-1), 조정분개 UI(M-2), 무인증 액션(M-3), 권한 가드(M-27/M-4), 확인링크 정리(M-5/M-6) 등.
4. **P3**: 용어·자산·접근성·페이지네이션 정리.
