## 1. 현재 프로젝트 분석

### 1-1. 코드베이스 현황
현재 접근 가능한 소스가 없어 **그린필드(신규 구축)** 상태입니다. 셀러브릭스·사주메이트에서 재사용을 검토하려던 영역은 다음과 같으며, 소스가 연결되면 즉시 재분석하여 본 문서를 개정합니다.

| 재사용 후보 | 기브싸인에서의 대응 | 소스 없을 때의 대체안 |
|---|---|---|
| 디자인 시스템 / 공통 컴포넌트 | 버튼·카드·모달·폼·토스트 | Tailwind 기반 기브싸인 자체 디자인 토큰 신규 정의 |
| 인증 (회원/소셜/본인인증) | 후원자·사회복지기관·관리자 3-롤 | 세션 기반 자체 인증 + 본인인증 어댑터 |
| 관리자 프레임 (LNB, 권한, 감사로그) | 통합 관리자 23개 메뉴 | 신규 구축 (RBAC + AuditLog) |
| 정산 모듈 | 후원 전용 원장으로 재설계 | 신규 구축 (복식 원장 구조) |
| 반응형 레이아웃 | 모바일 우선 + PC 중앙 정렬 | 신규 구축 |

### 1-2. 기존 자산 부재로 인한 영향
- 초기 1~2주는 **디자인 시스템·인증·관리자 뼈대**를 새로 만드는 비용이 발생합니다.
- 반대로 레거시 제약이 없어 **결제·정산 원장 구조를 후원 도메인에 최적화**해 설계할 수 있습니다. 문자후원은 일반 커머스와 거래 단위·환불 규칙·정산 주기가 달라, 오히려 신규 설계가 유리한 영역입니다.

### 1-3. 도메인 특수성 (일반 커머스와의 결정적 차이)
1. **결제 트리거가 웹이 아니라 문자(MO)** — 사용자가 결제 화면을 보지 않은 상태에서 출금이 발생할 수 있음. 국내 PG·금융사 심사에서 가장 민감한 지점.
2. **1건 단가가 작고 건수가 많음** — 결제 수수료 비중이 크고, 중복 결제 1건의 신뢰 훼손이 매우 큼.
3. **결제 성공과 방송 노출이 별개의 성공/실패 축** — 상태를 한 축으로 합치면 반드시 사고가 납니다.
4. **실시간성 요구** — 문자 수신 → 방송 노출까지 목표 3초 이내.

## 2. 기브싸인 적용 가능 범위

### 2-1. 계약 없이 지금 바로 구현 가능 (Mock/Adapter)
- 메인페이지, 사회복지기관 코드 검색(`/c/{code}`), 반응형 레이아웃, 디자인 시스템
- 회원가입·로그인·권한(후원자/사회복지기관/관리자)
- 사회복지기관 코드·MO 번호 재고 관리(관리자 화면 포함)
- MO 수신 Webhook **수신 엔드포인트 + 서명 검증 골격** (Mock 발신기 포함)
- MT 발송 큐 + 발송 로그 (Mock 프로바이더)
- 결제 어댑터 인터페이스 + Mock PG (성공/실패/타임아웃/중복 시나리오 재현)
- 후원 거래 상태머신 14단계 전체
- 한도·연속발송·이상거래 정책 엔진
- 금칙어·개인정보 감지 필터
- 오버레이(WebSocket/SSE) + 회오리 애니메이션 + 브라우저 TTS 시험 재생
- 정산 원장, 수수료 정책, 정산 요청 흐름
- 통합 관리자 23개 메뉴, 감사로그
- 자동 테스트 20개 시나리오

### 2-2. 계약·키 확보 후 실연동 가능
- MO 수신 번호 배정 및 실제 Webhook
- MT 실제 발송 (발신번호 사전등록 필요)
- 헥토파이낸셜 내통장결제 계좌등록·승인·조회·취소
- Google OAuth + YouTube Data API 라이브 채팅 등록
- 상용 TTS (자연스러운 한국어 음성)
- 생성형 이미지 에셋

### 2-3. 별도 인프라가 필요해 후순위로 분리
- RTMPS Ingest / HLS 자체 방송 / 유튜브 동시송출
  → 웹 애플리케이션과 **완전히 다른 인프라**(미디어 서버, 대역폭 과금)입니다. MVP에서는 **OBS·PRISM 브라우저 소스 오버레이 방식**만 적용하고, 자체 방송은 4단계로 분리하는 것을 강력히 권장합니다.

### 2-4. 적용 범위에서 조정을 제안하는 항목
| 원안 | 조정 제안 | 사유 |
|---|---|---|
| `DIRECT_TRIGGER` 기본 지원 | 코드에는 구현하되 **관리자 UI에서 기본 비활성 + 서면승인 등록 없이는 토글 불가** | 금융사 심사·분쟁 리스크. 마스터 프롬프트 5.4항과 동일 방향이며, 잠금 수준을 한 단계 더 높이는 안 |
| 유튜브 메시지에 이모지 | 텍스트 전용 접두사 `[기브싸인 후원]` | 이모지 금지 규칙 + 슈퍼챗 오인 방지 동시 충족 |
| 자체 방송 MVP 포함 | 5단계 중 4단계로 분리 | 비용·일정 리스크 |

## 3. 외부 연동에 필요한 계약과 키

### 3-1. 결제 — 헥토파이낸셜 내통장결제(EzAuth)
공개 개발자문서 기준 확인된 사항입니다.

- 흐름: 결제창에서 **계좌 인증 및 출금이체 등록** → 사회복지기관 서버가 **결제승인 API 호출** → 고객 계좌에서 즉시 출금
- 결제 방식 3종: 일반결제 / 1회차 후 빌키결제 / **0원 인증 후 빌키결제**
  → 기브싸인는 **0원 인증 후 빌키결제**가 정확히 들어맞습니다. 최초 등록 시 0원 인증으로 빌키를 받고, 이후 MO 문자마다 빌키로 승인.
- **중요 제약: 결제인증 완료 후 10분 이내에 결제승인 API를 호출**해야 하며 초과 시 만료
  → `CONFIRM_LINK` 모드의 확인 링크 유효시간을 10분보다 짧게(권장 5분) 설계해야 합니다.
- API 타임아웃 시 **거래결과조회 API로 최종 상태 확인** 필수 (설계에 반영)
- 운영환경 테스트 비용은 사회복지기관 부담 → **테스트베드에서 전 시나리오 선검증**

필요 항목: 사회복지기관 ID(MID), 라이선스/해시키, 암호화 키, 테스트베드 계정, 운영 IP 화이트리스트, 콜백 도메인 등록, **문자 트리거 방식에 대한 서면 승인**

### 3-2. MO 수신 / MT 발송
- MO(수신): 전국대표번호(1522/1544 등) 또는 이동통신사 단축번호 기반 MO 수신 서비스 계약 필요. 사회복지기관 1인당 **고유 수신번호 또는 대표번호+식별코드** 방식 중 선택해야 하며, 번호 재고 비용이 직접적인 원가입니다.
  → **권장: 대표번호 1개 + 사회복지기관별 접두 코드**(예: `TOR8291 응원합니다`) 방식을 병행 지원. 번호 재고 비용을 크게 줄일 수 있어 MVP에 유리합니다. 전용번호 방식은 데이터모델상 동일하게 처리 가능하도록 설계합니다.
- MT(발송): 발신번호 사전등록(KISA), SMS/LMS 단가 계약, 090 수신거부 처리, 야간 발송 규정 확인
- 필요 키: API Key/Secret, Webhook 서명 시크릿, 발신번호, 허용 IP

### 3-3. 유튜브
- Google Cloud 프로젝트, OAuth 2.0 클라이언트(웹), 동의화면 **검증 심사(민감 스코프)**
- 스코프: `youtube.force-ssl` (라이브 채팅 등록에 필요)
- **할당량**: 기본 일일 10,000 units. 라이브 채팅 메시지 등록은 공개 자료 기준 호출당 비용이 높은 편(50 units로 알려져 있으나 공식 표에 라이브 API 비용이 명시되어 있지 않아 **실측 필요**)으로, 이 경우 채널 전체 합산 **하루 약 200건**만 전송 가능합니다.
  → **반드시 실측 후 할당량 증설 신청(Quota Extension)**을 진행해야 하며, 그 전까지는 사회복지기관별 전송 상한과 큐를 두어야 합니다. 이 항목은 서비스 성패에 직결되는 최우선 검증 과제입니다.
- 정책: 외부 결제이므로 Super Chat 표기·색상·배지 모방 금지, 작성자는 연결된 채널/봇 계정임을 후원자에게 사전 고지

### 3-4. TTS
- 상용(자연스러운 한국어 다화자) 또는 자체 호스팅 선택. MVP는 브라우저 SpeechSynthesis로 대체 가능하나 품질 편차가 큼
- 필요 키: 서비스 계정 / API Key, 월 사용량 한도

### 3-5. 자체 방송(4단계)
- RTMPS Ingest 미디어 서버, TLS 인증서, 스트림키 발급 체계, HLS 배포(CDN), 대역폭 과금 계약

### 3-6. 인프라·기타
- AWS 계정, RDS/Aurora PostgreSQL, ElastiCache(Redis), S3, KMS, Secrets Manager, CloudWatch
- 도메인 `givesign.kr` 및 SSL
- 본인인증(휴대폰 실명확인) 사업자 — 미성년자 차단에 필요
- 사업자 신고: 통신판매(중개)업 신고, 개인정보처리방침, 전자금융거래 이용약관

> 모든 키는 환경변수 + AWS Secrets Manager로 관리하며 소스코드·로그·프론트엔드에 노출하지 않습니다.

## 4. 데이터베이스 설계안 (AWS 호환)

### 4-1. 엔진 및 AWS 호환 원칙
- **Amazon Aurora PostgreSQL 호환(권장)** 또는 RDS PostgreSQL 16
- 사용 확장은 RDS/Aurora에서 제공되는 것만 사용: `pgcrypto`, `pg_trgm`, `citext`, `pgaudit`, `pg_stat_statements`
  → TimescaleDB 등 RDS 미지원 확장은 사용하지 않습니다.
- **ID는 애플리케이션에서 생성**(ULID/UUIDv7 문자열)하여 DB 함수 의존 제거 → 마이그레이션·샤딩·리플리카 환경에서 안전
- **모든 시각은 `timestamptz` + UTC 저장**, 표시 시점에만 Asia/Seoul 변환
- **금액은 `BIGINT`(원 단위 정수)**. 부동소수점 금지. 수수료율만 `NUMERIC(10,6)`
- 커넥션 풀은 **RDS Proxy 또는 PgBouncer** 경유 (Prisma 다중 인스턴스 대비)
- 대용량 로그 테이블(`mo_inbound_message`, `mt_outbound_message`, `webhook_log`, `overlay_event`)은 **월 단위 선언적 파티셔닝** + 보관주기 정책
- 읽기 부하(관리자 통계)는 **리드 리플리카**로 분리
- 암호화: 저장 암호화는 KMS, **컬럼 암호화는 애플리케이션 레이어에서 KMS 봉투암호화**(키를 DB에 두지 않음)
- 감사: `pgaudit` + 애플리케이션 `admin_audit_log` 이중화
- 마이그레이션: Prisma Migrate, 모든 변경은 되돌릴 수 있는 순방향 스크립트로 관리

### 4-2. 개인정보·금융정보 저장 규칙
| 데이터 | 저장 방식 |
|---|---|
| 휴대전화번호 | `phone_hash`(HMAC-SHA256, 키는 KMS) + `phone_enc`(KMS 봉투암호화) + `phone_masked`(010-****-1234) 3컬럼 분리. 검색은 해시로만 |
| 계좌번호 | **원문 저장 금지.** `bank_code`, `account_tail4`만 저장 |
| 결제 빌키 | 암호화 저장, 복호화는 결제 워커 프로세스에서만. 로그 출력 금지 |
| OAuth 토큰 | 암호화 저장, 자동 갱신, 화면·로그 노출 금지 |
| 스트림 키 | 해시 저장 + 마스킹 표시, 재발급 시 즉시 폐기 |

### 4-3. 핵심 테이블 (마스터 프롬프트 13항 기준 + 보강)

**계정/사회복지기관**
`user`, `donor_profile`, `creator_profile`, `creator_code`, `creator_mo_number`(상태: `AVAILABLE/ASSIGNED/RESERVED/RECLAIMED`), `creator_setting`

**문자**
`mo_inbound_message`(파티션, `provider_message_id` **UNIQUE**), `mt_outbound_message`(파티션), `webhook_log`(파티션)

**결제**
`payment_registration`, `payment_method_token`, `donation`, `payment_transaction`, `payment_attempt`, `refund`, `idempotency_key`

**정책/리스크**
`donation_limit_policy`, `donation_counter`(일/월 집계, Redis 캐시 + DB 원본), `risk_detection`, `blocked_donor`, `banned_word`

**방송**
`youtube_connection`, `youtube_broadcast`, `youtube_chat_delivery`, `stream_channel`, `stream_key`, `overlay_setting`, `overlay_event`, `tts_setting`

**정산**
`fee_policy`, `settlement_account`, `settlement_ledger`(**append-only, UPDATE/DELETE 금지 — 정정은 반대분개**), `settlement_request`, `settlement_payout`

**운영**
`consent_record`, `terms_version`, `notification`, `admin_user`, `admin_audit_log`, `report`(신고), `system_health`

### 4-4. 중복 결제 방지 설계 (최우선)
4중 방어를 겁니다.

1. `mo_inbound_message.provider_message_id` **UNIQUE 제약** — 사업자 재전송 차단
2. `idempotency_key` 테이블에 `(creator_id, donor_id, provider_message_id)` **UNIQUE** — 거래 생성 멱등
3. 결제 승인 호출 시 **PostgreSQL advisory lock**(후원자 단위)으로 동시성 직렬화
4. PG 호출 시 **사회복지기관 주문번호를 멱등키로 재사용**, 타임아웃 시 반드시 거래결과조회 API로 확정

> 정산 원장은 결제 원장과 분리하되 `donation_id`/`transaction_no`로 추적 가능하게 연결하고, 원장은 어떤 경로로도 UPDATE 하지 않습니다.

## 7. 예상 위험요소

### 7-1. 치명적 (착수 전 확인 필요)
| # | 위험 | 영향 | 대응 |
|---|---|---|---|
| R1 | **MO 문자만으로 계좌 출금** 구조에 대한 금융사·PG 미승인 | 서비스 근간 불가 | 기본값 `CONFIRM_LINK`, `DIRECT_TRIGGER`는 서면승인 등록 시에만 관리자 활성화. 계약 협의를 최우선 진행 |
| R2 | **유튜브 API 할당량** — 라이브 채팅 등록 비용이 커서 하루 수백 건 수준에 묶일 수 있음 | 후원 메시지 미노출 | 1주차에 실측 → 할당량 증설 신청 → 큐·상한·실패 재시도, 실패해도 결제는 유지 |
| R3 | **중복 결제** | 신뢰 붕괴, 환불·민원 | 4중 멱등 방어(4-4항), 전용 회귀 테스트 상시 실행 |
| R4 | **미성년자 결제** — 법정대리인 동의 없는 계약은 취소 가능 | 전액 환불·제재 | 본인인증 기반 성인 확인 필수, 미성년자 등록 차단, 한도 강제 |
| R5 | **정산 자금 보유 구조** — 후원금을 플랫폼이 수취 후 사회복지기관에 지급하면 전자금융거래법상 규제 대상 여부 판단 필요 | 사업 구조 변경 | 착수 전 법률·PG 자문. 하위사회복지기관/에스크로 구조 검토 |

### 7-2. 높음
- **MO 번호 원가** — 사회복지기관별 전용번호는 재고 비용이 선형 증가. 대표번호+코드 방식 병행 설계로 완충
- **문자 지연** — 이통사 구간 지연은 통제 불가. 방송 노출 지연에 대한 사전 고지 필요
- **환불 후 정산 차감** — 이미 지급된 정산분의 환불은 마이너스 원장 처리. 정산 주기·보류금 정책으로 완충
- **슈퍼챗 오인** — 유튜브 정책 위반 시 채널 리스크. 표기·색상 가이드 고정 및 문구 검수
- **개인정보 유출** — 문자 본문에 후원자가 개인정보를 적어 방송에 노출될 위험. 자동 감지·마스킹 필수
- **악성 메시지 방송 노출** — 금칙어 필터 + 지연 노출(수 초 버퍼) + 사회복지기관 즉시 차단 버튼

### 7-3. 보통
- 세무: 사회복지기관 정산의 소득 구분(사업소득 원천징수 vs 세금계산서), 부가세 처리 → 세무 자문 필요
- 자체 방송 인프라 비용
- TTS 품질·비용
- OAuth 동의화면 검증 심사 기간(수 주 소요 가능)
- 발신번호 사전등록 및 야간 문자 발송 규정

## 8. 구현 우선순위

### P0 — 없으면 서비스가 성립하지 않음
1. 후원 거래 상태머신 + 중복결제 방지(멱등성)
2. MO 수신 → 사회복지기관 식별 → 등록 여부 판정 → MT 링크 발송
3. 계좌 등록(0원 인증 빌키) + 동의 이력 저장
4. 결제 승인 / 조회 / 취소 + 타임아웃 확정 로직
5. 한도·연속발송·실패잠금 정책 엔진
6. 사회복지기관 코드 검색 + 후원 페이지 + 메인
7. 정산 원장(append-only)

### P1 — MVP 완료 기준 충족에 필요
8. 사회복지기관 관리자(대시보드·후원내역·문자관리·정산)
9. 통합 관리자(회원·MO번호·거래·환불·한도·수수료·감사로그)
10. 유튜브 OAuth + Live Chat 등록 + 큐
11. OBS/PRISM 오버레이 + TTS + 감사 스티커
12. 금칙어·개인정보 필터, 신고·차단

### P2 — 운영 안정화
13. 이상거래 탐지, 통계, 고객센터, 공지·FAQ, 배너
14. 정산 확정·세무자료·환불 차감 자동화

### P3 — 확장
15. 자체 RTMPS 방송, HLS 재생, 동시송출

다음 항목에 대한 확인을 부탁드립니다. 승인되면 **0단계(기반) + 1단계(Mock MVP)** 부터 착수합니다.
