## 1. 후원 확인 페이지 현황

### 1-1. 진입 경로

메인 화면 공개 셸의 상단/하단 내비게이션에 `후원확인` 항목이 있고, **페이지 이동이 아니라 바텀시트를 여는 방식**이다.

- `src/components/layout/public-shell-client.tsx:57`
  `{ href: '#lookup', label: '후원확인', icon: HeartHandshake, sheet: true }`
- `src/components/layout/public-shell-client.tsx:328`
  `<DonationLookupSheet open={lookupOpen} onClose={() => setLookupOpen(false)} />`

즉 `/lookup` 같은 독립 라우트는 존재하지 않는다. 공개 셸이 렌더되는 모든 화면에서 시트가 **항상 마운트된 채** 열림/닫힘만 토글된다. (이 사실이 아래 2-3의 문제로 이어진다.)

### 1-2. 관련 파일 전체

| 역할 | 경로 | 줄수 |
| --- | --- | --- |
| 화면(바텀시트, 3단계 UI) | `src/components/public/donation-lookup-sheet.tsx` | 275 |
| 서버 액션(인증번호 발송·검증·조회) | `src/app/actions/donation-lookup.ts` | 218 |
| 진입 메뉴 | `src/components/layout/public-shell-client.tsx` | — |
| 문자 발송 어댑터 | `src/server/adapters/mt/index.ts` | 69 |
| 인증 상태 저장소 | `src/server/redis.ts` (Redis / 인메모리 폴백) | — |
| 해시·마스킹·코드생성 | `src/lib/crypto.ts` | — |

### 1-3. 동작 흐름 (구현된 그대로)

```
[phone] 휴대전화 번호 입력
   └ requestLookupCode()            (donation-lookup.ts:71)
       · 형식검증 /^01[0-9]{8,9}$/
       · 번호단위 발송 속도제한: 10분 3회 (kv.incr, lookup:send:{phoneHash})
       · 6자리 CSPRNG 코드 생성 → MT 어댑터로 발송 (templateCode: LOOKUP_VERIFY)
       · KV 에 {phoneHash, phoneMasked, hmac(code), 시도 5회} 를 ticket 키로 300초 저장
       · 응답에는 ticket + 마스킹번호만 내려감 (원문 번호·코드는 미노출)
[code] 인증번호 6자리 입력
   └ verifyAndLookup()              (donation-lookup.ts:120)
       · HMAC-SHA256 + safeEqual 비교 (타이밍 공격 방어)
       · 실패 시 잔여 시도 차감, 0회 → 폐기 후 처음부터
       · 성공 시 코드 즉시 폐기(재사용 차단) → loadResult()
[result] 결과 표시
   └ loadResult()                   (donation-lookup.ts:161)
       · DonorProfile.phoneHash 로 후원자 조회
       · Donation 최근 30건 + 결제성공 상태군 합계/건수 집계
       · 사회복지기관명/코드, 금액, 메시지, 상태배지, 수신시각만 반환
       · 거래번호·결제수단·카드정보는 반환하지 않음 (요구사항 준수)
```

### 1-4. 조회 로직 정확성 평가 — 대체로 정상

- **본인 확인 없이 결과가 나가지 않는다.** 번호 입력만으로는 결과가 반환되지 않고, 반드시 코드 검증을 통과해야 `loadResult()` 가 호출된다. 설계 의도대로다.
- **검증값이 클라이언트로 내려가지 않는다.** 상태 전체가 서버 KV 에 있고, 클라이언트는 랜덤 `ticket` 만 들고 다닌다.
- **조회 키가 안전하다.** 클라이언트가 보낸 번호가 아니라 KV 레코드의 `phoneHash` 로 조회하므로, ticket 을 탈취해도 다른 번호 내역을 열 수 없다.
- **집계 상태군이 합리적이다.** `PAYMENT_SUCCESS ~ SETTLED` 만 누적금액에 포함하고, 목록은 상태 무관 최근 30건을 보여준다. (목록 30건 ≠ 집계 모수 → 화면상 "누적 N건"과 리스트 개수가 다를 수 있으나, UI 문구가 각각 "누적"과 "최근 30건"으로 구분돼 있어 오해 소지는 낮다.)

## 2. SMS 인증 연동 현황 및 문제점

### 2-1. 연동 현황 요약

| 구간 | 상태 |
| --- | --- |
| 인증번호 생성·검증 로직 | **완료** (CSPRNG 6자리, HMAC 보관, 5분 TTL, 5회 제한) |
| 발송 속도 제한 | **부분 완료** (번호 기준만) |
| MT 어댑터 인터페이스 | **완료** (`MtAdapter.send()` 규격 확정) |
| **실제 문자 사업자 연동** | **미구현 — mock 뿐** |
| 관리자 화면에서의 키 설정 | **없음** (3장 참고) |

`src/server/adapters/mt/index.ts` 에는 `mockMtAdapter` 하나만 있다.

```ts
export function getMtAdapter(): MtAdapter {
  if (env.safety.safeMode && env.mt.provider !== 'mock') { ... return mockMtAdapter; }
  switch (env.mt.provider) {
    case 'mock': return mockMtAdapter;
    default: throw new Error(`MT_PROVIDER=... 어댑터가 구현되지 않았습니다. 사업자 계약 확정 후 추가하십시오.`);
  }
}
```

비교하면 **MO(수신) 쪽은 실사업자 구현이 이미 있다** (`src/server/adapters/mo/mtonet.ts`). 즉 문자를 "받는" 쪽은 실연동 준비가 되어 있고, "보내는" 쪽(MT)만 mock 상태다. `.env.example:77` 의 `MT_PROVIDER="mock" # mock | <사업자코드>` 도 사업자 미확정 상태를 그대로 보여준다.

### 2-2. 문제점 — 우선순위 순

**[P1-A] 실사업자 어댑터 부재 → 운영 전환 시 서버 액션이 예외로 죽는다**
`MT_PROVIDER` 를 사업자 코드로 바꾸는 순간 `getMtAdapter()` 가 `throw` 한다. 이 호출은 `requestLookupCode()` (donation-lookup.ts:92) 안에서 try/catch 없이 실행되므로, 사용자에게 안내 문구가 아니라 서버 액션 예외(일반 오류 화면)가 노출된다. `donation-flow.ts` 의 `sendMt()` 는 try/catch 로 감싸 이력만 FAILED 로 남기는데, 후원확인/휴대폰인증 경로만 이 보호가 없다.

**[P1-B] SAFE_MODE 로 인한 조용한 실패**
`SAFE_MODE` 기본값이 `true` 다(`env.ts`). 실사업자 키를 넣어도 SAFE_MODE 를 내리지 않으면 mock 으로 대체되고, 화면에는 "인증번호를 발송했습니다"가 뜬다. `devCode` 는 `isLocal` 일 때만 노출되므로 **스테이징에서는 코드도 안 보이고 문자도 안 오는 완전 교착**이 된다. 화면에 mock 임을 명시하라는 프로젝트 절대규칙 2 를 이 경로에서만 만족하지 못한다.

**[P1-C] 인증 문자가 MT 발송 이력(MtOutboundMessage)에 남지 않는다**
`donation-lookup.ts:92`, `phone-link.ts:109` 는 `adapter.send()` 를 **직접** 호출한다. `donation-flow.ts:46` 의 `sendMt()` 처럼 DB 이력을 만들지 않는다. 결과:
- `/admin/mt-messages` 에서 인증 문자 발송 이력을 볼 수 없다 (mock outbox 는 프로세스 메모리라 재시작/다중 인스턴스에서 소실).
- 통신비 정산·발송 실패율 집계에서 인증 문자가 통째로 빠진다.
- 고객이 "인증문자가 안 왔다"고 문의해도 상담사가 확인할 근거가 없다.

**[P2-A] 결과 화면이 시트를 닫아도 초기화되지 않는다 (개인정보 노출)**
시트는 공개 셸에 상시 마운트돼 있고(`public-shell-client.tsx:328`), `onClose` 는 `open=false` 만 준다. `donation-lookup-sheet.tsx` 어디에도 닫을 때 `step`/`result` 를 리셋하는 코드가 없다. 따라서 A가 조회 후 닫으면, **같은 브라우저 세션에서 시트를 다시 여는 누구든 재인증 없이 A의 후원 내역(금액·메시지·사회복지기관)을 그대로 본다.** PC방·공용 PC·가족 공용 기기에서 실제 노출 경로다.

**[P2-B] "10분 뒤 자동으로 닫힙니다" 안내가 사실과 다르다 (미구현 데드코드)**
`donation-lookup.ts:63,155` 가 `lookup:session:{ticket}` 을 `SESSION_SEC(600)` 로 저장하지만, **이 키를 읽는 코드가 저장소 어디에도 없다.** (`web-donation.ts` 는 같은 패턴을 `getSession()` 으로 실제 사용 중 — 후원확인만 반쪽 구현.) 반면 UI 안내문에는 "결과는 10분 뒤 자동으로 닫힙니다"라고 적혀 있다(`donation-lookup-sheet.tsx` 안내 리스트). 세션 만료 개념 자체가 동작하지 않으므로 P2-A 와 합쳐 **결과가 무기한 유지**된다.

**[P2-C] 발송 속도제한이 번호 기준뿐 — IP/기기 기준이 없다**
`lookup:send:{phoneHash}` 만 센다. 로그인 전 경로라 사용자 축이 없는 것은 이해되지만, 공격자가 번호를 바꿔가며 무제한 발송을 트리거할 수 있다(문자 폭탄 + 발송비 과금). `phone-link.ts` 는 사용자+번호 2축인데 후원확인은 1축이다. IP 또는 익명 기기 쿠키 축 추가가 필요하다.

**[P3-A] 인메모리 폴백 시 인증 붕괴 가능**
`ALLOW_INMEMORY_FALLBACK` 기본값이 `true` 다. 다중 인스턴스에서 폴백이 켜지면 발송 인스턴스와 검증 인스턴스가 달라 "유효시간이 지났습니다"가 무작위로 발생한다. 운영 점검(`assertProductionSafety`)이 이를 막고 있으나, 스테이징에는 가드가 없다.

**[P3-B] 발신번호 상수 미사용**
`env.mt.fromNumber` 는 `donation-flow.sendMt()` 에서만 쓰인다. 인증 문자 경로는 발신번호를 지정하지 않으므로, 실사업자 어댑터 구현 시 발신번호 사전등록 검증에서 누락될 소지가 있다.

## 3. 최고관리자에서 인증 API 설정 가능 여부

### 결론: **설정 화면이 없다. 조회(읽기 전용)만 가능하다.**

| 화면 | 경로 | 인증 API 관련 기능 |
| --- | --- | --- |
| 시스템 상태 | `src/app/admin/system/page.tsx` | `MT 발송` provider 값을 **배지로 표시만** 함. `mock`/`local` 이면 warning 배지. 입력·저장 불가 |
| MT 발송 관리 | `src/app/admin/mt-messages/page.tsx` | 발송 **이력 조회·필터**만. 단, 2-2 [P1-C] 로 인증 문자는 여기 안 나옴 |
| TTS 연동 | `src/app/admin/tts/page.tsx` | 키 등록 여부만 표시하고, 화면에 "키는 화면에 저장하지 않고 서버 환경변수로만 관리합니다" 라고 **명시적으로 안내** |
| 유튜브 연동 | `src/app/admin/youtube/page.tsx` | 채널 연결/해제만. 클라이언트 시크릿은 env |

즉 이 프로젝트는 **모든 외부 연동 키를 `.env` 로만 관리하는 정책**이며(`src/lib/env.ts` 상단 주석: "모든 외부 연동 키는 여기서만 읽는다"), MT/SMS 도 예외가 아니다. 관리자가 SMS 인증 API 를 화면에서 설정·전환·테스트할 수 있는 UI 는 **존재하지 않는다.**

부수 발견: `prisma/schema.prisma:1487` 에 `SystemSetting { key, value(Json), memo, updatedBy, updatedAt }` 모델이 정의되어 있으나, **애플리케이션 코드에서 단 한 번도 참조되지 않는다** (`grep systemSetting src/` 결과 0건, generated 제외). 관리자 화면 기반 설정을 염두에 두고 만들어 둔 뒤 사용하지 않은 상태다. 향후 "관리자 화면에서 SMS 설정" 요구가 확정되면 이 테이블이 자연스러운 착지점이지만, **API 키 원문을 DB 에 넣는 것은 프로젝트 절대규칙 6(개인정보/금융정보 3분리) 및 현 env 정책과 충돌**하므로, 키는 env 에 두고 **DB 에는 provider 선택·발신번호·템플릿·SAFE_MODE 같은 비밀 아닌 운영 스위치만** 두는 절충이 타당하다.

### 4-1. 현재 구조의 문제

1. **마지막 그룹이 12개로 비대하다.** 전체의 절반이 "정산·정책·운영"이라는 잡동사니 서랍에 들어가 있다. 그룹 이름이 세 단어 복합어인 것 자체가 분류 실패 신호다.
2. **성격이 완전히 다른 것들이 한 그룹에 있다.** 정산(재무) / 배너·공지(콘텐츠 마케팅) / 관리자 권한·감사로그(보안 거버넌스) / MO 시뮬레이터(개발 도구)가 나란히 있다.
3. **정책이 두 군데로 흩어진다.** `한도 정책(/admin/policies)` 은 정책 그룹, `한도·이상거래(/admin/risk)` 는 거래 그룹에 있다. 운영자는 한도를 조정하려면 두 메뉴를 오간다.
4. **TTS 가 두 화면에 중복 노출된다.** `/admin/tts` 와 `/admin/overlay`(제목이 "오버레이·TTS 관리") 가 겹친다.
5. **권한별 메뉴 필터가 사실상 없다.** `admin/layout.tsx` 는 `/admin/inquiries` 하나만 SUPER_ADMIN 으로 거른다. 반면 서버 액션 층에는 `READ_ONLY`, `SUPPORT`, `SUPER_ADMIN` 별 분기가 광범위하게 존재한다(`actions/admin/settlement.ts`, `accounts.ts`, `holidays.ts` 등). 결과적으로 **고객지원 권한자에게 정산·수수료 메뉴가 보이지만 누르면 에러**가 나는 구조다.
6. **MO 시뮬레이터가 운영 메뉴에 섞여 있다.** 개발/검수 전용 도구이며, 노출 조건 분기도 메뉴 층에는 없다.

### 5-3. 그룹과 권한을 함께 정리하는 제안 (선택)

현행 `groups` 배열의 `items` 에 `permissions?: AdminPermission[]` 를 추가하고, `admin/layout.tsx` 의 필터를 `/admin/inquiries` 하드코딩 대신 이 필드 기반으로 바꾸면 4-1 의 5번 문제(보이지만 눌리지 않는 메뉴)를 구조적으로 없앨 수 있다. 서버 액션 층의 기존 권한 분기와 값을 맞추면 된다.

| 그룹 | 최소 권한 제안 |
| --- | --- |
| 운영 현황 / 회원·사회복지기관 / 문자·결제 | 전 권한 (READ_ONLY 는 읽기만) |
| 정산·재무 | SUPER_ADMIN, OPERATION, FINANCE (SUPPORT 제외 — 액션 층과 동일) |
| 방송 연동 / 정책·리스크 / 콘텐츠·고객지원 | SUPER_ADMIN, OPERATION (문의는 현행대로 SUPER_ADMIN) |
| 보안·시스템 관리 | SUPER_ADMIN |

아이콘은 `console-shell.tsx` 의 `CONSOLE_ICONS` 에 이미 전부 존재하므로 **추가 아이콘 없이 재배치만으로 적용 가능**하다. lucide 라인 아이콘만 쓰는 절대규칙 1 도 유지된다.

## 6. 종합 평가 및 개발 필요 항목 우선순위

### 종합 평가

**후원확인 기능의 인증 설계 자체는 견고하다.** 코드 원문 미보관·HMAC 비교·safeEqual·TTL·시도 제한·티켓 방식 등 이 규모 서비스에서 기대할 수 있는 수준을 충족했고, 결과 데이터에 결제수단·거래번호를 넣지 않은 판단도 적절하다. 문제는 **설계가 아니라 마감**에 있다: 실사업자 어댑터가 없고, 세션 만료가 반쪽만 구현됐으며, 인증 문자만 발송 이력에서 빠져 있고, 시트가 닫혀도 남의 내역이 화면에 남는다.

**관리자 메뉴는 기능 커버리지는 충분하나 정보구조가 무너져 있다.** 25개 항목 중 12개가 한 그룹에 몰려 있고, 권한 필터가 메뉴 층에 거의 없어 "보이지만 눌리면 에러"가 발생한다.

### 착수 권고

P1 3건은 서로 인접한 코드라 **한 번의 작업으로 묶는 것이 효율적**이며, 외부 계약과 무관하게 지금 처리 가능하다. 특히 첫 번째 항목(시트 상태 초기화)은 공용 PC 에서 즉시 재현되는 개인정보 노출이므로 최우선이다. 관리자 메뉴 재그루핑(P2 마지막)은 배열 재배치만으로 끝나고 위험도가 낮아, P1 작업과 병행해도 무방하다.
