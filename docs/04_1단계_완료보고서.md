## 1. 구현한 기능

### 1-1. 기반
- Next.js 16(App Router) + TypeScript + Tailwind v4 프로젝트 신규 구축 (독립 프로젝트)
- 기브싸인 전용 디자인 토큰·공용 컴포넌트 (이모지 미사용, 라인형 아이콘 통일)
- 세션 기반 인증 3롤(후원자 / 사회복지기관 / 관리자) + 관리자 감사로그
- PostgreSQL 스키마 **45개 모델 / 28개 enum**, AWS RDS·Aurora 호환 설계
- 무결성 가드 마이그레이션 (정산 원장 append-only 트리거, 부분 유니크 인덱스, CHECK 제약)
- 시드 데이터 (관리자·사회복지기관 2명·MO 번호 2종·후원자·약관 6종·FAQ·정책)

### 1-2. 핵심 도메인
- **MO 수신 → 후원 거래 → 결제 → 방송 노출** 전 흐름
- 후원 상태머신 15단계 + 상태 전이 로그
- **중복 결제 4중 방어** (사업자 메시지 ID UNIQUE / 멱등키 / 1회용 링크 / PG 주문번호 재사용 + 승인 부분 유니크)
- 결제 타임아웃 시 **거래결과조회로 최종 상태 확정**
- 한도·속도·연속발송·실패잠금·신규 첫날 한도 정책 엔진 (GLOBAL/CREATOR/DONOR 우선순위)
- 금칙어 + 개인정보(주민번호·카드·전화·계좌·이메일·URL) 자동 마스킹 필터
- 정산 원장(복식 분개) + 수수료 정책 + 정산 요청/지급 + 환불 반대분개
- 1회용 보안링크(해시 저장, 단기 만료, 1회 소비)

### 1-4. 안전장치
- `SAFE_MODE=true` — 실제 결제 승인·실제 MT 발송 차단
- `ALLOW_DIRECT_TRIGGER=false` — MO 수신 즉시 결제를 코드 레벨에서 강등 (금융사 서면승인 전까지 열리지 않음)
- 미구현 사업자 어댑터는 **예외를 던져** 조용한 mock 대체를 막음
- 운영 전환 경고 점검 `GET /api/health` → `productionWarnings`
- `/admin/simulator` 는 `APP_ENV=prod` 에서 화면·서버액션 모두 차단

## 5. 실제 계약 또는 API 키가 필요한 기능

착수 순서 기준 우선순위입니다.

1. **헥토파이낸셜** — 사회복지기관 계약 + MID/라이선스/AES/HASH + 테스트베드. **문자 수신을 결제 트리거로 쓰는 구조에 대한 서면 승인**이 가장 중요합니다.
2. **MO 사업자** — 수신번호 방식(전용번호 vs 대표번호+키워드) 결정 후 계약. 번호 원가가 직접적인 손익 요인입니다.
3. **MT 사업자** — 발신번호 사전등록, SMS/LMS 단가.
4. **Google Cloud / YouTube** — OAuth 클라이언트 + 동의화면 검증 + **할당량 실측 및 증설 신청**(1주차 최우선 검증 과제).
5. **AWS** — RDS/Aurora, ElastiCache, S3, KMS, Secrets Manager.
6. TTS, 본인인증, 계좌실명조회, 미디어 인프라.

## 7. 다음 단계 작업 (2단계 — 실제 문자·결제 연동)

1. 헥토파이낸셜 실 어댑터 구현 (`src/server/adapters/payment/hecto.ts`)
   - 결제창 파라미터 암호화(AES) / 해시 검증
   - 0원 인증 후 빌키 발급, 승인·조회·취소
   - **결제인증 후 10분 제한**에 맞춘 확인 링크 TTL(현재 300초) 재검증
2. MO 사업자 실 어댑터 + Webhook 스펙 매핑 + 허용 IP 등록
3. MT 사업자 실 어댑터 + 템플릿 사전 등록(필요 시) + 실패 재발송 큐
4. BullMQ 워커 분리 (결제 재시도 / 유튜브 전송 / MT 재발송 / 확인 만료 정리 배치)
5. 테스트베드 전 시나리오 회귀 (중복 결제 0건 확인)
6. 관리자 한도 정책 운영 값 확정

이후 3단계(유튜브 실연동), 4단계(자체 방송), 5단계(정산·운영 고도화) 순서로 진행합니다.
