# 기브싸인 아키텍처

## 1. 전체 흐름

```
[시청자 휴대폰]
      │ MO 문자
      ▼
[MO 사업자] ──Webhook(HMAC 서명 + IP 허용)──▶ POST /api/webhooks/mo
                                                    │
                                            WebhookLog 원문 보존
                                                    │
                                            MoAdapter.parse()
                                                    ▼
                                          handleMoInbound()
      ┌─────────────────────────────────────────────┼─────────────────────────────────┐
      │ 1) providerMessageId UNIQUE → 중복 차단                                        │
      │ 2) 수신번호(+키워드)로 사회복지기관 라우팅                                       │
      │ 3) 발신번호 해시로 후원자 식별 (없으면 생성)                                  │
      │ 4) 활성 결제수단 없음 → UNREGISTERED_DONOR + 등록 링크 MT (결제 없음)         │
      │ 5) 콘텐츠 필터 (개인정보 마스킹 / 금칙어)                                     │
      │ 6) 한도·속도·차단 검사                                                        │
      │ 7) Charge 생성 (멱등키: merchantId:providerMessageId)                          │
      │ 8) CONFIRM_LINK → MT 확인 링크 / DIRECT_TRIGGER → 즉시 결제                    │
      └─────────────────────────────────────────────┼─────────────────────────────────┘
                                                    ▼
                                            executePayment()
                            PaymentTransaction(orderNo = PG 멱등키) 생성
                            PaymentAdapter.approve()
                              ├─ 성공  → 수수료 계산 → 정산 원장 3분개 → 카운터 반영
                              ├─ 실패  → 실패 MT, 실패 누적 시 후원자 잠금
                              └─ 타임아웃 → inquire() 로 최종 상태 확정
                                                    ▼
                                          dispatchBroadcast()   ※ 결제 성공 건만
                              ├─ 오버레이 이벤트 발행 (SSE / Redis Pub/Sub)
                              └─ 유튜브 라이브 채팅 등록 (할당량 가드 + 큐)
                                                    ▼
                              BROADCASTED / PARTIAL_DELIVERY_FAILED
```

**핵심 원칙**: 결제 성공과 방송 송출 성공은 별개의 축이다. 유튜브 전송이 실패해도 결제 결과는 유지되며, `youtubeStatus` / `overlayStatus` / `mtStatus` 를 각각 기록한다.

## 2. 후원 상태머신

| 상태 | 의미 | 결제 발생 |
|---|---|---|
| `RECEIVED` | MO 수신, 거래 생성 | X |
| `UNREGISTERED` | 결제수단 미등록 | X |
| `LIMIT_BLOCKED` | 한도·속도·차단 위반 | X |
| `CONTENT_BLOCKED` | 금칙어 차단 | X |
| `PENDING_CONFIRM` | 확인형(MT 링크) 대기 | X |
| `PENDING_PAYMENT` | 결제 승인 요청 중 | 진행 |
| `PAYMENT_SUCCESS` | 승인 완료 | O |
| `PAYMENT_FAILED` | 승인 실패 / 확인 시간 초과 | X |
| `BROADCAST_PENDING` | 방송 송출 시도 중 | O |
| `BROADCASTED` | 오버레이 + 유튜브 모두 성공(또는 건너뜀) | O |
| `PARTIAL_DELIVERY_FAILED` | 일부 송출 실패 (결제는 유효) | O |
| `REFUND_REQUESTED` / `REFUNDED` | 환불 | O(취소) |
| `SETTLEMENT_PENDING` / `SETTLED` | 정산 | O |

모든 전이는 `charge_status_log` 에 `from → to`, 사유, 주체와 함께 기록된다.

## 3. 중복 결제 방지 — 4중 방어

| 계층 | 수단 | 막는 상황 |
|---|---|---|
| 1 | `mo_inbound_message.provider_message_id` **UNIQUE** | MO 사업자의 재전송 |
| 2 | `idempotency_key(scope, key)` **UNIQUE** (`charge:{merchantId}:{providerMessageId}`) | 동시 요청의 거래 중복 생성 |
| 3 | `secure_link.usedAt` **1회 소비** (`updateMany where usedAt IS NULL`) | 확인 링크 중복 클릭 |
| 4 | `payment_transaction` 거래당 1건 + `orderNo` 를 PG 멱등키로 재사용<br>+ 부분 유니크 인덱스 `payment_transaction_approved_uniq` | PG 재요청 / 응답 유실 |

추가로 타임아웃·네트워크 오류 시 **반드시 `inquire()`(거래결과조회)로 최종 상태를 확정**한다. 조회조차 불확실하면 `UNKNOWN` 으로 남기고 관리자 화면(`/admin/payments`)에 "확인 필요"로 노출한다.

## 4. 정산 원장

- `settlement_ledger` 는 **append-only**. `settlement_ledger_append_only` 트리거가 UPDATE/DELETE 를 차단한다.
- 결제 성공 1건 = 3분개
  - `CHARGE_GROSS` (+결제금)
  - `PG_FEE` (−결제수수료)
  - `PLATFORM_FEE` (−플랫폼수수료)
- 환불 = 반대분개 `REFUND`(−후원금) + `REFUND_FEE_RETURN`(+플랫폼수수료 환입). PG 수수료는 환입하지 않는다(정책값).
- 정산 지급 = `PAYOUT`(−실지급액) + `PAYOUT_WITHHOLDING`(−원천징수).
- **정산 가능 금액 = 원장 합계 − 정산 요청 중(REQUESTED/REVIEWING/APPROVED) 금액.**
- 이미 지급된 건의 환불은 마이너스 잔액으로 남아 다음 정산에서 자동 차감된다.

## 5. 개인정보 · 금융정보

| 데이터 | 저장 |
|---|---|
| 휴대전화번호 | `phone_hash`(HMAC-SHA256, secret) + `phone_enc`(AES-256-GCM 봉투암호화) + `phone_masked` |
| 문자 원문 | `content_enc` (암호화). 방송·화면 노출은 `content_filtered` 만 사용 |
| 계좌번호 | **원문 저장 금지.** `bank_code`, `account_tail4` 만 |
| 결제 빌키 | `bill_key_enc` (암호화). 복호화는 결제 실행 지점에서만, 로그 출력 금지 |
| OAuth 토큰 | 암호화 저장, 만료 시 자동 갱신 |
| 오버레이 토큰 / 스트림 키 | 해시만 저장(`tokenHash`), 발급 시 1회만 원문 노출 |

- 운영에서는 `CRYPTO_PROVIDER=aws-kms` 로 전환해 KMS 봉투암호화를 사용한다(`setCryptoProvider()` 로 주입).
- 로거는 출력 직전에 민감 키와 전화번호 패턴을 한 번 더 마스킹한다(`src/lib/logger.ts`).

## 6. 어댑터 (Provider Adapter 패턴)

| 어댑터 | 인터페이스 | mock 동작 |
|---|---|---|
| MO | `verify(rawBody, headers, ip)`, `parse(body)` | HMAC 서명 + IP 허용 검증 |
| MT | `send({to, text, templateCode})` | 인메모리 outbox 적재 |
| Payment | `createRegistrationSession` / `completeRegistration` / `approve` / `inquire` / `cancel` / `revokeBillKey` | 금액 끝자리로 시나리오 제어 (`999` 실패, `888` 타임아웃→승인, `777` 타임아웃→실패) |
| YouTube | `getAuthUrl` / `exchangeCode` / `refresh` / `getChannel` / `findActiveBroadcast` / `insertChatMessage` / `revoke` | 가상 라이브 방송, `setMockLive(false)` 로 종료 재현 |
| TTS | `synthesize` | 브라우저 SpeechSynthesis 사용 지시 |
| Stream | `issueKey` / `revokeKey` / `status` | 키 발급만 |

미구현 사업자를 mock 으로 조용히 대체하지 않는다. `getXxxAdapter()` 는 알 수 없는 provider 에 대해 **예외를 던진다.**

## 7. 유튜브 할당량

- 기본 일일 10,000 units. `liveChatMessages.insert` 는 비용이 큰 편(공개 자료 기준 50 units)이라 실측 전에는 **하루 200건 수준**만 전송 가능할 수 있다.
- `reserveYouTubeQuota()` 가 KST 일자 기준으로 사용량을 선점하고, 초과 시 전송을 `FAILED(QUOTA_EXCEEDED)` 로 남긴다. **결제는 유지된다.**
- `/studio/youtube` 와 `/admin/youtube` 에서 사용량과 잔여 전송 가능 건수를 노출한다.
- 실연동 1주차 과제: 실제 비용 실측 → 할당량 증설 신청.

## 8. 실시간 오버레이

- 이벤트 버스: 단일 인스턴스는 인메모리 EventEmitter, 다중 인스턴스는 **Redis Pub/Sub**(`givesign:overlay`).
- 전송: SSE (`GET /api/overlay/{creatorId}/stream?token=`), 20초 하트비트, `X-Accel-Buffering: no`.
- 클라이언트: 이벤트 대기열 **순차 재생**, TTS 재생 종료와 표시 시간 중 긴 쪽 기준으로 다음 항목 진행, 지수 백오프 재연결(최대 30초), `?debug=1` 에서만 연결 상태 표시.
- 결제 성공 이벤트만 버스에 올린다. 테스트 후원은 `isTest: true` 로 구분하며 정산·상태에 반영하지 않는다.

## 9. MO 라우팅 두 가지 모드

| 모드 | 구성 | 장단점 |
|---|---|---|
| `DEDICATED` | 사회복지기관별 전용 수신번호 | 사용자 경험이 단순. 번호 재고 비용이 인원수만큼 선형 증가 |
| `SHARED_PREFIX` | 대표번호 1개 + 문자 맨 앞 키워드 (`MSG3QP7 응원합니다`) | 번호 원가 절감. 키워드 입력 실패 가능성 |

라우팅은 전용번호를 먼저 조회하고, 없으면 대표번호+키워드로 조회한다. 키워드는 메시지에서 제거된 뒤 후원 메시지로 저장된다.
