# 기브싸인 정리 보고서 (4차)

**대상**: 수수료 정책 관리(전역 / 사회복지기관별) · 부가세 포함 요율 · PG 토큰 구조
**작성일**: 2026-09-01
**성격**: **정리·보고만.** 코드 수정은 하지 않았습니다.

---

## 1. 수수료 정책 — 요청하신 구조가 이미 만들어져 있습니다

`/admin/fees` 화면과 `resolveFeePolicy()` 를 직접 확인했습니다.

### 이미 되어 있는 것

| 항목 | 현재 상태 |
|---|---|
| 적용 범위 2단계 | `GLOBAL`(전역) / `MERCHANT`(사회복지기관 개별) 선택 가능 |
| **우선순위** | **사회복지기관 개별 → 전역 → 코드 기본값** 순으로 자동 적용 |
| 등록 화면 | `/admin/fees` 에서 범위 선택 + 사회복지기관 드롭다운으로 등록 |
| 시행일 지정 | 적용 시작일(KST) 입력 가능 |
| 이력 보존 | 기존 정책은 **삭제하지 않고 마감**. 이력 표에 남음 |
| 조정 가능 항목 | 결제수수료율 / 건당 고정비 / 플랫폼수수료율 / 문자원가 / 지급일(영업일) / 부가세 포함여부 |
| 권한 | SUPPORT 권한 차단, 감사로그 기록(`FEE_POLICY_CREATE`·`FEE_POLICY_DEACTIVATE`) |
| 되돌리기 | 사회복지기관 개별 정책을 마감하면 **자동으로 전역 정책으로 복귀** |
| 전체 적용 | 전역 정책을 새로 등록하면 **개별 정책이 없는 모든 사회복지기관에 즉시 적용** |
| 안전장치 | 결제+플랫폼 수수료 합이 100% 이상이면 등록 거부 (자릿수 실수 방지) |
| 범위 격리 | 사회복지기관 정책을 등록해도 전역 정책은 마감되지 않음 (확인 완료) |

**즉 "전체 적용 + 사회복지기관별 개별 수정" 구조는 손댈 필요가 없습니다.** 아래 4가지만 고치면 요청하신 형태가 완성됩니다.

## 2. 고쳐야 할 것 4가지

### 2-1. 입력을 `5.5%` 형식으로 받게 (요청사항)

**현재**: `0.055` 소수만 허용합니다. (`src/app/actions/admin/shared.ts:88`)

```
if (!/^\d(\.\d{1,6})?$/.test(raw)) throw new Error('요율은 0 ~ 1 사이 소수로 입력해 주세요. (예: 0.018)')
```

`5.5` 를 입력하면 오류가 납니다. 더 위험한 건 **만약 그대로 통과시키면 550%** 가 된다는 점입니다.

**개선안**
- 입력란을 **퍼센트 단위**로 바꾸고 옆에 실시간 환산을 표시 → `5.5 %  (= 0.055)`
- 검증: 0 ~ 100, 소수점 4자리까지
- **저장은 소수(0.055) 유지** — 기존 원장·계산식과의 호환 때문
- 화면 표시도 전부 % 로 통일
  - 지금 `/admin/merchants/[id]` 는 `0.15` 를 그대로 노출합니다 (읽기 불편)

### 2-2. ★ 핵심 — 부가세 포함 5.5%로 받되, 장부에는 분리 기록해야 합니다

**대표님 방침**: 부가세 포함 5.5% 형식으로 적용.

**현재 코드의 문제** (`src/server/services/settlement.ts:151-152`)

```ts
const pgFeeVat       = rates.vatIncluded ? 0n : applyRate(pgFeeSupply, VAT_RATE);
const platformFeeVat = rates.vatIncluded ? 0n : applyRate(platformFeeSupply, VAT_RATE);
```

`vatIncluded = true` 로 두면 **부가세를 0원으로 기록**합니다.
→ **돈은 맞는데 장부가 틀립니다.** 세금계산서에 공급가액/부가세를 분리해 넣어야 하는데 그 근거가 원장에 없습니다. 우리가 국세청에 낼 부가세의 산출 근거가 사라집니다.

**수정안 — 포함 요율일 때 역산하기**

```
공급가액 = 차감액 ÷ 1.1   (원 미만 버림)
부가세   = 차감액 − 공급가액
```

3,000원 결제 / 플랫폼 수수료 5.5%(포함) 기준:

| | 지금 | 수정 후 |
|---|---|---|
| 차감액 | 165원 | 165원 (동일) |
| 공급가액 기록 | 165원 | **150원** |
| 부가세 기록 | **0원** | **15원** |
| 사회복지기관 정산금 | 2,835원 | 2,835원 (동일) |

**정산금은 1원도 바뀌지 않습니다.** 장부 기록만 정확해집니다.

이렇게 하면 세 가지가 동시에 충족됩니다.
1. 관리자는 대표님 방식(`5.5% 포함`)으로 입력
2. 원장에는 공급가액·부가세가 분리 기록 → 세금계산서 발행 가능
3. 사회복지기관 정산금·화면 표시 변화 없음

**수정 위치**: `computeFees()` 2줄, `feeMemo()` 문구, `tests/fee-vat-and-settings.test.ts` 2건

> 참고 — 3차 보고서에서는 "부가세 별도(`vatIncluded=false`) 로 바꾸자"고 말씀드렸으나,
> 대표님 방침(포함 5.5%)에 맞춰 **위 역산 방식으로 정정**합니다.
> 두 방식 모두 결과 금액은 같고, 이 방식이 관리자 입력이 더 직관적입니다.

### 2-3. 🔴 신규 발견 — 시행일을 미래로 잡으면 그 사이가 비어 버립니다

**등록 시** (`createFeePolicy`)
```ts
await tx.feePolicy.updateMany({
  where: { active: true, scope, merchantId },
  data: { active: false, effectiveTo: effectiveFrom },   // ← 즉시 비활성
});
```

**조회 시** (`resolveFeePolicy`)
```ts
where: { active: true, effectiveFrom: { lte: now }, ... }
```

**무슨 일이 벌어지나**

오늘(9/1) 새 정책을 등록하면서 시행일을 **10/1** 로 지정하면,

| 기간 | 적용되는 정책 |
|---|---|
| 9/1 ~ 9/30 | **없음** → 코드 기본값(PG 1.8% / 플랫폼 15% / 부가세 포함)이 조용히 적용 |
| 10/1 ~ | 새 정책 |

기존 정책이 **즉시** 꺼지는데 새 정책은 **아직** 안 켜져서, 그 사이 한 달 동안 사회복지기관 정산금이 엉뚱한 요율로 계산됩니다. 화면 어디에도 경고가 뜨지 않습니다.

**수정안**: 기존 정책을 `active: false` 로 바꾸지 말고, `effectiveTo` 만 미래 시각으로 설정합니다. `resolveFeePolicy` 의 `effectiveTo` 조건이 이미 만료를 처리하므로 그것만으로 충분합니다.

### 2-4. 사회복지기관 상세화면에서 바로 수정할 수 없습니다

`/admin/merchants/[id]` 에는 현재 적용 중인 정책이 **읽기 전용**으로만 표시됩니다. 수수료를 바꾸려면 `/admin/fees` 로 이동해 사회복지기관을 다시 골라야 합니다.

**개선안**: 사회복지기관 상세화면에 "이 사회복지기관 수수료 변경" 버튼을 붙여, 해당 사회복지기관이 선택된 상태로 등록 폼을 열어 줍니다. (결함은 아니고 운영 편의)

### 2-5. 함께 정리할 작은 것들

- **정책 미등록 경고**: 정책이 하나도 없으면 코드 기본값(1.8% / 15%)이 조용히 적용됩니다. `/admin/fees` 상단에 경고 배너를 띄우는 게 안전합니다.
- **요율 합 검증 경계**: 현재 `결제요율 + 플랫폼요율 >= 1` 이면 거부합니다. 부가세 별도 정책에서는 실제 차감이 요율의 1.1배이므로 **90.9% 부터** 정산금이 0이 됩니다. 경계값을 재검토할 필요가 있습니다.

## 3. PG 토큰 구조 — 이미 그 구조로 설계되어 있습니다

**대표님 설명**: 결제는 PG사(헥토 내통장결제 / 빌링키 업체)에서 이루어지고, **PG사가 모든 결제정보를 보관**하며, 우리는 **토큰 값만** 받는다.

스키마를 확인한 결과 **정확히 그 구조**입니다.

### `PaymentMethodToken` (결제수단)

| 우리가 저장하는 것 | 우리가 저장하지 않는 것 |
|---|---|
| 빌키 암호문 (`billKeyEnc`) | 계좌번호 원문 |
| 계좌 끝 4자리 (`accountTail4`) | 카드번호 원문 |
| 은행코드 / 은행명 | CVC, 유효기간 |
| 카드 발급사명 / 카드 끝 4자리 | 카드·계좌 비밀번호 |

스키마 주석에 명시되어 있습니다 — *"계좌 원문 저장 금지. 끝 4자리만 보관"*, *"카드 원문 저장 금지, 발급사명과 끝 4자리만 보관"*, *"빌키 복호화는 결제 워커에서만 수행하며 로그 출력 금지"*.

### `PaymentTransaction` (거래)

`providerTid`(PG 거래번호) · `orderNo`(우리 주문번호) · 금액 · 상태 · `rawMasked`(마스킹된 응답)만 보관합니다.

**결론: PCI-DSS 적용 범위 밖으로 설계되어 있고, 이대로 가면 됩니다.**

### 3-1. 이 구조가 확정되면서 새로 챙겨야 할 것

#### (a) 본인확인 결과 — 3차 보고서 내용을 조정합니다

3차에서 *"CI를 저장하면 한도 우회·번호 재사용·분쟁대응이 한 번에 풀린다"* 고 말씀드렸는데, **토큰만 받는 구조라면 CI가 안 내려올 가능성이 큽니다.**

**헥토 연동 규격서에서 확인하실 것**: 빌키 발급 응답에 다음이 있는지
- `DI` (사회복지기관별 중복확인값) — CI 전체는 안 줘도 DI는 주는 경우가 많습니다
- `성인여부` 플래그
- `소유주 실명`

| 확인 결과 | 조치 |
|---|---|
| DI 또는 성인여부를 **준다** | `PayerProfile` 에 `ownerDiHash`, `adultVerifiedAt` 추가. 한도 합산 기준을 DI로 → 번호 여러 개로 한도 우회 차단 |
| **안 준다** | 식별 단위는 전화번호로 유지. **`/admin/payers/[id]` 의 "성인 확인 완료" 표시는 제거**해야 합니다. `ageVerified` 의 의미를 "PG 인증 완료"로 바꿔 기록 |

어느 쪽이든 **근거 없이 "성인 확인 완료"라고 표시하는 현재 상태는 고쳐야 합니다.**

#### (b) 분쟁 대응이 전적으로 PG 조회 API에 걸립니다

우리에겐 원문이 없으므로, *"결제한 적 없다"* 는 이의제기의 최종 근거는 **PG 로그**입니다.

**계약서에 반드시 넣어야 할 조항**
- 거래 조회 API 제공 및 **응답 SLA**
- PG측 거래정보 **보관기간** — 전자상거래법상 대금결제 기록 5년, 최소 5년 권장
- **일 단위 정산내역 파일** 제공 (대사용)
- PG 장애 시 **수기 대사 절차**

#### (c) 🔴 토큰 무효화 통지가 필요합니다

카드 재발급, 유효기간 만료, 계좌 해지가 일어나면 **PG쪽 토큰이 죽습니다. 우리는 알 수 없습니다.**

통지 경로가 없으면 이렇게 됩니다:
```
후원자가 문자 발송 → 결제 실패 → 실패 카운터 누적 → 계정 정지 → CS 폭증
```

현재 스키마에 `PaymentTokenStatus`(ACTIVE / …)는 있지만, **PG가 상태 변화를 알려주는 경로가 없습니다.**

**조치**
1. 연동 규격서에 **토큰 상태변경 통지(webhook)** 포함 요구
2. 통지를 못 받는다면, 최소한 결제 실패코드로 "토큰 무효"를 구분해 `status` 를 `REVOKED` 로 내리고 재등록을 안내하는 처리 필요

#### (d) PG 정산 대사 기능이 없습니다

PG가 실제로 우리에게 입금하는 금액과, 우리 원장의 `CHARGE_GROSS` 합계를 맞춰야 합니다. **현재 PG 정산내역을 받아 대사하는 기능이 없습니다.** 오픈 전 필요합니다.

#### (e) 이 구조의 장점

- 개인정보 보관 범위가 크게 줄어듭니다. 유출 사고가 나도 노출되는 것은 마스킹 값(끝 4자리)에 한정됩니다.
- PCI-DSS 인증 부담이 없습니다.
- 3-way 분리 원칙(해시 + 암호화 + 마스킹)과도 일관됩니다.
