## 2. 1차 — 기능이 깨져 있던 것

### 상품 "결제 화면에 노출" 체크박스가 저장되지 않던 문제
`actions/studio.ts` · `components/studio/product-form.tsx`

해제한 체크박스는 FormData 에 담기지 않으므로 `!formData.has('active') || checked(...)` 는 **항상 true** 였습니다. 짝이 되는 hidden(`activePresent`)을 폼에 추가하고, 그 값이 함께 온 경우에만 체크 상태를 신뢰하도록 바꿨습니다. 이제 숨김이 실제로 저장되고, 복제본·복원 상품이 저장과 동시에 노출되던 일도 없어집니다.

### 상품을 저장할 때마다 진열 순서가 0으로 초기화되던 문제
`actions/studio.ts`

폼에 없는 `sortOrder` 를 액션이 읽어 항상 0이 됐고, 수정 시 그 값이 그대로 덮였습니다. 파서에서 `sortOrder` 를 제거해 **수정은 순서를 건드리지 않고**, 등록 시에만 목록 맨 뒤(`count`)로 넣습니다. 도달 불가능하던 `?? count` 죽은 코드도 정리했습니다.

### 후원 설정의 직접 입력 범위·단위가 결제에 적용되지 않던 문제
`services/charge-select.ts` · `r/[token]/select-amount-panel.tsx` · `r/[token]/page.tsx`

저장만 되고 아무도 읽지 않던 `customMinAmount / customMaxAmount / customAmountStep` 을 결제 컨텍스트(`customMin`/`customMax`/`customStep`)로 내려보내고, **서버가 화면 값과 무관하게 범위·배수를 다시 검사**합니다. 화면도 같은 값으로 안내·검증합니다. 유효 범위(사회복지기관 ∩ 한도 정책) 밖으로는 넓혀지지 않습니다.

### 환불을 요청하면 주문이 목록에서 사라지던 문제
`components/studio/shared.ts` · `studio/orders/page.tsx` · `api/studio/orders/export`

주문 화면 전용 상태 집합 `ORDER_CHARGE_STATUSES`(= `PAID_STATUSES` + `REFUND_REQUESTED` + `REFUNDED`)를 새로 두고 목록·CSV에 적용했습니다. 정산 집계용 `PAID_STATUSES` 와는 의도적으로 분리했습니다. 이로써 도달 불가능하던 "환불됨 / 환불 요청됨" 배지가 실제로 표시됩니다.
> 상단 타일(배송 준비 등)은 **처리 대기 기준**을 유지했습니다. 환불된 주문을 "발송하라"고 세는 것이 더 위험하다고 판단했고, 행에는 환불 배지가 붙습니다.

### 직접 입력 결제가 "지급 대기" 안내를 따라가도 보이지 않던 문제
`studio/orders/page.tsx` · `studio/layout.tsx` · `services/studio-pending.ts`

비실물 지급 조건을 `product.kind = DIGITAL` 단독에서 `DIGITAL 또는 productId = null` 로 넓혀, 후원 내역·주문 화면·사이드바 배지·파트너 API의 기준을 하나로 맞췄습니다.

### 후원자의 배송 요청을 사회복지기관 메모가 덮어쓰던 문제 — 마이그레이션 포함
`prisma/schema.prisma` · 신규 마이그레이션 `20260902200000_shipment_merchant_memo`

`charge_shipment.merchant_memo` 컬럼을 추가해 **후원자 요청(`memo`, 읽기 전용)** 과 **사회복지기관 내부 메모(`merchantMemo`)** 를 분리했습니다. 주문 카드는 둘을 나눠 보여 주고, 폼은 내부 메모만 저장하며, 주문서 CSV에도 두 열로 나갑니다. 환불 시 남기던 "발송분 회수 필요" 안내도 내부 메모로 옮겼습니다(기존 테스트도 이 기준으로 갱신).

### 환불이 반려되면 재요청할 수 없던 문제
`studio/orders/page.tsx` — 서버는 `REJECTED` 재요청을 허용하는데 화면이 "환불 이력이 있으면" 무조건 감추던 조건을 진행 중(`REQUESTED/APPROVED/DONE`)일 때만 감추도록 바꿨습니다.

## 3. 2차 — 돈·장부·법

### 환불 승인이 중간에 실패하면 복구할 수 없던 문제
`services/refund.ts` · `actions/admin/transactions.ts` · `admin/refunds/page.tsx`

- 승인 거래 존재 확인을 **선점(APPROVED) 이전으로** 옮겨, 그 경우 상태가 전혀 변하지 않습니다.
- PG 취소 실패로 `FAILED` 가 된 건을 위해 **`reopenRefund` + `reopenRefundAction`** 을 추가했습니다. 사유를 받고 감사로그(`REFUND_REOPEN`)를 남기며, 환불을 `REQUESTED` 로, 결제를 `REFUND_REQUESTED` 로 되돌려 재시도·거절로 이어갈 수 있습니다. 자동 복구는 하지 않습니다 — PG 취소가 실제로는 성공했는데 응답만 실패했을 수 있어, 관리자가 PG 내역을 확인하고 누르도록 화면에 경고를 붙였습니다.
- 환불 **거절도 트랜잭션으로 묶어** 상태 불일치를 없앴고, 승인에 **사유 입력을 필수화**(거절·직접환불과 동일 기준)했으며, 이미 처리된 건 재승인 시 성공 응답+감사로그 중복이 생기던 것을 막았습니다.
- 관리자 직접 환불에 **결제 금액 대조**를 추가해, 거래번호 오타로 무관한 결제가 환불되는 것을 서버에서 차단합니다.

### 미래 시행일 약관을 등록하면 현행 약관이 사라지던 문제
신규 `services/terms.ts` · `actions/admin/policy.ts` · 공개 약관 3종 · `r/[token]` · `payer-registration.ts` · `admin/terms`

새 버전 등록 시 기존 버전을 즉시 `active=false` 로 내리던 동작을 없앴습니다. 현행 판단은 **시행일 기준**(`currentTermsDoc` / `currentTermsList`)으로 통일했고, `active` 는 "수동 폐기" 의미만 남겼습니다. `/privacy` 만 시행일을 보지 않던 것도 함께 맞췄습니다. 관리자 화면 배지는 **시행 중 / 시행 예정 / 지난 버전 / 폐기** 4단계로 바뀝니다.

### 수수료 상한이 걸릴 때 부가세가 어긋난 채 원장에 확정되던 문제
`services/settlement.ts`

잘라낸 뒤 공급가액·부가세를 **재산출**(`splitSupplyVat`)합니다. 1원 이하 차감액에서 공급가액이 0원이 되던 것도 전액 공급가액으로 처리합니다. `공급가액 + 부가세 = 차감액`, `수수료 합 + 정산금 = 결제금액`, `정산금 ≥ 0` 불변식을 회귀 테스트로 고정했습니다.

### 후원 내역 CSV의 "오늘" 이 서버 로컬 자정 기준이던 문제
`components/studio/shared.ts` · 화면 3곳 · CSV 라우트 2곳

`periodStart()` / `normalizePeriod()` 를 공용으로 만들어 **화면과 CSV가 같은 함수**를 쓰게 했습니다. 운영(UTC)에서 KST 00:00~08:59 결제가 통째로 빠지던 문제가 사라집니다. 검증되지 않던 `period` 파라미터도 화이트리스트로 정규화했습니다.

### 정산 정책·한도 정책의 기간 처리
- 수수료 정책 마감 쿼리에 `effectiveTo: null` 을 추가해 **이미 마감된 정책의 종료일이 미래로 밀리던** 이력 변조를 막았습니다.
- 한도 정책도 "활성 정책이 있으면 거절"에서 **기간 겹침 검사**로 바꾸고, 새 정책 시행일까지 현행을 살려 두도록 트랜잭션으로 처리했습니다. 예약 등록 시 코드 기본값이 조용히 적용되던 공백 구간이 사라집니다.
- 한도 정책 화면도 `active` 대신 **시행 기간**으로 판정하고 적용 기간을 표시합니다.

### 지급 예정 금액이 실제 지급액과 다르던 문제 + N+1
`services/auto-settlement.ts` · `admin/settlements` · `studio/settlement`

- 화면과 배치가 같은 규칙을 쓰도록 `selectPayoutCharges()` 를 공통 함수로 분리하고, 대시보드도 **원장 가용 잔액·최소 지급 금액**을 반영합니다.
- 사회복지기관마다 조회하던 구조를 **집계 4회**로 바꿔, 200곳 기준 600여 쿼리가 나가던 정산 화면을 정리했습니다.
- 사회복지기관별 요약도 이름순 30곳 절단 대신 **원장이 있는 전 사회복지기관을 집계 2회**로 가져와 가능 금액 순 상위 100곳을 보여 주고, 더 있으면 그 사실을 밝힙니다.
- 사회복지기관 정산 화면의 원천징수·실지급 예상은 **다음 회차 지급 대상 금액** 기준으로 계산하고, 이미 지급된 건이 캘린더에 "정산예정"으로 다시 잡히던 것도 제외했습니다.

## 6. 5차 — 수치 신뢰·UI·문구

- **잘린 목록 길이를 건수로 쓰던 곳**을 실제 집계로 교체: 상품·주문(지연 배송, 재고 부족), 결제(결과 확인 필요), 신고, 보관 상품.
- **타일에만 필터가 빠져 있던 곳**에 목록과 같은 `where` 적용(정산·문의·상품).
- **정렬 tie-breaker(`id`)** 추가: 상품·결제·환불·이상거래·수신 문자·신고.
- **대시보드 복붙 제거**: 90줄짜리 두 벌을 한 벌로 합쳐 링크 불일치를 없애고, 문의 타일은 최고 관리자에게만 보입니다.
- **mock 표시**: 결제·환불 화면에 안전 배너를 붙이고, 거래에 기록하는 `provider` 를 **실제 실행 어댑터**로 바꿨습니다.
- **배너**: 종료일 당일까지 노출, 위치 한글 라벨, 홈에 `HOME_TOP`/`HOME_MIDDLE` 실제 렌더.
- **금칙어**: BLOCK 이 결제를 막는다는 사실을 안내와 선택지에 반영.
- **문자 관리**: 페이지네이션·기간 필터 추가, "차단·필터" 탭 판정을 `***` 기준으로 변경.
- **CSV 절단 고지**: 결제 5,000건 / 주문서 3,000건 초과 시 화면 경고.
- **온보딩 체크리스트**: "사업자 정보 등록"을 선택 항목으로 분리, 정산 계좌 링크에서 리다이렉트 스텁 제거.
- **마이페이지**: 실물 주문의 `SKIPPED` 누락, 마케팅 동의 최신 판정, 차단 해제 확인 절차·성공 메시지, 한도 입력 `type="number"`, 빈 화면 연결 버튼, 페이지 범위 초과 시 이동.
- **감사로그**: 종류 수가 조회 상한에 잘려 멈추던 것을 별도 집계로 교체.
- **요율 표시**: 소수점 유효 자릿수 유지(1.8375% 가 "1.84%" 로 보이던 문제).
- **문구·용어**: "결제과 → 결제와", "결제 설정 → 후원 설정", "상위 10명 → 상위 10곳", 사회복지기관 "님" 호칭, 같은 제목의 표 두 개, 금액 범위 확인창의 "자동 보정", 관리자 "탈퇴" 라벨, MO 키워드 플레이스홀더, 시스템 화면 그리드.

## 8. 2차 보완 — 1차에서 남겼던 항목 (2026-09-03)

### 페이지 범위를 벗어나면 목록으로 돌아갈 수 없던 문제
`components/admin/constants.ts` 의 `clampPage()` + 관리자 목록 13개 화면 · 정산 화면의 두 목록

목록이 비면 Pager 도 함께 사라져(빈 상태 분기 안에 있음) `?page=999` 로 들어가면 URL 을 직접 고치는 수밖에 없었습니다. 조회 직후 범위를 벗어난 페이지 번호를 **마지막 페이지로 리다이렉트**합니다. 정산 화면처럼 목록이 둘인 곳은 `rpage`/`page` 를 각각 보정합니다.
> 실동작 확인: `/admin/users?page=999` → `307 → /admin/users?page=1`

### 권한 없는 버튼이 활성 상태로 보이던 문제
`components/admin/constants.ts` 의 `canWrite` / `canManageMoney` / `isSuperAdmin` / `canManageTemplates` + 관리자 화면 19개

**서버 액션이 실제로 막는 등급과 같은 기준**으로 화면의 변경 컨트롤을 잠급니다. `ActionFormWithDetail` 에도 `disabled` 를 추가했고, 이미 조건이 있던 두 곳(잠금 해제)은 조건을 합쳐 덮어쓰지 않게 했습니다.
> 실동작 확인: READ_ONLY·SUPPORT·SUPER_ADMIN 세 계정으로 접속해, 앞의 둘에만 권한 배너가 뜨고 수수료 정책 2개·정산 11개·금칙어 7개 컨트롤이 비활성화되는 것을 확인했습니다(SUPER_ADMIN 은 0개).

### 정산 회차 단건 상태 변경이 화면에 없던 문제
`components/admin/settlement-requests.tsx`

`updateSettlementRequestStatus` 는 호출부가 없었습니다. 그 안에만 있던 안전장치(이체파일이 발급된 건을 반려·검토로 되돌리면 "돈은 나갔는데 원장에 지급 분개가 없는 상태"가 되므로 차단)가 실제 경로 없이 코드에만 남아 있던 셈입니다. 정산 요청 표에 **"단건 처리" 열**을 추가하고, **서버가 허용하는 전이만** 노출합니다.

| 현재 상태 | 고를 수 있는 것 |
|---|---|
| 접수·검토중 | 검토중 / 승인 / 반려 |
| 승인 | 지급 완료 / 지급 실패 / 반려 |
| 지급 완료 | 지급 실패로 되돌리기 |
| 지급 실패 | 승인(재지급 대상) / 반려 |
| 반려 | (없음 — "처리 완료") |

반려·지급실패는 사유가 필수이며, 권한이 없으면 잠깁니다.

### 웹훅 본문 크기 검사가 chunked 요청을 막지 못하던 문제
`server/request-guard.ts` 의 `readTextWithLimit()` · MO / PIN 콜백 라우트

`Content-Length` 만 보고 판단하면 길이 헤더 없는 chunked 전송을 막지 못하고, `req.text()` 로 전부 읽은 뒤 재는 것도 검사 시점에는 이미 메모리에 다 올라간 뒤입니다. **스트림을 읽으며 누적 바이트가 상한을 넘는 순간 중단**하도록 바꿨습니다(인증 이전 단계라 이 자체가 공격 표면이었습니다).

### 같은 집계를 요청마다 두 번 돌던 문제
신규 `server/services/studio-pending.ts`

사이드바 배지(layout)와 대시보드(page)가 같은 count 를 각각 돌려, 대시보드 한 번 렌더에 같은 쿼리가 두 번씩 나갔습니다(둘 다 `force-dynamic`). react 의 `cache` 로 묶어 **요청 단위에 한 번만** 실행합니다. 조건을 한 곳에 모은 덕에, 대시보드만 직접 입력 결제를 세지 않아 사이드바 배지와 수치가 달랐던 것도 함께 해소됐습니다.

### 열람 권한 범위 — 현행 유지 (결정)
READ_ONLY 는 열람이 본래 역할이고, 고객지원도 문의 응대에 이력 조회가 필요하므로 **지금 구조를 유지**하기로 했습니다. 변경 동작은 서버·화면 양쪽에서 모두 막혀 있고, 권한 배너가 무엇을 할 수 없는지 안내합니다.

## 9. 남긴 것과 그 이유

| 항목 | 이유 |
|---|---|
| MO/PIN 웹훅의 타임스탬프·nonce | 사업자 규격서를 받으면 서명 방식 자체가 바뀝니다. 현재도 `providerMessageId` UNIQUE 와 PIN 세션 원자적 선점으로 **이중결제는 막혀 있습니다**. 파트너 API(`partner-auth.ts`)에 이미 있는 패턴을 그대로 옮기면 되므로, 규격서 수령 시 최우선으로 적용하십시오 |
| PIN 콜백의 본문 결속 서명 | 위와 같음. 현재는 정적 공유비밀(`X-Pin-Secret`) 대조이며 코드에 `TODO(계약 후)` 로 표시돼 있습니다 |
| 리버스 프록시 본문 크기 제한 | 애플리케이션에서는 스트리밍 검사로 막았습니다. ALB/Nginx 의 `client_max_body_size` 로 한 겹 더 막는 편이 확실하며, 이는 배포 설정 영역입니다 |
