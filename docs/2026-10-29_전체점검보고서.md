## 2. 중간 (24건)

### 정기후원 배치

**M-1. 건너뜀(SKIPPED) 기록까지 시도 횟수로 세서 첫 실패에 정지한다** (재현함)
`recurring.ts:294` — `recurringRun.count({ recurringId, monthKey })` 가 상태를 거르지 않는다. 자동 출금 승인 전 며칠 건너뛴 약정은 승인 후 첫 잔액 부족에서 바로 정지된다. → `status: 'FAILED'` 만 센다.

**M-2. 재시도가 다음 달로 넘어가면 한 달이 빠지고 실패 한도가 리셋된다**
`recurring.ts:257-258` — `monthKey` 를 원래 출금 예정월이 아니라 배치 실행일로 잡는다. 27일 출금 → 10/27·10/30 실패 → 11/2 재시도 성공이 "11월분"으로 기록되고 다음 출금이 12/27 로 잡힌다. 10월분 미수납, 11월분 누락. 실패 횟수도 11월 1회차부터 다시 센다. → `monthKey` 를 약정의 출금 예정월(`nextChargeOn` 의 원래 월)로 고정.

**M-3. 결제 전에 멱등키를 '완료'로 바꿔, 결제 중 예외가 나면 그달이 조용히 처리된 것으로 넘어간다**
`recurring.ts:313-354` — `idem.release(chargeId)` 를 `executePayment` 전에 부른다. `executePayment` 가 예외(트랜잭션 시간 초과 등)를 던지면 결제 건은 `PENDING_PAYMENT` 로 고착되고, 다음 날 배치는 키 중복으로 "이달 이미 처리" 처리 후 다음 달로 넘긴다. `acquireIdempotency` 는 DB 순간 장애도 '중복'으로 돌려준다. → 결제 건 상태를 확인해 성공일 때만 넘기고, 나머지는 확인 대기로.

**M-4. 약정 금액을 결제 한도와 대조하지 않는다**
`recurring.ts:85-90` 은 1천~200만원만 본다. 실행 시 `checkLimits` 는 기관 최소·최대 금액과 후원자 일·월 한도를 적용한다. 기관 최대 금액을 넘는 약정은 처음부터 성공할 수 없고, 한도 차단 문자와 정기후원 실패 문자가 3회 반복된 뒤 정지된다. → 약정 시 `resolvePolicy` 교집합으로 검사.

**M-5. 정기후원 결제 건을 `DIRECT_TRIGGER` 로 기록하고, 콘솔에는 "문자(MO)·MO 즉시결제"로 보인다**
`recurring.ts:340`, `src/app/studio/charges/page.tsx:294`, `src/app/admin/payments/page.tsx:75`, `charge-cards.tsx:45` — 절대 규칙 7 은 즉시결제를 서면승인 후에만 쓰도록 하는데, 정기후원은 `ALLOW_DIRECT_TRIGGER` 를 보지 않고 이 값을 박는다(실제 차단은 `ALLOW_RECURRING_DEBIT` 하나). 화면은 채널을 `'WEB'` 아니면 모두 MO 로 표시한다. 감사·민원에서 "승인 없이 즉시결제가 열렸다"로 읽힌다. → 결제 모드에 `RECURRING` 을 추가하거나 규칙에 예외 명시, 채널 라벨에 "정기" 추가.

### 기부금영수증

**M-6. 영수증 발급과 환불 승인이 동시에 일어나면 환불된 건이 유효 영수증에 남는다**
`receipts.ts:199, 259-262`, `refund.ts:212` — 대상 건을 트랜잭션 밖에서 읽고, 묶을 때 `receiptId: null` 만 보고 상태는 보지 않는다. 사이에 환불이 승인되면 무효화 훅은 아직 묶이지 않아 아무것도 안 하고, 발급은 환불 건을 묶는다. 무효화 실패도 로그만 남고 재시도가 없다. → 묶는 `updateMany` 조건에 `status: { in: PAID_STATUSES }` 추가, 건수 불일치 시 롤백.

**M-7. 홈택스 CSV 가 발급 당시 정보가 아니라 현재 후원자 정보로 만들어진다**
`receipts.ts:433-466` — 성명·주민번호를 현재 `payerReceiptProfile` 에서 읽는다. 발급 뒤 후원자가 정보를 바꾸면 발급본과 다른 사람 명의로 제출 파일이 생기고, 정보를 지우면 그 영수증은 명세에서 조용히 빠진다. → 발급 시 주민번호 암호문까지 영수증에 스냅샷(암호화 상태로)하고 CSV 는 그것을 쓴다.

**M-8. 공익법인 지정·고유번호를 기관이 스스로 체크하고 아무도 검증하지 않는다**
`actions/fundraising.ts:151-206`, `receipts.ts:171-183`, `donation-landing.tsx:143` — 체크 하나로 공개 페이지에 "기부금영수증 발급 가능(공익법인)" 배지가 뜨고 영수증 발급·명세 생성까지 된다. 지정 만료일(`designatedDoneeUntil`)도 보지 않는다. 변경 감사로그도 없다. 지정 단체가 아닌 기관의 영수증은 연말정산에서 부인되고 후원자에게 가산세 위험이 간다. → 관리자 확인 절차(지정 증빙 첨부 → 관리자 승인), 만료일 검사.

**M-9. 기관 계정 하나로 주민번호 원문 CSV 를 추가 확인 없이 받는다**
`api/studio/receipts/export/route.ts` — 로그인 + 동일 출처만 통과하면 된다. 재인증·2차 인증·다운로드 사유·속도 제한이 없고, 기관 계정에는 역할 구분이 없다. 후원자의 영수증 정보는 기관별이 아니라 전역 1건이라, 그 기관에 한 번이라도 후원한 정보 등록 후원자는 모두 일괄 발급 → CSV 로 이어진다. → 다운로드 시 비밀번호 재확인(또는 OTP), 사유 입력, 일일 횟수 제한.

**M-10. 기관·후원자가 한 행위가 감사로그에 "시스템"으로 남는다**

- **`nan29077/givesign` 은 공개(public) 저장소다.** 커밋된 비밀값은 없고(개발용 기본값만 있으며 운영 부팅 점검이 거부), 커밋 이력에도 키는 없다. 다만 결제·개인정보 처리 코드 전체와 보안 설계(멱등·한도·PIN 콜백 구조)가 공개되어 있으므로 **비공개 전환을 권장**한다. 원본 `nan29077/messagepay` 도 공개 상태다.

## 4. 확인했으나 문제없음 (주요 항목)

- **테넌트 격리**: 캠페인·영수증·명세·후원자·정기후원 목록과 액션이 모두 세션의 `merchantId` / `payerId` 로 범위 제한. 다른 기관의 캠페인 id 주입은 MO·웹·정기후원 모두 서버에서 거절.
- **비공개 미리보기**: `viewer?.merchantId === org.id || viewer?.role === 'ADMIN'` 이 실제 세션 필드와 맞음. 작성 중 캠페인은 담당자만, 비공개 후원페이지는 공개 캠페인 URL 로도 열리지 않음.
- **주민번호**: 화면·스냅샷·문자·로그에는 마스킹 값만. 복호화는 `buildHometaxExport` 한 곳뿐이고 로그 출력 없음. CSV 는 `no-store`, 동일 출처 검사(fail-closed).
- **영수증 번호**: 기관 행 잠금 + `(merchant, tax_year, seq)` 유니크. 무효 번호 재사용 없음. 연도 구간 KST 기준 정확.
- **캠페인 집계**: `charge.campaign_id` + PAID_STATUSES(규칙 10). 키워드 정규화가 등록·매칭 양쪽 동일. MO 처리 순서(대표번호 키워드 → 캠페인 키워드) 정상.
- **정기후원 정상 경로**: 같은 달 성공 후 재실행·출금일 변경·재개 시 멱등키로 재출금 차단(결과 미확인 예외는 H-1). 날짜 계산(1~28일) 월 넘침 없음.
- **마이그레이션 이관 SQL**: `substring(key from 15)` 오프셋 정확, 형변환 안전.
- **새 문자 템플릿 4종**: 관리자 템플릿 화면에 자동 포함, 치환자와 `vars` 일치, 영수증 안내는 링크 보존(편집 불가).
- **동의 분리**: 영수증·정기후원 동의는 가입 화면과 필수 동의 검사에서 함께 빠져 서로 어긋나지 않음.
- **리브랜딩 식별자**: 기관 코드 `GIV-`, 쿠키·서명 헤더·잠금 파일·도커 이름·포트(3060/5463/5462/6390)가 설정하는 쪽과 읽는 쪽에서 일치. 화면 계층에 구브랜드 문자열·이모지 0건. 링크 97종·정적 자산 전수 대조 결과 끊어진 것 0건. 'use client' 파일의 서버 모듈 import 0건.
- **배치 인증**: `/api/cron/recurring` 은 비밀이 없으면 로컬에서만 통과(fail-closed), `safeEqual` 비교, 잠금 확인 불가 시 503.
