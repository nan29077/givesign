# 1부. 정산 프로세스 검수

## 결론: 전 구간 정상 동작합니다. 다만 **알림 누락 1건을 발견해 고쳤습니다.**

### 🔴 발견·수정: 정산 요청이 들어와도 최고관리자가 통보받지 못했습니다

사회복지기관가 정산을 신청하면 `/admin/settlements` 목록에는 정상적으로 뜹니다. 그런데 **아무에게도 알림이 가지 않았습니다.** 관리자가 그 화면을 직접 열어보기 전까지는 요청이 들어온 사실 자체를 알 수 없는 상태였습니다.

- 원인: `requestSettlementAction` 이 요청만 생성하고 `notifySuperAdmins()` 를 호출하지 않음
- 참고로 문의(support/inquiry)는 이미 최고관리자 알림을 보내고 있어, 정산만 빠져 있던 상태였습니다
- 조치: 요청 접수 시 최고관리자 전원에게 알림 발송 (사회복지기관명·코드·요청금·실지급 예정액 포함, `/admin/settlements` 로 이동)
- 알림 발송이 실패해도 요청 접수 자체는 되돌리지 않습니다

**추가로**, 결제 결과 미확인(UNKNOWN) 건도 최고관리자 알림함에 올라가도록 했습니다. 이 건은 후원자 통장에서 돈이 빠졌을 수 있어 대사가 늦을수록 손해가 커집니다.

### 실행 검증 결과

전 구간을 실제로 돌려 확인했습니다.

| 검증 항목 | 결과 |
|---|---|
| 사회복지기관 요청 → 최고관리자 **알림함** 도착 | ✅ (E2E: 미읽음 0 → 1, 제목 "새 정산 요청") |
| 사회복지기관 요청 → 관리자 **정산 목록** 노출 | ✅ (사회복지기관명·코드 함께 조회됨) |
| 요청 즉시 잔액이 **보류**로 잡혀 이중 요청 차단 | ✅ (available 0, 재요청 시 "초과" 오류) |
| **승인 전** 건은 이체파일에 들어가지 않음 | ✅ (`buildPayoutRows` 빈 배열, `assertPayable` false) |
| 승인 후 이체파일에 복호화된 계좌·금액 포함 | ✅ |
| 이체파일 발급 시 **배치번호** 기록 | ✅ |
| 지급 완료 시 원장에 **지급 + 원천징수** 2분개 | ✅ |
| 지급 후 **잔액·보류가 모두 0** 으로 정확히 떨어짐 | ✅ (지급+원천징수 = 요청금 전액) |
| 같은 건 재지급 시 분개가 늘지 않음 (멱등) | ✅ (2건 유지) |
| 원천징수액이 화면 미리보기와 서버 계산이 일치 | ✅ (아래 수정 반영) |

### 🟡 발견·수정: 원천징수 미리보기가 옛 계산식을 쓰고 있었습니다

정산 요청 화면의 "원천징수 예상" 이 어제 바꾼 2단계 계산이 아니라 **옛 3.3% 단일 절사**를 쓰고 있었습니다.

- 예: 정산 가능금 7,488원 → 화면은 **247원** 표시, 실제 접수는 **0원**(소액부징수)
- 돈이 잘못 나가는 건 아니지만(서버 계산은 정상) 사회복지기관가 표시 금액과 다른 결과를 받습니다
- 조치: 미리보기가 서버와 **같은 `calculateWithholding()`** 을 호출하도록 통일. 표시도 `소득세 / 지방소득세 / 원천징수 합계 / 실지급 예상` 으로 나누고, 소액부징수면 `0원 (소액부징수)` 라고 명시

계산이 두 군데 나뉘어 있으면 반드시 어긋나므로 한 함수로 합쳤습니다.

# 2부. 정산 주기(영업일 5일) 반영

## 규칙

> **정산일 = 후원(결제 완료)일 다음날부터 세어 영업일 5일째**
> 영업일 = 토·일과 공휴일(법정공휴일·대체공휴일·임시공휴일·근로자의 날)을 뺀 날

지시하신 예시가 그대로 나오는지 전수 검증했습니다.

| 후원일 | 정산일 | 확인 |
|---|---|---|
| 2026-08-03 (월) | **2026-08-10 (월)** | ✅ 지시하신 예시와 일치 |
| 2026-08-07 (금) | **2026-08-14 (금)** | ✅ 다음 주 금요일 |
| 2026-08-08 (토) | **2026-08-14 (금)** | ✅ 금·토·일이 하나로 모임 |
| 2026-08-09 (일) | **2026-08-14 (금)** | ✅ |
| 2026-08-12 (수) | 2026-08-20 (목) | 광복절(8/15 토) + 대체공휴일(8/17 월)만큼 밀림 |
| 2026-02-13 (금) | 2026-02-25 (수) | 설 연휴 3일만큼 밀림 |
| 2026-04-28 (화) | 2026-05-07 (목) | 근로자의 날·어린이날만큼 밀림 |

1년 365일 전수로 "정산일은 반드시 영업일이고 후원일보다 뒤" 임을 확인했습니다.

## 공휴일은 관리자가 직접 관리합니다

임시공휴일은 매년 갑자기 지정됩니다. 코드에 박아두면 그때마다 배포해야 하고, 배포가 늦으면 **그 기간 정산일이 통째로 틀어집니다.** 그래서 `public_holiday` 표를 만들고 **관리자 화면(`/admin/holidays`)** 에서 바로 추가·수정할 수 있게 했습니다.

- 2026년 공휴일 22건을 미리 넣어두었습니다 (설날·삼일절+대체·근로자의 날·어린이날·부처님오신날+대체·지방선거·현충일·광복절+대체·추석+대체·개천절+대체·한글날·성탄절)
- 2027년은 **날짜가 확정된 양력 공휴일만** 넣었습니다. 음력(설날·추석)과 그에 따른 대체공휴일은 확정 발표 후 추가하시면 됩니다
- 화면이 두 가지를 경고합니다: ①해당 연도 공휴일이 아예 없을 때 ②그 해에 설날·추석이 등록되지 않았을 때
- 날짜는 `type=date` 로 브라우저가 1차 검증하고, 서버가 "달력에 실제로 있는 날짜인지" 2차 검증합니다 (2026-02-31 같은 값 차단)

> **한 가지 확인 부탁드립니다.** 근로자의 날(5/1)을 영업일에서 제외했습니다. 관공서 공휴일은 아니지만 **은행이 쉬어 이체가 불가능한 날**이라 정산 지급 기준으로는 빼는 게 맞다고 판단했습니다. 지급대행(쿠콘) 운영 기준과 다르면 관리자 화면에서 해당 행을 끄시면 됩니다.
> 시드로 넣은 2026년 날짜도 실제 운영 전에 한 번 대조해 주시길 권합니다.

## 화면 반영

**정산 현황 탭 상단**에 안내 카드를 넣었습니다.
- "정산은 후원일로부터 **영업일 5일 후**에 이루어집니다"
- 영업일 정의(토·일 + 공휴일 제외)
- **오늘 후원되면 → 언제 정산** / **금·토·일 후원분 → 언제 정산** 을 실제 날짜로 계산해 표시
- 예시 문구: "8월 3일(월) 후원 → 8월 10일(월) 정산"

**캘린더는 세 가지를 구분**해 표시합니다.
- **후원** (회색 세로선): 그 날 결제 완료된 금액·건수 + 바로 아래 `→ 8월 10일 정산` 표기
- **정산 예정** (노랑 테두리 배지): 그 날 정산될 금액 (영업일 5일 전 후원분)
- **지급 완료** (초록 배지): 실제로 계좌에 나간 금액
- **공휴일** (연분홍 배경): 영업일에서 빠지는 날

지난달 후원이 이번 달에 정산되므로 앞쪽 45일치를 함께 읽어 계산합니다.

# 4부. 유튜브 채널 연동 현황 (개발 미진행 — 보고만)

지시하신 대로 **개발은 하지 않았습니다.** 현재 상태만 정리합니다.

## 지금 구현된 방식

```
사회복지기관가 "구글 계정으로 채널 연결" 클릭
        │
        ▼
구글 OAuth 동의 화면 (scope: youtube.force-ssl)
        │  state = 사회복지기관ID + 서명
        ▼
GET /api/youtube/oauth/callback
        │
        ├─ state 검증: 세션의 사회복지기관와 일치하는지 + 서명 확인 (CSRF 방지)
        ├─ code → access/refresh 토큰 교환
        ├─ 채널 정보 조회 (channelId, title, thumbnail)
        └─ YouTubeConnection 에 upsert
              · accessToken / refreshToken 은 **암호화 저장** (평문·로그 금지)
              · status = CONNECTED
        │
        ▼
후원 결제 성공 시 → liveChatMessages.insert 로 라이브 채팅에 메시지 등록
```

| 항목 | 현재 상태 |
|---|---|
| 인증 방식 | 구글 OAuth 2.0 (Authorization Code) |
| 권한 범위 | `https://www.googleapis.com/auth/youtube.force-ssl` |
| 토큰 저장 | AES 암호화, 로그에 남기지 않음 |
| CSRF 방지 | state 에 사회복지기관ID + 서명, 세션과 대조 |
| 연결 해제 | 스튜디오에서 직접 해제 가능 |
| 라이브 방송 조회 | 연결된 채널의 진행 중 방송 조회 + 수동 갱신 |
| 할당량 관리 | 일일 10,000 units 기준으로 사전 예약·차단 (`yt:quota:<날짜>`) |
| 실연동 여부 | **아직 mock 어댑터.** 구글 OAuth 클라이언트 승인 후 어댑터 교체로 전환 |

## 제가 판단하는 현재 방식의 위치

이 구조는 국내외 후원 서비스가 공통으로 쓰는 표준 방식입니다. 토큰 암호화·state 검증·할당량 가드까지 들어가 있어 기본기는 갖췄습니다.

다만 **말씀하신 "셀러 계정 → 라이브커머스 → 유튜브 AI 챗봇" 탭은 지금 연결된 `기브싸인` 폴더에 없습니다.** 다른 프로젝트로 보입니다.

비교·반영을 원하시면 둘 중 하나를 부탁드립니다.
1. 그 프로젝트 폴더를 Cowork 에 연결해 주시면 코드를 직접 보고 대조하겠습니다
2. 또는 해당 탭의 화면 캡처와 "기브싸인와 어떤 점이 달라야 하는지"를 알려주시면 그에 맞춰 설계하겠습니다

특히 **AI 챗봇**이라는 이름을 보면 단순 채널 연결을 넘어 라이브 채팅을 읽고 자동 응답하는 기능일 가능성이 있는데, 그렇다면 지금 기브싸인의 "후원 메시지를 채팅에 쓰기만 하는" 구조와는 필요한 권한과 폴링 구조가 달라집니다. 확인 후 지시 주시면 진행하겠습니다.
