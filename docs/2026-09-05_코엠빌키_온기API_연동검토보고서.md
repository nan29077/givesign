# 코엠 빌키결제 · 온기 API 연동 검토 보고서

작성일 2026-09-05. 검토 대상은 (1) 코엠페이먼츠 빌키결제 DIRECTPAY v1.1 규격서, (2) 온기 사회복지기관 API 문서(https://www.ongi.site/api), (3) 기브싸인 현재 결제 어댑터 구조다.

결론부터: **코엠 빌키는 붙일 수 있고 기브싸인 구조와 잘 맞는다. 온기는 붙을 수는 있으나 지금 필요한 것(MO 기반 서버 주도 승인)과 결이 다르다.** 다만 양쪽 모두 규격서에 빠진 항목이 있어, 코드를 쓰기 전에 확인해야 할 것이 아래 5절에 정리돼 있다.

---

## 1. 현재 기브싸인 결제 구조 (기준선)

| 구성 | 파일 | 상태 |
|---|---|---|
| 어댑터 인터페이스 | `src/server/adapters/payment/index.ts` | 완성. 7개 메서드 |
| 헥토(내통장결제) 구현 | `src/server/adapters/payment/hecto.ts` | 서명·암호화·상태매핑 완성. **PIN 인증창만 mock** |
| Mock 구현 | 같은 파일 index.ts 내 | 금액 끝자리로 실패 시나리오 재현 |
| 빌키 저장 | `PaymentMethodToken` (schema.prisma:933) | `provider` 컬럼 있음(기본 HECTO), `method` = ACCOUNT/CARD |
| 정기결제 모델 | — | **없음** |

핵심 제약 두 가지를 먼저 짚는다.

- `env.payment.provider` 는 **전역 단일값**이다(`env.ts:122`). 내통장결제(헥토)와 카드(코엠)를 동시에 운영하려면 이 구조로는 안 된다.
- `PaymentMethodToken.provider` 컬럼은 저장만 되고 **승인 라우팅에 쓰이지 않는다.** 다중 PG 의 실제 분기점은 여기여야 한다.

## 2. 코엠페이먼츠 빌키(DIRECTPAY) — 연동 가능. 권장.

### 2.1 메서드 대응

| 기브싸인 인터페이스 | 코엠 엔드포인트 | 판정 |
|---|---|---|
| `createRegistrationSession` | (없음 — 키인 방식) | 구조 차이. 결제창이 없다 |
| `completeRegistration` | `POST /api/cc/billkey/register` | 대응 |
| `approve` | `POST /api/cc/billkey/approv` | 대응 |
| `cancel` | `POST /api/cc/approv/cancel` | 대응 |
| `revokeBillKey` | `POST /api/cc/billkey/unregister` | 대응 |
| `inquire` (거래결과조회) | **규격에 없음** | **치명적 공백. 5절 참고** |
| `requestPinLink` | 해당 없음 | 카드 빌키에 PIN 개념 없음 |

도메인은 개발기 `https://183.111.29.87:39500`, 상용기 `https://paycc.coam.co.kr`.

### 2.2 서명 방식이 헥토와 완전히 다르다

헥토는 SHA256 hex, 재료는 mercntId+authNo+reqDay+reqTime+hashKey.
코엠은 **HMAC-SHA256 → Base64**, 키는 API_KEY. 별도 함수가 필요하다.

여기서 규격서의 함정이 하나 있다. 공통 절(3.1.1.1)의 생성규칙은 `orderno + orderdt + ordertm + reqamt` 로 적혀 있지만, **실제 각 전문의 재료는 전부 다르다.**

| 전문 | checkHash 재료 |
|---|---|
| 빌키 발급 | `mid + card_no + reqdt + reqtm` |
| 빌키 결제 | `mid + orderno + orderdt + ordertm + buy_reqamt + bill_key` |
| 결제 취소 | `tid + mid + cancel_amt` |
| 빌키 해지 | `mid + bill_key` |

공통 절 예시를 그대로 구현하면 **전건 EC5008(인증 및 무결성 검증 실패)** 이 난다. 전문별로 따로 만들어야 한다.

### 2.3 규격서 자체의 불일치 (코엠에 확인 필요)

- **필드명 대소문자**: 발급·결제는 `checkHash`, 취소·해지는 `checkhash`. 오타인지 실제 구분인지 확인해야 한다. 잘못 보내면 EC2015 또는 EC5009.
- **응답 Content-Type**: 빌키 발급·결제 응답은 `application/x-www-form-urlencoded`, 취소·해지 응답은 `application/json` 으로 적혀 있다. 파서를 전문별로 분기해야 하는데, 실제로 그런지 확인이 먼저다.
- **길이 충돌**: 요청 `orderno` 는 Max 65 인데 응답 `orderno` 는 Max 20 이다. 20자를 넘는 주문번호는 응답에서 잘릴 수 있다. → 기브싸인 PG 주문번호는 **20자 이내**로 설계한다(현재 접두 `MSG`).
- 카드사코드 리스트에 2305~2310 이 중복 기재돼 있다(단순 문서 오류로 보임).

### 2.4 구조적으로 새로 생기는 문제

**(가) 카드번호를 우리 서버가 직접 받는다.**
DIRECTPAY 는 키인 방식이라 결제창 리다이렉트가 없다. 헥토(결제창)와 등록 UX 가 근본적으로 다르다.
- `/r/[token]` 등록 화면에 카드 입력 폼을 새로 만들어야 한다.
- 카드 원문은 메모리에서만 다루고 즉시 폐기한다. `PaymentMethodToken` 주석대로 발급사명 + 끝 4자리만 남긴다(schema.prisma:946).
- 여신전문금융업법상 카드정보 취급 요건과 PCI-DSS 범위가 넓어진다. 로그·APM·에러 리포팅에 카드번호가 새지 않도록 `logger.ts` 마스킹 대상에 `card_no` 를 반드시 추가한다.
- `card_ssn`(주민번호 앞 6자리)은 **선택 항목이므로 받지 않는다.** 받는 순간 개인정보 저장·파기 절차가 따라붙는다.

**(나) PIN 인증 단계가 사라진다.**
현재 헥토 경로는 `HECTO_PIN_LINK_IS_MOCK = true`(env.ts:82) 때문에 실결제가 막혀 있다. 카드 빌키에는 PIN 이 없으므로 코엠 경로는 이 차단을 통과해 실서비스가 가능하다.

바로 그래서 위험하다. **후원자 인증 없이 서버가 단독으로 출금**하는 구조가 된다. 코드를 쓰기 전에 "문자 링크 클릭 = 결제 의사표시"로 볼 수 있는지 법무 확인이 선행돼야 한다. `charge-flow.ts` 가 PIN 콜백을 전제로 짜여 있다면 카드용 분기를 따로 만들어야 한다.

**(다) 특수문자 제한이 후원자 메시지와 충돌한다.**
코엠은 `& ; \n \ | ' "` 입력 시 오류가 난다고 명시한다. 후원자 메시지가 `buy_itemnm` 에 실리면 결제가 통째로 실패한다. 금칙어 필터와 별개로 **PG 전송용 sanitizer** 를 둬야 한다.

**(라) 사회복지기관 서버 공인 IP 등록이 필수다 (개발기·상용기 각각).**
로컬 개발 PC 의 유동 IP 로는 개발기 테스트조차 안 된다. AWS 배포 시 NAT Gateway EIP 로 아웃바운드 IP 를 고정해야 한다. **이게 일정상 가장 앞에 와야 하는 작업이다.**

**(마) 개발기가 IP 기반 HTTPS 다.**
`https://183.111.29.87:39500` 은 인증서 CN 이 IP 와 맞지 않아 Node `fetch` 가 검증 실패할 가능성이 높다. 개발기 전용 CA/우회 설정이 필요하며, **운영 코드 경로에는 절대 반영하지 않는다.**

## 3. 온기 API — 붙을 수는 있으나 용도가 다르다

### 3.1 공개된 사회복지기관 외부 API 의 실제 범위

Base URL `https://api.ongi.site/api/external/integration/merchant/v1/organization`, 인증 `X-API-Key`(+선택 `X-API-MID`).

제공되는 것은 **QR 관리 4개 + 결제내역 조회 2개**가 전부다.

- QR 생성 / 목록 / 단건 / 비활성화
- 결제내역 목록 / 단건

**빌키 발급도, 빌키 승인도, 결제 요청도 외부 API 에 없다.** 결제는 `pay.ongi.site` 결제창으로 후원자를 보내고, 완료되면 서버로 노티(webhook)를 받는 구조다.

### 3.2 온기의 "내통장결제"는 헥토를 대신 열어주는 것이다

문서의 결제창 쿼리 설명에 명시돼 있다: `payment_method=bank|account` → *"계좌·로그인·금액 준비 후 **헥토 자동 오픈**"*.

즉 온기 경유 내통장결제 = 헥토 결제창이다. 기브싸인는 이미 헥토를 직접 붙여 두었으므로, 온기를 한 겹 더 끼우면 **수수료와 장애점만 늘고 얻는 기능이 없다.** 내통장결제는 헥토 직결을 유지하는 것이 맞다.

### 3.3 정기결제(장기결제) — 규격이 공개돼 있지 않다

문서에서 확인되는 단서는 두 개뿐이다.

- QR 생성 시 `subscription_period` (정기결제 기간, 개월)
- `POST https://api.ongi.site/api/v1/front/payment/regular/register` (정기 등록)

문제는 `/api/v1/front/*` 계열이 **온기 회원 앱용**이라는 점이다. 문서에 *"사회복지기관 외부 API(X-API-Key)와 별도로, 온기 회원 앱·pay.ongi.site·order.ongi.site에서 쓰는 생성 API"* 라고 적혀 있고, 예제도 `Authorization: Bearer <member_access_token>` 을 쓴다. 해지·조회·재시도 규격은 아예 공개돼 있지 않다.

→ **기브싸인가 사회복지기관 자격으로 서버에서 정기결제를 등록·해지·조회할 수 있는 규격이 있는지 온기에 문의해야 한다.** 지금 문서만으로는 구현할 수 없다.

### 3.4 온기에도 코엠이 이미 붙어 있다

같은 절에 `POST …/payment/coam/simple` (코엠 카드)가 나온다. 온기도 코엠을 결제사로 쓰고 있다는 뜻이다.

**같은 코엠을 우리가 직접 붙일지, 온기 경유로 쓸지 하나만 골라야 한다.** 둘 다 하면 정산과 대사가 두 갈래가 되고, 기브싸인의 append-only 정산 원장에서 이 분리는 사후에 되돌릴 수 없다. 코엠과 직접 계약이 완료된 상태이므로 **직결을 권한다.**

### 3.5 온기 결제 노티에서 주의할 점

- 서명: HMAC-SHA256, 메시지 `{X-Ongi-Timestamp}.{raw_json_body}`, 헤더 `sha256=` + lowercase hex. **파싱 전 raw body** 로 검증해야 한다. Next.js Route Handler 에서 `req.text()` 로 먼저 받아야 하며, 기존 `x-givesign-signature` 검증 코드와 재료가 다르므로 재사용 불가.
- 멱등 키: `payment_pk` / `payment_code`.
- **타임아웃 15초, 자동 재전송 큐 없음.** 우리 쪽 처리가 15초를 넘으면 통지가 유실되고 복구 수단이 없다. 반드시 즉시 200 반환 후 outbox/bullmq 로 비동기 처리한다.
- 재전송이 없으므로 **결제내역 조회 API(`/payment-transactions/list`)로 주기 대사(reconcile)** 를 반드시 돌려야 한다. `/api/cron/*` 에 잡을 추가한다.

### 3.6 온기가 실제로 값어치 있는 지점

MO→PIN→승인 흐름의 대체재로는 부적합하지만, **QR 결제와 정기기부 UI 를 이미 갖추고 있다.** 문자 채널 외에 QR/링크 결제 채널을 늘리려는 목적이라면 붙일 이유가 있다. 그 경우 기브싸인는 온기의 "사회복지기관"이 되고, 정산은 온기를 통해 들어온다.

## 4. MID 3개 정리 — 여기서 막혀 있다

### 4.1 정기결제 MID `PDHRXSOING…` (32자)

받은 값은 대문자 32자다. 그런데 어느 규격과도 맞지 않는다.

| 규격 | MID 형식 |
|---|---|
| 코엠 | `mid` **Fix 15** (AN) |
| 온기 | API MID 예시 `API000001ABCD1234` = 16자 |
| 헥토 | `mercntId`, 통상 15자 내외 |

32자 대문자 난수는 MID 라기보다 **API Key 또는 라이선스 키**의 형태다. 어느 회사(헥토/코엠/온기)에서 받은 무슨 값인지 확인이 필요하다. 확인 전에는 코드에 넣지 않는 편이 낫다.

그리고 이 값은 시크릿이다. **문서·코드·깃 커밋에 넣지 말고 `.env` 에만 둔다.** (이 보고서에도 전체 값을 적지 않았다.)

### 4.2 셀러브릭스 헥토 MID 공유 — 기술은 되지만 정산이 섞인다

기술적으로는 `HECTO_MID` 하나만 바꾸면 끝이다. 문제는 회계다.

헥토 MID 단위로 **정산 계좌·거래내역·수수료율**이 묶인다. 두 서비스가 같은 MID 를 쓰면,

1. 정산 대사에서 셀러브릭스 거래와 기브싸인 거래를 **분리할 수 없다.** 주문번호 접두(`MSG`)로 사후 구분은 되지만, 그건 회계 분리가 아니라 라벨링이다.
2. 한쪽 사고로 MID 가 정지되면 **두 서비스가 같이 멈춘다.**
3. 기브싸인는 사회복지기관별 정산 원장이 append-only 라 잘못 쌓인 분개를 지울 수 없다. 반대분개로만 정정된다.

→ **헥토에 서브MID(하위 상점) 발급이 가능한지 먼저 문의**하기를 권한다. 불가하다면 최소한 ordNo 접두 규칙을 계약 수준으로 고정하고, 정산 대사 스크립트를 서비스별로 분리해야 한다.

## 5. 규격서에 빠져 있어 반드시 물어야 하는 것

### 코엠페이먼츠에 (우선순위 순)

1. **거래결과조회 API 또는 결과 노티(webhook) 규격.** 이게 없으면 승인 응답이 유실됐을 때 출금 여부를 확정할 방법이 없다. 기브싸인 멱등성 4중 방어의 "타임아웃 시 조회로 확정" 경로가 통째로 성립하지 않고, 후원자 통장에서는 돈이 빠졌는데 결제는 실패로 닫히는 상황이 복구 불가로 남는다. **최우선 요청 항목이다.**
2. **동일 `orderno` 재요청 시 동작.** 기존 승인 결과를 돌려주는가(멱등), 아니면 중복 승인되는가. 규격서에 없다. 중복 승인이면 앱에서 재시도를 전면 금지해야 한다.
3. `checkHash` / `checkhash` 표기 통일 여부.
4. 응답 Content-Type 이 전문별로 실제로 다른지.
5. 부분취소 지원 여부(EC1088 "부분 취소 불가" 코드가 있는 걸 보면 조건부로 보인다).
6. 개발기 IP 등록 절차와 개발기 인증서 정보.

### 헥토파이낸셜에

7. 셀러브릭스 MID 하위에 기브싸인용 **서브MID 발급 가능 여부.**
8. (기존 미결) **PIN 인증창 연동규격서.** 이게 와야 `HECTO_PIN_LINK_IS_MOCK` 을 내릴 수 있다.

### 온기에

9. 사회복지기관 자격(X-API-Key)으로 **정기결제 등록·해지·조회**를 서버에서 호출할 수 있는 규격이 있는지.
10. 노티 실패 시 재전송 정책이 정말 없는지, 대사용 조회 API 의 rate limit.

### 사용자 확인 필요

11. **정기결제 MID 32자 값의 출처와 용도** (4.1절).
12. 온기를 어떤 목적으로 붙이는지 — QR/링크 결제 채널 확장인지, 정기결제 엔진 대여인지. 답에 따라 붙일 범위가 완전히 달라진다.

## 6. 코드 작업 범위 (규격 확인 후)

### 6.1 다중 PG 라우팅 — 선행 리팩터링

지금 구조로는 헥토와 코엠을 동시에 운영할 수 없다.

- `getPaymentAdapter()` → `getPaymentAdapter(method: PaymentMethodKind)` 로 시그니처 변경
- 승인 시점의 라우팅 키는 `PaymentMethodToken.provider` (이미 있는 컬럼)를 쓴다. 빌키를 발급한 PG 로만 승인이 나가야 한다.
- `env.payment.provider` 단일값 → `PAYMENT_PROVIDER_ACCOUNT` / `PAYMENT_PROVIDER_CARD` 로 분리
- `hecto.ts:250` 의 `CARD_NOT_SUPPORTED` 분기 제거 (어댑터 라우팅에서 갈라지므로 불필요해진다)

### 6.2 코엠 어댑터 신규

- `src/server/adapters/payment/coam.ts`
- `COAM_SPEC` 상수 블록(hecto.ts 의 `HECTO_SPEC` 패턴 그대로) — 4개 경로 + 결과코드
- HMAC-SHA256/Base64 서명 함수 4종(전문별 재료가 다르므로)
- `x-www-form-urlencoded` 응답 파서
- `EC****` → `ProviderResult` 매핑. **`isIndeterminate` 판정을 반드시 이식한다** — HTTP 5xx/408/429 를 확정 실패로 처리하면 회수 경로가 사라진다(hecto.ts 의 해당 주석 참고)
- 단위 테스트: 서명 벡터 4종, 특수문자 sanitize, 20자 주문번호 경계

### 6.3 카드 등록 UI

- `/r/[token]` 에 카드 입력 폼(번호/유효기간/비밀번호 앞 2자리/명의자)
- 서버 액션에서 즉시 코엠 register 호출 후 원문 폐기
- `logger.ts` 마스킹에 `card_no`, `card_pw`, `card_ssn` 추가

### 6.4 정기결제(장기결제) — 신규 설계

**모델이 아예 없다.** 아래가 전부 신규다.

- `Subscription`(사회복지기관·후원자·빌키·금액·주기·다음 결제일·상태) + `SubscriptionCycle`(회차별 결제 이력)
- 스케줄러: bullmq + `/api/cron/subscription` 잡
- 실패 재시도 정책(D+1/D+3 등), 연속 실패 시 자동 해지
- 후원자 해지 화면(`/my/account` 확장) 및 해지 즉시 반영
- 정산 원장 연동 — 회차별로 분개가 쌓이므로 기존 append-only 규칙 그대로 적용
- MT 문자: 결제 예정 사전 고지, 결제 완료, 실패 안내

코엠 빌키만 있으면 기술적으로 가능하다(빌키 결제를 주기적으로 호출). 온기를 쓰면 이 전부를 온기가 대신하지만, 3.3 의 규격 공백 때문에 지금은 판단할 수 없다.
